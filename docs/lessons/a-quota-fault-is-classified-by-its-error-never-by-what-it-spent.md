# A quota fault is classified by its ERROR, never by what it spent

_Relocated VERBATIM from `.claude/rules/agent-operating-lessons.md` (always-loaded tier) — the rules file now carries the hook and links here. Nothing was shortened._

[A quota fault is classified by its ERROR, never by what it spent](.) — 2026-09-10, cc-backlog `d98bf0055818` (Fable 5.1 effort re-sweep, `docs/research/fable51-effort-sweep-2026-09-10/`): a 5-hour session limit (HTTP 429) arrived AFTER full 64K/128K/192K-token streams — `served` non-empty, `output_tokens` 128000, `cost_usd` $7.44 for no answer — so a classifier keyed on "nothing was served ⇒ quota fault" filed quota walls as ARM failures, while the one genuine arm failure (`cp-09` @max, "response exceeded the 64000 output token maximum" after 256K tokens) is indistinguishable from them on every usage field. ⇒ classify a failed cell on `api_error_status` / the error text, never on tokens or cost. Two corollaries for any headless `claude -p` grid on this box: (a) every failure lands on an EXACT multiple of the output cap, because each continuation is a NEW request the rate limiter re-checks — a cap-boundary error cluster is the signature of a quota wall, not of a model limit, and the discriminator is the account's live 5-hour %; (b) `usage.output_tokens` is the CONTINUED total and can exceed `CLAUDE_CODE_MAX_OUTPUT_TOKENS` several-fold while `usage.iterations` is sometimes EMPTY, so derive continuations as `ceil(out/cap) − 1` from the total, never from iterations.
