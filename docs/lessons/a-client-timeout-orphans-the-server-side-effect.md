# A client timeout orphans the server-side effect

2026-10-22, session kte-w3, load ~450: 9 `Agent({name})` teammate spawns each failed with `it2-kitty: kitty launch failed (rc=124)`, yet kitty opened all 9 panes. `bin/it2-kitty`'s `kt()` wraps `kitty @ launch` in `timeout`, and `timeout` kills the CLIENT only: the request had already reached the kitty server, which completed it seconds later. With the reply lost, no pane id was recorded, so Claude Code never delivered a command, and `bin/cc-pane-runner` waited out its 300 s and then became an ordinary login shell that nobody owned or would ever close. ⇒ **a timeout on a request that CREATES something is an unknown, not a no: the effect may still land after you report failure.** Make the effect findable without the reply by tagging it at request time with a unique marker (here a `--var cc_spawn=<nonce>` user var). On a lost reply, reconcile against the server's own listing for that exact marker, within a bound, and adopt or undo what you find. Give the created thing its own deadline as a backstop for an arrival later than the reconcile bound (the runner now closes an agent pane that receives no command, through the same fullscreen guard as every other close). Never touch an object that lacks the exact marker. Fix: `bin/it2-kitty` `reconcile_spawn`, `bin/cc-pane-runner` `_no_command`; tests `tests/it2-kitty-launch-timeout-orphan.bats`, `tests/cc-pane-runner-no-command-closes.bats`.
