# Freshness is relative to the SUBJECT, not the clock

_Relocated VERBATIM from `.claude/rules/agent-operating-lessons.md` (always-loaded tier) — the rules file now carries the hook and links here. Nothing was shortened._

[Freshness is relative to the SUBJECT, not the clock](.) — 2026-09-09, `bin/cc-classify` gaining a `blocked-on-permission` cause (landed b1897fdb8): a store with a liveness heartbeat lets a consumer tell "nothing pending" from "the producer never ran", and the obvious reading of that heartbeat — *is it recent?* — is the wrong one. What a consumer actually needs is whether the observer was running **at the moment its SUBJECT could have produced a record**, so the comparison is `heartbeat_mtime >= subject's last activity`, never `now - heartbeat_mtime < some_bound`. An absolute bound answers a question about the BOX and gets read as an answer about the SESSION: on a quiet machine every heartbeat goes stale while the fleet is perfectly healthy, and on a busy one a heartbeat written by some OTHER session one second ago "proves" an all-clear for a session that went silent an hour earlier under a dead hook. The subject-relative form is immune to both because it is a statement about one timeline. Generalises to every absence-is-evidence read: a poller's last-run stamp, a sweeper's cursor, a watcher's mtime — ask *"was it observing when the thing I care about would have happened?"*, not *"did it run lately?"*. Companion from the same session, mechanically separate and equally reusable: **a commit made in a SHARED checkout is not merely a policy violation, it is a fleet-wide converge BLOCK.** The live layer is advanced by `merge --ff-only`, so one local commit trunk does not have makes the advance structurally impossible — `wrap-ledger` renders it as `🚀 … NO converge budget applies`, which is the tell that this is not a lag that time will clear. `git cherry origin/main HEAD` separates the two cases in one command: `-` means the content is already on trunk (a duplicate the converger can discard), `+` means it is real unlanded work. 🚨 **CORRECTED IN THE SAME SESSION, and the correction is the load-bearing half: landing an EQUIVALENT COPY does not clear the block.** I cherry-picked the stranded commit into my worktree and landed it; `deploy-live` still REFUSED, because `merge --ff-only` compares ANCESTRY and the local commit is still there — and `git cherry` still printed `+`, since the rebase gave the landed copy a different patch-id. Only two things clear a divergence: the OWNER lands that very commit, or the checkout is reset once its content is proven present. **So judge OWNERSHIP before touching it, with one command** — `cc-sessions --json | jq '.[] | select(.cwd=="<the checkout>")'`. A live session in that cwd means the work is THEIRS: the second commit I found there was a peer's 616-line feature (`bin/cc-mission`, `bin/cc-signoff`), and five live sessions shared the tree. Landing a live peer's in-flight feature through your own `/ship` is not a rescue, it is a fork of their branch under a sha they will never see. Surface it to them and stop. My own rescue was defensible only because its author was a SCRIPT (`cc-memory-rotate`) and its diff was three appended lines — and even so it bought nothing, which is the point. Read a stranded diff's real size before judging it, too: `git diff --stat <deploy-base>..HEAD` against an OLD base renders every file trunk gained since as a DELETION (5,619 of them here, all phantom); diff against the commit's own PARENT. Third, small and expensive: **ship-land refuses a second land from one worktree while the first is in flight (rc 11)** and its post-push stranded sweep runs for minutes AFTER `land-verify` has already printed success — so a log showing `HEAD -> main` is not the process exiting. Await the pid, not the push line.
