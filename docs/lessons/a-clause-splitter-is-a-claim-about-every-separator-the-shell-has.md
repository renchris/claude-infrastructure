# A clause splitter is a claim about EVERY separator the shell has

_Relocated VERBATIM from `.claude/rules/agent-operating-lessons.md` (always-loaded tier) — the rules file carries the hook and links here. Nothing was shortened._

[A clause splitter is a claim about EVERY separator the shell has](.) — 2026-09-17, `git_add_force_scan` (landed): an argv scanner that split on `|`, `||`, `&&`, `;`, `;;` and `&` still had a hole, because **shlex.split() discards a NEWLINE as ordinary whitespace** and a newline is a command separator too. So `git add x` on one line and an unrelated `[ ! -f "$M" ]` on the NEXT tokenized into ONE argv, and the force-flag reader took the next line's `-f` as git add's own — refusing the command with a message asserting *"a -f belonging to another command on the same line is not this rule"*, about precisely the case it cannot see. This was the REPORTED SYMPTOM of the very row that scanner was written for (`rm -f f.txt && … git add f.txt`), fixed there for `&&` and left open one separator later; it cost three refusals in one session, each blocking a bats fixture from being WRITTEN — a guard against committing gitignored binaries, stopping a test file that force-adds nothing. ⇒ **when a guard splits a command into clauses, enumerate the separators against the SHELL's grammar, not against the ones your incident happened to contain.** 🚨 The obvious cure is a BYPASS: joining the lines with ` ; ` so the existing splitter handles them puts the real invocation inside a comment whenever the lexer runs with `comments=True` (`echo hi # note ; git add -f x`). Scan each line SEPARATELY. Three properties must be pinned or the cure just trades one direction of failure for the other — a newline INSIDE quotes must NOT split (it desyncs every later token and throws the scan to the over-blocking text fallback), a BACKSLASH-newline is a line CONTINUATION and must stay joined (`git add \<nl> -f x` is one force-add), and an invocation on any LATER line must still be found, since the risk of teaching a scanner about newlines is that it stops looking past the first one. Companion, and the reason this class hides: the SIBLING guard in the same file flattens the other way — the FF-GATE's clause loop is `tr ';|' '\n'` read line by line, so `read` splits on newlines too and a heredoc BODY line is its own clause carrying no `<<`. A heredoc fail-open there must therefore test `$CMD`, never the clause. Two guards, one file, opposite line-handling: read which one you are in before writing the predicate.
