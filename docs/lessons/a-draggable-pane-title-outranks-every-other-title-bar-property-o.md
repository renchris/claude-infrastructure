# A draggable pane title outranks every other title-bar property — OPERATOR RULING, do not re-litigate

_Relocated VERBATIM from `.claude/rules/agent-operating-lessons.md` (always-loaded tier) — the rules file now carries the hook and links here. Nothing was shortened._

[A draggable pane title outranks every other title-bar property — OPERATOR RULING, do not re-litigate](.) — 2026-09-16, third time this exact regression reached him: **the operator has ruled that DRAGGABILITY IS PRIMARY and everything else about a kitty pane title is secondary — "all other features come secondary to being draggable if its a technical impossibility for all/both".** The mechanism that keeps taking it away is always the same and is always re-discovered from scratch: kitty's drag machinery hangs off REAL title-bar render data (`set_window_title_bar_render_data`, `set_window_being_dragged`), and `scripts/kitty-pane-title-overlay.py` draws a *picture* of a title bar with the graphics protocol. kitty has no idea that image exists, so a plain drag on those pixels cannot move anything however good it looks — and the overlay is genuinely prettier (SF Pro Semibold, our palette, zero row shift), which is exactly why session after session re-introduces it and silently pays the drag for it. ⌘⇧B was literally wired as `kitty-pane-title-toggle.sh off : overlay.py toggle` — *turn the real bars OFF, then show the picture*. He reported the identical failure on 2026-09-14 ("ensure that command shift b still allows for dragging split panes in placement. its not working for me right now") and again on 2026-09-16 ("Dragging this split pane's very own title bar does not drag"). ⇒ **`window_title_bar_min_windows 1` (kitty's own docs: 0 = never show, 1 = always show) is the restored state and is not a trade to re-open.** Any chord, script, daemon or default that disables real bars in exchange for the overlay is FORBIDDEN; the overlay is welcome on top of a real bar or as a glance that leaves real bars alone, never as a replacement. The price is honest and pre-accepted: a real bar is allocated from the cell grid, so at `window_padding_width 0 5 0 5` it costs ONE ROW per pane — the § 7d reservoir pair can buy that row back while KEEPING the bar, which is the only direction of optimisation still open. 🚨 **Two structural reasons this specific regression kept coming back, both worth generalising: (a) the disarm lived only in a shared WORKING TREE**, which three sessions share and any checkout reverts — the config says so in its own words, *"the disarm keeps being lost because it has only ever lived in this WORKING TREE"* — so a preference that is not ON TRUNK is not a decision, it is a local edit with a half-life; and **(b) the overlay DAEMON outlives the chord state**: measured today, `kitty-pane-title-overlay.py daemon --initial=on` was running (pid 88714) with BOTH B chords disarmed on trunk and live, so auditing the bindings said "nothing is armed" while a picture was still being painted over every pane. ⇒ when a feature has both a BINDING and a RESIDENT PROCESS, check the process — a disarmed chord is not an absent feature. Stop it with `kitty-pane-title-overlay.py off --all` then `stop`.
