# A driver shell's own CPU is not its pipeline's progress

_Relocated VERBATIM from `.claude/rules/agent-operating-lessons.md` (always-loaded tier) — the rules file now carries the hook and links here. Nothing was shortened._

[A driver shell's own CPU is not its pipeline's progress](.) — 2026-09-09, diagnosing a `/ship` that looked wedged at 16 min: `ps -o time` on the top-level `bash scripts/ship-land.sh` read **0:00.76 and did not move across 20 s**, `pgrep -P <pid>` returned NO children on three separate samples, `lsof` showed only /dev/null + the output pipe + its own script fd, and the land-lock read free with 0 waiters. Every one of those is consistent with "blocked", and all of them were WRONG: 25 consecutive 1-second samples of `pgrep -P` caught `scripts/unattended-path-lint.sh` running the whole time. A shell that drives subprocesses accrues almost no CPU of its own (children's time is not in the parent's `TIME` until reaped), and a single `pgrep -P` can land between forks, so **the absence of a child in one sample is not the absence of work** — the same error as an argv census sampled once (memory: *argv is sampling, cwd is durable*). ⇒ before calling a long pipeline wedged, SAMPLE ITS CHILDREN REPEATEDLY (`for i in $(seq 1 25); do pgrep -P $pid; sleep 1; done`) and name the child you caught; parent CPU, one pgrep, and an empty output file are each individually uninformative. Second half, mechanically separate: **`cmd | tail -N` cannot emit anything until its input closes**, so a 0-byte capture file from a backgrounded `… | tail -40` is the EXPECTED state of a healthy run, not evidence of silence — if you want progress visibility from a long command, redirect to a file and read the file, never pipe through `tail`.
