# Optimistic round cannot outrun its contention

_Relocated VERBATIM from `.claude/rules/agent-operating-lessons.md` (always-loaded tier) — the rules file now carries the hook and links here. Nothing was shortened._

[Optimistic round cannot outrun its contention](.) — 2026-09-09, exhaustive-drive: a `/ship` sat **3 h 10 m** without landing and was neither wedged nor slow — it was **livelocked by construction**. `ship-land` gates OPTIMISTICALLY (unlocked), takes the land-lock, re-fetches, and on a moved trunk prints `STALE GATE`, releases and re-gates: three rounds, each ~60 min under load, each ending the same way. **The measurement that settles it is a DISTRIBUTION, not a mean, and costs one command:** trunk took **22 commits in 4 h**, mean gap **2.7 min**, max **18.1 min**, and **0 of 21 gaps were >= 60 min** — the length of one round. A retry loop whose round exceeds the *maximum* quiet window on the resource it re-reads has probability ~0 of completing **on any given round**; elapsed time cannot tell that from "busy", a `git log --format=%cI` gap histogram can. 🚨 **AMENDED 2026-09-17 — the clause "however long it runs" was FALSE OF THIS TOOL and is struck.** `ship-land` is NOT an unbounded retry loop: it self-limits at `ROUNDS="${SHIP_LAND_GATE_ROUNDS:-3}"` and, when those are spent, takes the arm commented *"rounds exhausted (sustained contention) or SHIP_LAND_GATE_ROUNDS=0: guaranteed"* — an in-lock re-gate of STATICS ONLY that makes progress unconditionally. The dice are rolled a **bounded** number of times and every land terminates; the 3 h 10 m incident is 3 rounds x ~60 min, the bound paid in full, not a loop that would have run forever. Measured by THREE independent sessions on 2026-09-17, each verifying it in its own tree rather than quoting the others, and twice observed end-to-end in a real run (`1ac179ea0`, `3beda753d`: 3 stale rounds, then the fallback firing verbatim). **The knob is re-framed, not withdrawn:** `SHIP_LAND_GATE_ROUNDS=0` SKIPS the up-to-3 rounds you would otherwise pay — a latency trade — and is NOT a rescue from an unbounded loop; trap (a) below still applies to reaching for it by hand. ⇒ **the durable lesson survives sharper: before calling a retry-until-stable loop hopeless, read its ROUND BOUND and its exhaustion arm — a gap histogram settles PER-ROUND odds and says nothing about termination unless the loop is genuinely unbounded.** ⇒ **when a retry-until-stable loop has run for multiples of its own round, do not ask "is it stuck?" — ask "is there a gap in the contention long enough for a round to fit?"** If no, waiting is not a strategy: stop re-proving under contention (`SHIP_LAND_GATE_ROUNDS=0` + a raised `LAND_LOCK_WAIT` skips the optimistic round and re-gates STATICS ONLY in the lock — it turned the 3 h livelock into a 27 min queue wait that landed). Generalizes to CAS loops, optimistic-concurrency retries, rebase-then-push loops — any "validate unlocked, commit locked" design. Two traps measured with it: (a) **a documented escape hatch can carry a documented hazard** — these knobs are plain env vars that bats subprocesses INHERIT and `tests/ship-land.bats` asserts the very behaviour they change (46/46 -> 45/1 -> 7 failures, "a verdict about the tree manufactured out of a fact about the operator's flags"); the scrub `env -u SHIP_LAND_GATE_ROUNDS -u SHIP_LAND_VERIFY_RETRIES …` (cited here as `:1995` when written; measured at **`:2190`** on 2026-09-17, where `:1995` is now an unrelated GATE_HOME_ISO line — grep the expression, never the number: this entry rotted its own pointer in eight days, the very class it warns about) `env -u`s both, so READ the scrub rather than assume, in either direction — **and read it in the copy you will actually EXECUTE**, because `ship-land.sh` is a PER-WORKTREE file and the scrub is therefore a per-worktree rail: a sibling worktree cut before that fix landed still carries the trap (672, 2026-09-09, reproducing this remedy on a second branch — [Rail fix is per-worktree] intersecting this rule; the difference between reading a fix and running one). (b) **A cherry-pick made to clear a patch-id-keyed divergence CANNOT clear it** — `deploy-live` decides "present by content" by patch-id, so re-landing a stranded commit's TEXT at a different context leaves the check still reading DIVERGED (verified: the routed line was on `origin/main` at line 62 while `git cherry` still marked its source `+`). That is the ACTING corollary of [Ref may be pre-fix]/[cherry + is not absence]: those say a `+` does not prove absence; this says **you cannot make a `+` go away by re-landing the content** — only the tool's own `DIVERGED but ALREADY LANDED` arm (`git reset --keep origin/main`) clears it, and that needs EVERY divergent commit to match, so one genuinely-unlanded sibling pins the whole converge.
