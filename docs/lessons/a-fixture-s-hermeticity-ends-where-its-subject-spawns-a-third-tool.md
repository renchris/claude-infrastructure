2026-09-17, cc-backlog `b2135387fd55` (landed b33d3b5ac + 1260708b3): a test suite can be audited for `$HOME`, for every seam its SUBJECT reads, and for the one collaborator anybody thought about, and still reach the operator's live machine — because the subject END-TO-END SPAWNS A THIRD PROGRAM, and that child resolves its OWN paths from ITS OWN environment, under names the suite never heard of. `tests/ship-land.bats` pinned `POSTLAND_DIR` (ship-land.sh's spelling) and `POSTLAND_VERIFY=off`, and every green fixture land still fired a detached `deploy-live` at `${DEPLOY_REPO:-$HOME/Development/claude-infrastructure}` — the operator's SHARED CHECKOUT — carrying `env=dict(os.environ, ...)`, with `CC_POSTLAND_DIR` and `CC_PAGES_DIR` (deploy-live's spellings) UNSET. Measured with a recording stub where that script stands: the single case *"green: land end-to-end"* spawns one, `CLAUDE_CODE_SESSION_ID=test-sid-123`. It advanced the live layer, ran post-deploy host_checks against the real tree concurrently with the corpus that was its load, and filed a real `post-deploy HOST RED` naming three host suites into the backlog — **filedBy `test-sid-123`, the only row in 21.5k carrying it, and all three suites GREEN when re-run (2/2, 16/16, 82/82)**. A TEST minted a false finding about the live layer, and no `host RED` line exists in `deploy.log` because the kick logs to the one variable the fixture DID pin, so only the stores the CHILD resolved were real. ⇒ **when auditing a fixture, do not stop at what the subject READS — ask what it EXECUTES, and then audit that program's seams under ITS names.** A seam bound under a name the subject does not read looks exactly like a closed leak ([[lookup-miss-is-not-absence]]), and here the suite's one correct pin is what made the leak invisible in the log. 🚨 **The repo had already written the warning and filed it in the wrong place**: `tests/ship-land-converge-edge.bats` (which OWNS that kick) says in its own setup() that *"an unfixtured run … would point the guard at the OPERATOR'S REAL SHARED CHECKOUT and, on the clean branch, fire a real deploy-live from a test"* — true of `ship-land.bats` the entire time, in a comment only the suite that was already safe would ever load. A hazard note belongs in the RATCHET, not in the one file that has already handled it (now rule 9 of `scripts/test-hermeticity-lint.sh`). Two companions, each separable: **(a) the suite is GREEN in both arms** — pre-fix 173/173 while spawning, post-fix 173/173 while not — so the leak is invisible to the suite's own verdict and no amount of re-running finds it; the only instrument that can is a RECORDING STUB standing where the real tool stands, which is the same two-sided design rule 8 used for the dispatcher. **(b) The false row arrived UNFALSIFIABLE, and for a reason worth recognising**: the child began from the shared checkout's PRE-ADVANCE bytes — the deploy it was performing is what made the fix live — so it ran a `fals_host_set` that predated multi-suite probes (`2c808efc0`, landed 19 minutes earlier) and emitted no falsifier at all. **A self-modifying converger runs the version it is replacing**, so the first artifact produced by a deploy is evidence about the OLD code, never the new.
