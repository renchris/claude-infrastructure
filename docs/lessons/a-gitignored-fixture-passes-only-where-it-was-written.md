# A gitignored fixture passes only where it was written

**Rule.** A test fixture whose filename matches a `.gitignore` pattern is never committed, yet every test that reads it passes in the worktree that created it, because the file is sitting there untracked. The author's own suite run and the author's own land gate both run in that worktree, so neither can see the gap; the tests fail on trunk and in every other checkout with `No such file or directory`. Before committing a new test, run `git check-ignore -v` on every fixture path it reads (or `git status --short --ignored tests/fixtures/`), and name fixtures with an extension the ignore file does not match. Never `git add -f` around it; rename instead.

**Incident, 2026-10-17.** The move-lane fix session (pane 253) landed `475d66ced` with two replay tests reading `tests/fixtures/move-lane-2026-10-17/pane7/recycle-watcher.log`. `.gitignore:11` is `*.log`, so the fixture never reached the commit; the session reported its suites green (they were, in its worktree) and its land gate passed. The lead's verification run from the shared checkout, against the landed sha, failed both tests with `grep: …/recycle-watcher.log: No such file or directory`. Cure `24cea9e28`: the byte-identical file renamed to `recycle-watcher.txt` and both tests pointed at it (1..23, 0 not ok).

**Why the collector, not the author, catches it.** Verification of a dispatched session's work must run in a checkout that contains only what was committed: the shared checkout after the converge, or a fresh worktree at the landed sha. A re-run inside the author's worktree inherits the same untracked bytes and repeats the false green.
