[A digit-guard destroys the value it is hardening](.) — 2026-09-11, cc-backlog `c44949c9ed9e` (landed 8c26adebf): **`wc -l` PADS to width 8 on BSD, and the idiom that looks like it is SANITIZING that value is what silently zeroes it.** `n="$(grep -o -F X f | wc -l)"` yields `"       1"`; the very next line, `case "${n:-0}" in ''|*[!0-9]*) n=0 ;; esac`, reads those leading spaces as non-digits and normalizes a real count to **0**. The polarity is what makes it expensive: a guard written to reject garbage converts a TRUE count into the FALSE one, so the failure is a confident wrong answer rather than an error. In `propose-goal-flag-watch.sh` it inverted `--binary` from rc 0 ("`ProposeGoal` present but minified past the gate pattern — read it by hand") to rc 3 ("absent from a verified build — the feature is gone upstream"): opposite verdicts, from a formatting artifact, in the direction that mints a confident RETRACTION signal for a row nobody re-checks. ⇒ **the trap's boundary is exact, and it is why this survives review: `[ "$v" -gt 0 ]` ACCEPTS the padding (bash strips whitespace in arithmetic context) while a `case` digit-guard does not** — so the same padded value is safe at every numeric-comparison site and fatal at the one place someone tried to be careful. Measured both, one variable: `[ -gt ]` accepts, `case` zeroes. `| tr -d ' '` is this repo's idiom (85 sites); the guard is correct and stays, it just needs a value it can read.
