# The blocking gate was stricter than the repo's own verifier

[The blocking gate was stricter than the repo's own verifier](.) — 2026-09-10, cc-backlog `19ca2b91425c` (landed a2b2e262d): **when two tools in one repo judge the SAME population, the one that BLOCKS is not automatically the one whose standard is right — and a filing that names LOAD as the cause will not lead you to that comparison.** ship-land's DIRECT flake carve-out convicted on **1-of-2** — run 1 names a failure, the exoneration re-run is GREEN, and it calls that "intermittence in code you are landing" — i.e. it convicts on n=1 where the only re-observation CONTRADICTED it. `scripts/postland-verify.sh:24-25`, judging the same corpus on the same box, has always used *">=2/3 fails = REPRODUCIBLE, 1/3 = flake"*, with **179 `1-of-3` rows** in the shared ledger. The land gate was the strictest tool on the least evidence, and the only one that blocks. ⇒ **before tuning a gate's constants, grep the repo for a sibling that already adjudicates the same signal and read its rule** — aligning to an already-accepted in-house standard invents no policy and needs no argument about thresholds. Four separable companions: **(a) the filing's framing was a CORRELATE, not the mechanism.** It reported "the flaking IDENTITY ROTATES … the load correlation is the signal" and proposed sizing timing constants from load. Both true and neither actionable: the mechanism is that `run_smoke` passes its own list as the direct set and, with no `EXTRA_RANGE`, `own=direct` — so EVERY selected suite is convictable, and at the file's OWN stated `q=2.94%/suite` MLE the refusal probability is `1-(1-q(1-q))^N` = 54% at N=27, **70% at N=42**. A rotating identity is arithmetic over the DRAW; the constants that explain it were already written in the file, one screen above the defect. **(b) An alarm that returns before its own logging is unevaluable.** The carve-out did `return 1` ahead of the `printf` to `flakes.jsonl`, so every EXONERATION was recorded and every CONVICTION was invisible — you cannot compute the fence's precision from a ledger that only holds its acquittals. Log the firing, not just the release. **(c) A fixture keyed on `$1` cannot see an argument the fix ADDS.** The confirming run invokes `bats -f <regex> <suite>`, so two fixtures matching the suite against `$1` read `-f`, found no mode, and answered GREEN — holding the axis under test constant (same family as *fixture-identifier-shape-collapses-two-spaces*). Key on the LAST argument, or iterate `"$@"` as a third fixture in the same tree already did. **(d) `grep -c` PRINTS a valid `0` AND EXITS 1 on no-match**, so `"$(grep -c X f 2>/dev/null || echo 0)"` puts a SECOND producer on one stream and the test sees `"0\n0"` → `[: 0 0: integer expected`. This is not the `||`-swallows-a-failure class — it is the opposite: a fallback chained onto a command that had *already answered*. Capture once and default the VARIABLE (`n="$(grep -c … )" || true; [ "${n:-0}" -eq 0 ]`), never append a fallback to a stream that may already carry the answer.
