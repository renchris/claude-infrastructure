# Bun-GC A/B — raw measurements, 2026-08-18

Axis: **live A/B, pre-fix vs post-fix binary.** Question: does the 2.1.229 Bun-GC change reduce the
quantity `capacity_gate()` actually keys on — LOAD AVERAGE / runnable-thread count — or only CPU%,
which the gate does not measure?

Box: MacBookPro18,2 (M1 Max), 10 cores (8P+2E), 64 GiB, macOS 15.6.1. Measured 2026-08-18 00:07–01:10.
Scratch artifacts under `/tmp/gcab/`, `/tmp/cc228probe`, `/tmp/cc234probe`. Nothing outside `/tmp` was
written except this file. No live session was signalled, restarted, or otherwise disturbed;
`~/.claude-versions/MANIFEST.jsonl`, `~/.claude-220`, and every launcher/config are untouched.

---

## 0. Instrument validation (a control that could fail, and one that did)

**Runnable-thread instrument.** `ps -M` per pid; a thread row is `PID %CPU STAT PRI STIME UTIME`, a
process row is `USER PID TT %CPU STAT PRI STIME UTIME COMMAND`. `STAT` starting `R` = runnable.

*Positive control:* four `while :; do :; done` busy loops were spawned and `ps -M` reported `STAT=R`
with `%CPU` 92–96 for each. The instrument can therefore report `R`; a reading of 0 is a measurement,
not a blind spot.

*Binary-discrimination control (mandated):* `claude doctor` on each probe prints
`Running: npm-global (2.1.228)` and `Running: npm-global (2.1.234)` respectively. The harness
demonstrably distinguishes the two arms, so a null would have been a null and not a plumbing failure.

*A control that DID fail and was fixed:* the first A/B harness (`/tmp/gcab/ab.sh`) reported all-zero
CPU and `meanRunnable=0.0000`. Two bugs: `/usr/bin/time`'s own stderr was being discarded by an inner
`2>/dev/null`, and the sampler tracked the `time` wrapper (1 thread) rather than its `claude.exe`
grandchild. Rewritten as `/tmp/gcab/ab2.sh` with an `exec` runner so `claude.exe` is `time`'s direct
child. **The all-zero result is retained here as evidence that the harness could produce a false
null.**

*Instrument self-load, disclosed:* the samplers fork `ps` at 1–20 Hz. In the whole-box attribution
below, `ps` (27 runnable-thread hits / 25 samples) and `top` (10) are MY OWN instrument, i.e. roughly
**1.5 of the ~19.3 box runnable threads (~8%) is the measurement apparatus**. It is constant across
A/B arms and therefore cancels in every 228-vs-234 comparison; it does NOT cancel in the absolute
box-load figures, which are correspondingly ~8% overstated.

## 1. What the binaries actually are (checked, not assumed)

All three are **Bun-compiled single-file Mach-O arm64 executables** (`bin/claude.exe`), so the Bun GC
path is genuinely in our execution path — this was verified rather than inferred from the tweet.

| install | version | embedded Bun | sha256 (first 16) | size |
|---|---|---|---|---|
| `/Users/chrisren/.claude-220` (LIVE) | 2.1.220 | `bun-v1.4.0` | `8addc857f3fe64d5` | 245 M |
| `/tmp/cc228probe` | 2.1.228 | `bun-v1.4.0` | `43484b1352cef03a` | 289 M |
| `/tmp/cc234probe` | 2.1.234 | `bun-v1.4.0` | `08d8700313697cbe` | 305 M |

**All three report the same nominal Bun version, `1.4.0` — so the GC change is NOT a Bun version bump.**
The difference is visible in the embedded runtime's env-var table:

```
exact-string match count in claude.exe
                              2.1.220   2.1.228   2.1.234
BUN_GC_TIMER_DISABLE                0         0         1
BUN_GC_TIMER_INTERVAL               0         0         1
```

`BUN_GC_TIMER_DISABLE` and `BUN_GC_TIMER_INTERVAL` exist **only in 2.1.234**. `2.1.234` additionally
carries `_API_EXPERIMENTAL_NOGC_ENV_OPT_OUT` and a packed literal blob containing
`BUN_GC_RUNS_UNTIL_SKIP_REL` (present only inside a concatenated string, not as a standalone token —
reported at lower confidence than the two exact matches).

This is **direct binary evidence for the vendor's account** (a fixed-timer GC, now gated) and direct
evidence that **we do not have it**: our live 2.1.220 has neither knob. It also means the knobs cannot
be used as a mitigation on 2.1.220 — they do not exist in that binary.

## 2. THE CRUX — does GC work become RUNNABLE THREADS at all?

The gate keys on load average, which on Darwin counts runnable threads only. A CPU% win moves the gate
only if GC contributes *runnable threads*. Measured directly, API-free, on the standalone
`~/.bun/bin/bun` **1.3.0** (arbitrary JS cannot be run on `claude.exe`; this is therefore a claim about
the JSC/Bun threading model, explicitly not about the shipped 1.4.0 build).

Two arms, equal wall time (15 s), interleaved A/B/A/B/A/B, sampled at ~200 Hz:

- **`alloc`** — allocates 2000 objects per iteration in a tight loop ⇒ continuous GC pressure.
- **`compute`** — pure integer LCG arithmetic, near-zero allocation ⇒ same CPU, minimal GC.

| arm | rep | samples | mean threads | **mean RUNNABLE** | max R |
|---|---|---|---|---|---|
| alloc | 1 | 2916 | 6.3 | **1.148** | 4 |
| compute | 1 | 3059 | 4.9 | **1.000** | 1 |
| alloc | 2 | 3065 | 6.3 | **1.176** | 4 |
| compute | 2 | 3366 | 5.0 | **1.000** | 1 |
| alloc | 3 | 3050 | 6.3 | **1.151** | 5 |
| compute | 3 | 3480 | 5.0 | **1.000** | 1 |

**Result.** A fully CPU-saturated JS process contributes **exactly 1.000 runnable threads** (max 1,
across ~9,900 samples) — one unit of load, the JS main thread, and nothing more. GC pressure adds
**+0.158 runnable threads** (1.158 vs 1.000) and 1.4 extra resident threads: JSC's parallel-marking
helpers, which do briefly go runnable (max 4–5).

So the answer to the crux is a qualified yes with a hard magnitude bound:

> **GC does produce runnable threads, but a process doing nothing but allocating as fast as it
> possibly can attributes only ~0.16 runnable threads to GC — a ceiling of ~13.6% of that process's
> own load contribution.** A real session, which spends most of its life waiting on the network, is
> far below that ceiling.

The `compute` arm is the control that could have failed: had it shown >1 runnable thread, the
single-threaded-main-thread premise would have been refuted. It did not, in any of ~9,900 samples.

## 3. THE A/B — 2.1.228 vs 2.1.234, identical workloads

Auth is unavailable for a scratch config dir (see §6 NULL-1), so both workloads are **API-free and
purely local**, run from a scratch `CLAUDE_CONFIG_DIR=/tmp/gcab/cfgB` and scratch cwd `/tmp/gcab/work`
(no `.claude/` ⇒ **no hooks load at all**):

- **`doctor`** — `claude doctor`: full Bun runtime init, JS bundle eval, settings scan. ~0.85 s.
- **`bigstdin`** — `claude -p --model claude-sonnet-4-5 < big9.txt` with an 8,808,000-byte stdin
  (just under the 10 MB cap). The binary ingests and processes all 8.8 MB locally, then exits on
  `Not logged in`. Allocation-heavy, deterministic, zero API spend. ~1.0 s.

Order was interleaved **228 / 234 / 234 / 228** within each rep to cancel drift on a box whose load
moved between 19 and 26 during the session. 15 reps × 2 orderings = **n = 30 runs per cell.**

**Honest reading.** The CPU-seconds win is solid and reproducible at **8–11%**. The runnable-thread
win is **directionally consistent in 4 of 4 cells** but its magnitude is only **0.04–0.09 runnable

lies between the two tests; take **−0.04 to −0.09 runnable threads per working process** as the
generous upper estimate.

Note also that **8–11% is not "2× less CPU."** The vendor figure is p99 CPU share *across all sessions
in their fleet* — the worst session, not aggregate load, and not this workload.

## 5. Headroom arithmetic — what the fix buys under the load-20 gate

`capacity_gate()` (`scripts/handoff-fire.sh:4376`) refuses above `CC_FIRE_MAX_LOAD_PER_CORE`=2.0
× 10 cores = **load 20**.

Session-attributable load = `claude.exe` (0.950) + cc-tooling (6.000) = **6.95 for 16 sessions
= 0.434 load/session**. Non-session-attributable = OS daemons (3.025) + category-4 residue
(9.300) ≈ 12.33.

*Self-consistency check:* this model predicts a wall at (20 − 12.33) / 0.434 = **17.7 sessions**,
which matches the observed felt wall of ~15–16 and the ground-truth "we sit at 19.06 with 14
sessions". The model reproduces the phenomenon, so it is the one to reason with.

Applying the most generous measured runnable-thread win (−10.4%) to the `claude.exe` term only —
6.95 → 6.85, per-session 0.434 → 0.428:

> **(20 − 12.33) / 0.428 = 17.9 sessions. Gain: +0.2 sessions.**

The optimistic alternative model — count only `claude.exe` + direct descendants (0.171/session),
ignoring detached tooling — yields +2.8 sessions, **but it predicts a 45-session wall that we do not
observe**, so it is refuted by the very measurement it would be quoted from.

**Range: +0.2 sessions (self-consistent model) to +2.8 sessions (model refuted by the observed wall).**

## 6. What could NOT be measured — stated as nulls, not guesses

- **NULL-1 — no active-turn A/B.** The A/B never exercised a real API turn. A scratch
  `CLAUDE_CONFIG_DIR` returns `Not logged in · Please run /login`; no `ANTHROPIC_API_KEY` exists in the
  environment or in any launcher (`env | grep -c ANTHROPIC_API_KEY` → 0); `--bare` requires
  `ANTHROPIC_API_KEY` or `apiKeyHelper` explicitly. Investigating the credential store was **denied by
  the auto-mode classifier**, and that denial was respected rather than routed around. Borrowing a live
  per-account config dir was rejected on its own merits: those dirs carry `settings.json` hooks that
  would have fired `cc-dispatch` / backlog writes / `deploy-live` against the live fleet, violating the
  brief's hard constraint. **Consequence: the 228-vs-234 deltas in §3 are for local work only
  (startup, 8.8 MB ingest). Mid-turn streaming-token GC — precisely the phase the vendor names — was
  not sampled on either binary.** Quota spent: **$0.00, zero API turns.**
- **NULL-2 — no genuinely ACTIVE live session was captured.** Across 65 s at 4 Hz over 16 sessions,
  the busiest reached mean 0.158 runnable threads. Either no session was mid-turn in that window, or
  the prior "2.5–5 runnable threads per active session" figure
  (`scaling-bottlenecks-2026-08-09.md`, Wall 2) counts the session's *subprocesses*, not `claude.exe`.
  §4b favours the latter (descendants are 64% of subtree load), and §2 bounds `claude.exe` itself at
  ~1.16 runnable threads *even when CPU-saturated* — so 2.5–5 is unreachable by the binary alone. This
  is a **strong inference, not a direct measurement**, and it is not settled here.
- **NULL-3 — `powermetrics` never run.** It requires sudo; per the brief no password prompt was
  issued. Per-thread wakeup counts and E-core/P-core residency are therefore unmeasured.
- **NULL-4 — the GC mechanism probe (§2) ran on standalone bun 1.3.0, not the embedded 1.4.0.**
  `claude.exe` cannot execute arbitrary JS. The +0.158 figure is a claim about the JSC threading model,
  and the shipped 1.4.0 could differ in magnitude (not, plausibly, in kind).
- **NULL-5 — `BUN_GC_TIMER_DISABLE` / `BUN_GC_TIMER_INTERVAL` were never exercised.** Their presence
  in 2.1.234 is a string-table fact only; no run toggled them, so their runtime effect is unmeasured.
  They are absent from 2.1.220, so they are not available as a mitigation on the live binary.
- **NULL-6 — absolute box-load figures carry ~8% instrument self-load** (§0). A/B deltas are unaffected.

## 7. An accidental demonstration of the whole thesis

Load average at session start (17 sessions, ground truth): **19.06**.
Load average at session end (17 sessions, unchanged): **36.07**.

The delta is **my own instrumentation** — `ps -M` / `ps -axM` / `vmmap` poll loops and the two probe
binaries. A handful of shell fork loops moved the box's load average by ~17 units, while **seventeen
`claude.exe` sessions together contribute 0.95**.

That is the finding in one line: on this box the load average — the quantity the fire gate refuses
on — is a measure of *fork and shell activity*, not of how many Claude sessions are resident. Halving
`claude.exe`'s CPU cannot move a number that `claude.exe` barely participates in.

*(Constraint check at close: `~/.claude-versions/MANIFEST.jsonl` mtime Aug 12 18:03, `~/.claude-220`
mtime Aug 1 12:15 — both untouched. Live session count 17, none lost.)*
