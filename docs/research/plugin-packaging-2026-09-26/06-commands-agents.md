# 06 — Commands and agents: which can ship in a public plugin

Scope: 25 files in `commands/` and 5 in `agents/` of `/Users/chrisren/Development/claude-infrastructure` (read-only; nothing in the repo was modified).
Tiers: **T1** ship as-is · **T2** ship after decoupling · **T3** fleet/personal only · **T4** cannot ship.

## Answer first

- **Split: 5 T1, 10 T2, 8 T3, 2 T4 commands. Agents: 1 T1, 3 T2, 1 T3.** The generic dev commands (review, fix-lint, deploy-check, scaffold) are generic because they are thin. Each is 14–30 lines of checklist, and each is worth 1–2 to a stranger. The commands worth the most to a stranger are `ship`, `read-twitter`, `commit` and `pr`, and each needs targeted edits first.
- **Every agent frontmatter field in use is plugin-legal.** The fields are `name`, `description`, `model`, `maxTurns`, `tools` and `omitClaudeMd`. None of them is on the ignored list (`permissionMode`, `hooks`, `mcpServers`, `initialPrompt`). Source: https://code.claude.com/docs/en/plugins/components § "Frontmatter fields in plugin agents".
  - `omitClaudeMd` needs Claude Code v2.1.271 or later (https://code.claude.com/docs/en/sub-agents, field table).
  - One agent has a latent YAML defect. It passes the 2.1.280 validator but fails 2.1.114 (see Agents table, critic row).
- **Measured:** I copied all 25 commands and 5 agents into a temp plugin and ran `claude plugin validate --strict` on 2.1.280 (`~/.claude-280/node_modules/.bin/claude`). Result: `Validation passed`, with 0 errors and 0 warnings. A deliberately broken control agent did fail, so the validator does check agents.
- **Repo-wide blocker, above every tier:** the repo has no `LICENSE` (`ls LICENSE*` finds nothing). As published, strangers have no reuse rights to any unit, T1 included. The manifest takes an SPDX `license` field (https://code.claude.com/docs/en/plugins-reference, Fields table), but the repo still has to choose a license first.

## Plugin mechanics that decide the tiers (docs)

| Fact | Consequence here | Source |
|---|---|---|
| `${CLAUDE_PLUGIN_ROOT}` / `${CLAUDE_PLUGIN_DATA}` are substituted inline in skill, command and agent Markdown and in `allowed-tools` Bash rules. They are **not** set in the environment of Claude's Bash tool. | Every `~/.claude/scripts/…` and `~/.claude/bin/…` path must be rewritten as `${CLAUDE_PLUGIN_ROOT}/…` in the Markdown body. | plugins-reference § Environment variables; https://code.claude.com/docs/en/skills § string substitutions |
| Plugin `bin/` is on the Bash tool's PATH, after the user's own PATH. `!` injections "run through the Bash tool". | A shipped `bin/cc-read-twitter` or `bin/cc-lid` resolves as a bare name. This is an inference joining two doc sections; `${CLAUDE_PLUGIN_ROOT}/bin/x` is the safe form. | plugins/components § Executables; skills § "How injected commands run" |
| claude.ai and Cowork **do not install** a plugin with a top-level `bin/`. | Shipping `bin/` restricts the plugin to Claude Code CLI/desktop. | plugins/components § Executables |
| An injected `!` command that exits non-zero **aborts the whole invocation**, so Claude never sees the body. Exit 1 is exempt only for search/compare commands. | Two live bugs (see Adversarial findings). | skills § "When an injected command fails" |
| Command files accept the same frontmatter as skills except `name` and `paths`. | The `name:` field in 12 commands is ignored. It is harmless because every one matches its filename. | skills § frontmatter reference |
| Plugin units are namespaced `/plugin:cmd` and `plugin:agent`. A plugin command never takes a bundled alias; `/review` stays the bundled `/code-review`. | Names don't collide. Every in-body reference to a bare agent name (`deep-research`) must become `plugin:deep-research`. | skills § "Resolve skills that share a name"; plugins/components § Agents |
| Default subagent nesting depth is **3**. | The Permission-to-Recurse section of `deep-research` (lines 112–171) describes the operator's own `~/.zshrc:484` cap. For a stranger it is false. | https://code.claude.com/docs/en/sub-agents § nesting |

## Command/skill duplicates, and legacy status

- **Same-named pairs:** `read-twitter` and `resume-sessions`. Each exists both in `commands/` and in `skills/` of the repo, and both are deployed to `~/.claude/skills/<name>` and `~/.claude/commands/<name>.md` (checked by path).
- **No `handoff` skill exists.** `skills/handoff` is absent and nothing under `~/.claude/skills` matches `handoff`. It only appears in the session's skill list because Claude Code now lists commands alongside skills. Other near-pairs share a function under different names: `relogin`/`account-relogin`, `research`/`research-subagents`, `accounts` (command only).
- **Locally, the skill wins and the command file is dead code.** The docs say that for "A skill and a file in `.claude/commands/`", "The skill" runs (https://code.claude.com/docs/en/skills § Resolve skills that share a name). Observed: this session's skill list shows the SKILL.md descriptions for both names, not the command descriptions. So:
  - `/read-twitter`'s injected `!cc-read-twitter` pre-run (read-twitter.md:11) never executes. Claude runs the tool itself, following the skill.
  - `commands/resume-sessions.md:10-12` says it exists because the skill "advertised a `/resume-sessions` trigger that had no command file". That premise is obsolete, because skills are slash-invocable.
  - Both command files can be deleted without losing behaviour.
- **Commands are the legacy format.**
  - "**Custom commands have been merged into skills.** … Your existing `.claude/commands/` files keep working" (skills doc, top).
  - "Commands are the older format, and skills supersede them for new work… Keep `commands/` for files you're moving over" (https://code.claude.com/docs/en/plugins/components § Commands).
  - "Prefer `skills/` for new plugins" (plugins-reference § Standard layout).
  - For a new public plugin, convert shipped units to `skills/<name>/SKILL.md`. That also gives each unit a directory for its helper script, referenced as `${CLAUDE_SKILL_DIR}`, instead of a shared `bin/`, which keeps claude.ai/Cowork installability open.

## Adversarial findings (checked with tool calls)

1. **copy-plan's error branch cannot run.** find-plan.sh exits **1** on a miss (find-plan.sh:33). The docs say any non-zero exit from a non-search command aborts the invocation and "Claude never sees the skill content". So copy-plan.md:10 ("If the content starts with 'Plan not found:'… surface that error") never fires. Fix: `|| true`. This affects the operator today, not only a plugin.
2. **The same applies to read-twitter.** cc-read-twitter returns **3** when every source declines (`return 3` in `main()`, near cc-read-twitter:527). Step 3 of read-twitter.md (:21-22, "relay the reported statuses") never runs; the operator is currently spared only because the skill shadows the command.
3. **Bundled name collision:** the built-in `/deep-research` **workflow** exists (commands ref). Shipping `/plugin:research` plus the agent `plugin:deep-research` competes with it for the same user intent. The value case has to rest on the drift-refusal and adversarial discipline, not on fan-out.
4. **deep-research's brief-drift refusal is operator policy.** It refuses legal, BD or competitive research unless the lead echoes a user quote (deep-research.md:28-83). A stranger asking a legitimate legal question gets `BRIEF_DRIFT_DETECTED`. Make it opt-in, or state it in the plugin README.
5. **Runtime floor:** `omitClaudeMd` needs v2.1.271, and the plugin manifest has no minimum-Claude-Code-version field (plugins-reference Fields table has `version` and `dependencies` only). On older binaries the field is presumably ignored and CLAUDE.md loads; that is an inference, not tested.

## Alternatives ruled out

- **Ship the fleet commands behind `userConfig` options.** Ruled out: the closure is 20k+ lines (handoff-fire 13,747, claude-accounts 6,425, wrap-ledger 2,587) that assume iTerm2 or kitty, 4 accounts and `~/.claude/autonomy` stores. Configuration cannot remove those assumptions.
- **Ship everything in `bin/`.** Ruled out: it forfeits claude.ai/Cowork installs (plugins/components § Executables), and bare-name `!` resolution through plugin `bin/` is inferred, not documented.
