# C5-macos-dataless-semantics — verdict: partially_confirmed

Host: macOS 15.7.9 (24G830). `man 3 setiopolicy_np` dated "macOS 15.7 / February 11, 2019".
Kernel source: apple-oss-distributions/xnu @ tag `xnu-11215.1.10` (pinned raw URLs).
Userland source: apple-oss-distributions/file_cmds @ `main` (`ls/ls.c`, `ls/print.c`).
OneDrive FileProvider extension present (`com.microsoft.OneDrive.FileProvider 26.158.0816`) but
`~/Library/CloudStorage` is EMPTY — no dataless file existed on this Mac, so (a)/(b) could not be
measured locally, only sourced.

## (a) SF_DATALESS + stat without download — CONFIRMED
`MacOSX.sdk/usr/include/sys/stat.h:359`: `#define SF_DATALESS 0x40000000 /* file is dataless object */`,
inside `SF_SYNTHETIC 0xc0000000 /* mask of system read-only synthetic flags */` (:337).
`file_cmds ls/ls.c:96`: `#define IS_DATALESS(sp) (f_dataless && (sp) && ((sp)->st_flags & SF_DATALESS))`
— i.e. Apple reads the bit out of `lstat`'s `st_flags`. `man ls`: "-%  Distinguish dataless files and
directories with a '%' character in long (-l) output, and don't materialize dataless directories when
listing them." Apple File Provider docs (fetchContents): "the enumeration only provides the item's
metadata. When the user accesses the item, the system needs to download the full contents".

## (b) read ⇒ blocking materialization — CONFIRMED
`bsd/vfs/vfs_syscalls.c:11345`: "When I/O is performed to a dataless file or directory (read, write,
lookup-in, etc.), the file system performs an upcall to the namespace resolver (filecoordinationd) to
materialize the object." :11375 "The caller now waits for the request to complete. Tnis is achieved by
sleeping on the address of the request structure … This is an interruptible sleep call; if interrupted
… EINTR is returned to the caller." Note stat/lstat is NOT in the faulting-operation list.

## (c) EDEADLK — CONFIRMED, scope corrected
`vfs_context_dataless_materialization_is_prevented()` (vfs_syscalls.c:11990-12044) returns EDEADLK in
three cases: kernel context ("Kernel context ==> return EDEADLK"), a thread with
`UT_NSPACE_NODATALESSFAULTS`, and the fallback "The default behavior is to not materialize dataless
files; return to the caller that deadlock was detected." So EDEADLK is the *defined* outcome whenever
materialization is prevented for the requesting context — not an anomalous alternative. Issue
anthropics/claude-code#40783 ("File read failure on macOS FileProvider-backed paths", CLOSED/stale)
reports exactly this: `ls`/`stat` fine, "Blocks: 0", every read path → "errno 35, Resource deadlock
avoided". Its environment is Cowork's **Ubuntu 22 VM sandbox** reading a macOS FileProvider path over
`fuse.bindfs` — Google Drive primarily, OneDrive only listed as an also-affected provider.

## (d) setiopolicy_np OFF + inheritance — CONFIRMED (sharpened)
Reads do not merely "fail": they fail with **EDEADLK**, per the code above. Inheritance is real and is
at fork: `bsd/kern/kern_fork.c:1046` `child_proc->p_vfs_iopolicy = (parent_proc->p_vfs_iopolicy &
P_VFS_IOPOLICY_INHERITED_MASK);` with `P_VFS_IOPOLICY_MATERIALIZE_DATALESS_FILES` (0x0004) in that mask
(`proc_internal.h:590,604`); exec preserves it. A THREAD-scope OFF outranks even the
dataless-manipulation entitlement (comment at vfs_syscalls.c:12020).

## (e) the "contradiction" — REFUTED
The man sentence ("For IOPOL_SCOPE_PROCESS, all accesses will follow the system default policy
(IOPOL_MATERIALIZE_DATALESS_FILES_OFF)") describes what *passing DEFAULT* does:
`set_proc_materialize_policy()` (kern_resource.c:2285-2300) maps DEFAULT→OFF and CLEARS the bit. It is
not the policy a running process has. Measured on this Mac (compiled probe in the scratchpad):
`getiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, IOPOL_SCOPE_PROCESS)` = **2 = ON**
(thread = 0 = DEFAULT/inherit). Corroborated structurally: Apple's `ls` must OPT OUT —
`ls.c:706-711` sets `sysctlbyname("vfs.nspace.prevent_materialization", …, state=1)` under `-%` — and
`launchd.plist(5)` exposes `MaterializeDatalessFiles` per job ("If this key is not set, the default
system policy … will be used"), with `MaterializeDatalessFiles` present in `/sbin/launchd`. So a plain
`cat` of a dataless file MATERIALIZES (blocking download); EDEADLK requires an explicit opt-out,
the kernel context, or a sandbox/daemon that did not inherit the bit.
