# C4-sharepoint-rewrites-bytes — adversarial verification

**Verdict: partially_confirmed.** Both halves are documented behaviour and the citations are accurate.
Two parts fail: the OneDrive-for-Business carve-out is a reporter assertion, not a vendor guarantee
(and (b) is itself an ODB behaviour), and the upload-path framing misses a second, independent class —
a **serving-path** divergence where the server's own reported size/hash disagree with the bytes it
returns.

## (a) SharePoint libraries rewrite uploaded rich files — CONFIRMED, vendor-acknowledged

rclone `docs/content/onedrive.md` @ v1.71.0 L1101-1104:
> "It is a known issue that Sharepoint (not OneDrive or OneDrive for Business) silently modifies
> uploaded files, mainly Office files (.docx, .xlsx, etc.), causing file size and hash checks to fail."

Microsoft, onedrive-api-docs #935, JeremyKelley (440079639):
> "After doing a little research this is normal behavior for SharePoint and has been since at least
> SharePoint 2010. When uploading a file that can contain metadata SharePoint will associate some
> metadata from the library the file is uploaded to directly in the file. … Since basic text files
> don't have in-file metadata they don't see this behavior."

chackman (441741631): "This is a feature in SharePoint document libraries that has been around for
some time." Closing (448450261): "this is how the document library features work."
Mechanism (435172239): local 20,143 B → downloaded 26,194 B, `docProps/custom.xml` + a `customXml/`
folder injected into the OPC zip. Purview doc corroborates the route — files "that have a Document ID
added when they're uploaded". Affected per the issue body: PDF, Office, HTML; text files unaffected.

## Scope — the ODB carve-out is not a vendor statement

Issue body: "When uploading to a standard OneDrive Business Account, this behavior does not occur."
— the reporter's 2018 observation, which rclone restated. Microsoft scoped its answer to "SharePoint
document libraries"; an ODB personal drive IS a SharePoint site, so the boundary is feature
enablement (Document ID service, library metadata columns), not architecture. Contradicted in-thread
by ytrezq (810151323): "Does this behavior happen on a user's OneDrive for Business?" → "sadly yes."
Usually unaffected, never guaranteed.

## (b) Labelled/AIP files: online size+hash ≠ downloaded bytes — CONFIRMED, and it is a DOWNLOAD fact

abraunegg `docs/usage.md` (master), § Support for Microsoft Azure Information Protected Files:
> "If you are using OneDrive Business Accounts and your organisation implements Azure Information
> Protection, these AIP files will report as one size & hash online, but when downloaded, will report
> a totally different size and hash. This is due to how the Microsoft Graph API handles AIP files and
> how Microsoft SharePoint (the technology behind Microsoft OneDrive for Business) serves these files
> via the API."
> "By default these files will fail integrity checking and be deleted locally…"

Vendor corroboration that the transform is on download — Purview: "When users download or access
these files from SharePoint or OneDrive, the sensitivity label and any encryption settings from the
label are enforced and remain with the file"; on SharePoint IRM: "applying encryption and
restrictions **when users download files**." Third cause, plain OneDrive Personal: rclone's iOS Live
Photos section — the downloaded `.heic` is smaller than the size shown online ("sizes differ").

## Is a sha256 of downloaded bytes a stable identity?

**Unresolved; no primary source asserts stability.** Nothing states that two downloads of an
unchanged item return identical bytes. For label-encrypted/IRM files protection is applied on the
download path (above), so cross-download byte identity is uncitable; for unlabelled files no
per-download transform is documented, so stability is plausible but unevidenced. Server-side sha256
is unavailable: Graph `hashes` — "**sha256Hash** … This property isn't supported. Don't use." and
"quickXorHash is the only value that is guaranteed to be available for both OneDrive for work or
school and OneDrive for home."

No live experiment: the only authenticated account here is a consumer outlook.com drive (OneDrive
Personal) — out of scope, and a test would write to the operator's live drive.
