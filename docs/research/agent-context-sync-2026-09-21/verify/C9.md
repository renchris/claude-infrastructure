# C9 — OneDrive scan guidance & SPO throttling

**Verdict: partially_confirmed.** Every number in (b) is exact against the live docs. One
sub-clause of (a) is misattributed, and the throttling doc *contradicts itself* on RateLimit
headers — the claim quotes only one side.

Sources (primary, Microsoft Learn; both `ms.date: 2025-10-02`):
- scan-guidance — `updated_at: 2026-05-14`, git `ae070e06c`, moniker `odsp-graph-online`
- avoid-throttling — `updated_at: 2026-08-10`, git `71e7d784f`, `ms.service: sharepoint-online`

## (a) Scan pattern — CONFIRMED except the "vs children paging for completeness" clause

Verbatim, under **Recommended calling pattern**:

> 1. **Discover** – Configure the locations that you want to scan.
> 2. **Crawl** – Discover and process the entire set of files that you are interested in.
> 3. **Notify** – Monitor changes to those files via notification.
> 4. **Process changes** – Reprocess only files that have changed by using delta query.

Stored deltaLink: "Always remember to keep the URL returned by @odata.deltaLink so you can
efficiently check for the changes later on."

Periodic reconcile, verbatim:

> Even with webhooks sending your application notifications, you may want to provide a periodic
> delta query to ensure that no changes are missed if it appears to have been a long time since a
> notification was received. **We recommend no more than once per day for this periodic check.**

**The misattribution.** scan-guidance never compares delta to `children` paging and never argues
delta on *completeness*; delta "gives apps an initial crawl of all content and then subsequent
changes from a point in time." The delta-over-children preference lives in the *other* doc and is
a **cost** argument: the RU table prices "Multi item query, such as list children, except delta
with a token" at 2 against delta-with-token at 1, and "Delta with a token is the most efficient
way to scan content in SharePoint."

## (b) Throttling numbers — all CONFIRMED

- RU cost: "| 1 | - Single item query, such as get item<br>- **Delta with a token**<br>- Download
  file from drive item |"; 5 RU for "All permission resource operations". Plus: "we lower the resource unit cost of delta requests with a token to
  1 resource unit, although it's a multi-item query. The delta request **without** a token ...
  costs 2 resource units per request." Carries "We reserve the right to change the API resource
  unit cost."
- Per APP Per Tenant RU, band 0–1,000 licences: 1 min → **1,250**, 24 H → **1,200,000**. Bands
  0–1,000 / 1,001–5,000 / 5,001–15,000 / 15,001–50,000 / 50,000+: 1 min = 1,250 / 2,500 / 3,750 /
  5,000 / 6,250; 24 H = 1.2M / 2.4M / 3.6M / 4.8M / 6.0M.
- Egress: User, 1 H → **100 GB**; Per APP Per Tenant, 1 H, "no license bound" → **400 GB**.
- Retry-After: "we **require** using the `Retry-After` HTTP header to ensure a minimum delay until
  the throttle is removed" and "Throttled requests count towards usage limits, so failure to honor
  `Retry-After` may result in more throttling."
- RateLimit: "**SharePoint Online does not return or support `IETF RateLimit` headers.** Although
  these headers may be used by other services, applications should not depend on them for
  SharePoint Online and should instead honor the `Retry-After` header when throttling occurs."
- User-Agent: "| Enterprise application | NONISV|CompanyName|AppName/Version | ..." (ISV form:
  `ISV|CompanyName|AppName/Version`), RFC2616 separators, appending to an existing UA is allowed.

## The residual the claim hides

The same page, two sections earlier, tells you to do what it later says is unsupported:
"Use the `Retry-After` and `RateLimit` HTTP headers" and "The `RateLimit` HTTP headers send you
early signals when you're close to limits." A live self-contradiction — design against the
negative; never make RateLimit-* load-bearing.

Claim omits the **tenant-wide** bucket that also gates an app: Tenant Resource Units, 5 min,
0–1,000 licences → 18,750 (up to 93,750 at 50,000+), shared across all apps in the tenant.
