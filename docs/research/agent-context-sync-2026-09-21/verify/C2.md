# C2-ctag-omitted-odb — adversarial verification

Verdict: **partially_confirmed**. (a) confirmed and the contradiction with scan-guidance is real; (b) confirmed for FILES but the same page states an opposite-flavoured rule for FOLDERS; (c) is true only as vendor *example* data, never stated normatively, and the "separate counters" half is not demonstrated (in every live record I measured the two counters were EQUAL). "Applies to SharePoint document libraries too?" — **undocumented**, not confirmed.

## (a) The exact table — primary, two independent renderings

`driveItem: delta` (v1.0 and beta), § Remarks, bullet 4:

> "Delta query won't return some DriveItem properties, depending on the operation and service type, as shown in the following tables."
>
> **OneDrive for Business**
> | Operation type | Properties omitted by delta query |
> | Create/Modify | `ctag` |
> | Delete | `ctag`, `name` |
>
> **OneDrive (consumer)**
> | Create/Modify | n/a |
> | Delete | `ctag`, `size` |

Same table in the doc SOURCE (`microsoft-graph-docs-contrib`, `api-reference/v1.0/api/driveitem-delta.md:393-405`), so the rendering is not an artifact. Pinned-commit URL of the live page: gitcommit `079340ab…` (v1.0), `4a9839ac…` (beta).

The contradiction is with the scan-guidance page's § Process changes:

> "If your processing requires downloading the contents of an individual file, you can use the cTag property to determine if the contents of the file have changed since the last time you downloaded it."

That sentence sits immediately after "Follow up the acknowledgement with a delta query for the latest changes" — i.e. it prescribes a property the delta response for ODB does not carry. Both pages are Microsoft reference docs; neither cross-references the other on this point. The Graph **known-issues** page has no cTag / driveItem-delta entry at all (checked 2026-09-21), so this is *documented behaviour*, not a filed known issue.

**SharePoint:** the omission tables name exactly two service types — "OneDrive for Business" and "OneDrive (consumer)". There is no SharePoint row, and no sentence extends the table to document libraries. The same file *does* name SharePoint explicitly where it means it ("This feature is applicable to SharePoint and OneDrive for Business but not consumer OneDrive accounts"), so silence here is not shorthand for inclusion. Treat SharePoint as **unmeasured**.

## (b) eTag vs cTag — driveItem resource, property table

> cTag: "An eTag for the content of the item. This eTag isn't changed if only the metadata is changed. **Note** This property isn't returned if the item is a folder. Read-only."
> eTag: "eTag for the entire item (metadata + content). Read-only."

Confirmed for files. Scope limit the claim omits — the note below the same table INVERTS the roles for containers:

> "The eTag and cTag properties work differently on containers (folders). The cTag value is modified when content or metadata of any descendant of the folder is changed. The eTag value is only modified when the folder's properties are changed…"

Plus: "In OneDrive for Business or SharePoint document libraries, the **cTag** property isn't returned, if the **driveItem** has a folder facet."

## (c) Shared GUID, separate counters

Not stated in any property table. Sole vendor evidence is the `Get driveItem` example response:

> `"cTag": "\"c:{86EB4C8E-D20D-46B9-AD41-23B8868DDA8A},0\""`
> `"eTag": "\"{86EB4C8E-D20D-46B9-AD41-23B8868DDA8A},1\""`

(That example is itself inconsistent with the folder note above — it carries a cTag on a `folder`-faceted root whose webUrl is `contoso-my.sharepoint.com`.)

Live read (read-only `GET /drives/{id}/items/root/delta`, OneDrive **consumer**, `ren.chris@outlook.com`, 2026-09-21): file records carry both, shape as claimed — `eTag "{D2D9BE1E-86DE-209C-80A2-A70000000000},2"` / `cTag "c:{D2D9BE1E-86DE-209C-80A2-A70000000000},2"`; folder records carry eTag and **no** cTag. Across ~35 file records the two counters were always equal (2/2, 3/3), so the shared-GUID half is confirmed and the *divergent*-counter half ("…,4" vs "c:…,2") is unobserved here. This run also acts as a control for the consumer row: cTag present on Create/Modify, as "n/a" predicts.
