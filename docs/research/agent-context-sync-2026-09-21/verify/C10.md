# C10-ooxml-hash-churn — verdict: partially_confirmed

Instruments: macOS 15.7.9 (24G830), Python 3.11.4, openpyxl 3.1.5, python-docx 1.x (import ok),
zipfile (stdlib). All files under this dir. Two attempts at refutation failed; one sub-clause is wrong
and one is writer-dependent.

## Measured — openpyxl, two saves 3 s apart (`exp.py`)
- whole-file sha256 differs: `fa572b6e…` (4840 B) vs `8f8c4b58…` (4839 B).
- part NAME list identical (9 parts). Per-part content sha equal on all but ONE.
- **CONTENT-VOLATILE PARTS: `['docProps/core.xml']`** — and it is volatile in `dcterms:created`
  **as well as** `dcterms:modified` (openpyxl stamps both with `now`):
  `…created…>2026-09-21T21:11:08Z<…modified…>2026-09-21T21:11:08Z<` vs both `…21:11:11Z`.
- ZIP `date_time` moved on **all 9 entries** ((2026,9,21,16,11,8) → (…,10)).
- Rollup over sorted `name+content`, no ZIP metadata: **differs**.
  Same rollup **excluding `docProps/*`: identical** (`369b9935…` both).

## Measured — python-docx, two saves 3 s apart (`exp2.py`)
- whole-file sha256 differs (`b2a420f4…` vs `d0630ea6…`).
- **content-volatile parts: `[]`** — `docProps/core.xml` is byte-identical (template values,
  `dcterms:created 2013-12-23T23:15:00Z`); `docProps/app.xml` carries `<TotalTime>0</TotalTime>`
  and does not change. ZIP `date_time` moved on all 17 entries.
  ⇒ the claim's "because … core.xml carries dcterms:modified" is NOT the cause here; the ZIP
  timestamps alone are sufficient.

## Measured — ZIP-timestamp axis isolated (stdlib only)
Two zips, identical member bytes, entry `date_time` 2 s apart: container sha
`edaaebc2…` vs `02fef577…`, per-part content equal. Differing byte offsets **[10, 69, 133, 198]** —
i.e. the 2-byte mod-time field of each *local* header **and** of each *central directory* header
(raw `0050355d` → `0150355d`).

## Measured — the churn is a writer choice, not a format necessity
Re-emitting both xlsx with pinned `date_time=(1980,1,1,0,0,0)` and normalised core.xml dates yields
**identical whole-file sha256** (`97faf7ac…` both). So "an OOXML container changes bytes on re-save"
is true of real writers, false as a property of the format.

## Primary sources
ECMA-376 Part 2, 5th ed. Dec 2021 (OPC), Table 3 — Core properties:
`modified | DCMI Metadata Terms | Date on which the resource was changed.`
§8.3.4.3: "This document allows created and modified elements as core property elements… These
elements shall have the xsi:type attribute whose value is `dcterms:W3CDTF`"; §8.3.1 example shows
`<dcterms:modified xsi:type="dcterms:W3CDTF">2005-11-23</dcterms:modified>` inside `<coreProperties>`.
§8.2: "A package shall contain at most one Core Properties part."
PKWARE APPNOTE.TXT 6.3.10 (FINAL, Nov 01 2022) §4.3.7 local file header and §4.3.12 central file
header both list `last mod file time 2 bytes` / `last mod file date 2 bytes`.
Microsoft Learn, `DocumentFormat.OpenXml.ExtendedProperties.TotalTime`: "Total Edit Time Metadata
Element… Total time that a document has been edited. The default time unit is minutes."

## Scope / residual
Tested: openpyxl 3.1.5 + python-docx writers on macOS 15.7.9. **NOT tested:** real Microsoft Word /
Excel / PowerPoint saves (no Office run here) — so the `app.xml` `TotalTime` arm and Word's
`word/settings.xml` `w:rsid*` / `w:proofState` churn are *unmeasured*; a `docProps/*`-excluding
rollup may therefore still over-trigger on real Word files. `.pptx` untested. Nothing OneDrive- or
SharePoint-specific was exercised; a sync service may also rewrite the container independently.
