# C1-quickxor-in-business-delta — PARTIALLY CONFIRMED

Verdict: the hash is available in business/SharePoint delta items, but "guaranteed present for every file"
is refuted by the vendor's own wording and by both reference clients, which code for its absence.

## 1. Availability by drive type (primary, Graph v1.0 `hashes`, ms.date 2024-03-21)

- "**quickXorHash** is the only value that is guaranteed to be available for both OneDrive for work or
  school and OneDrive for home."
- Counterweight on the same page: "Not all services provide a value for all hash properties listed." and
  each property is "(if available)".

Scope gap: the vendor sentence names *OneDrive for work or school* and *OneDrive for home*. No primary
Microsoft sentence I reached names a **SharePoint document library** for quickXorHash. rclone's docs say
"OneDrive Personal, OneDrive for Business and Sharepoint **Server** support QuickXorHash"
(docs/content/onedrive.md:296) — again not SharePoint Online libraries by name.

## 2. It rides inside the delta item (no second call)

`driveItem: delta` returns "a collection of DriveItem resources in the response body", and its Remarks
enumerate exactly what delta drops:

- OneDrive for Business — Create/Modify: `ctag`; Delete: `ctag`, `name`.
- OneDrive (consumer) — Create/Modify: n/a; Delete: `ctag`, `size`.

`file` / `file.hashes` is **not** in either omission list ⇒ documented-present on business Create/Modify.
Note the trap this creates: Microsoft's own scale guidance says "you can use the cTag property to determine
if the contents of the file have changed since the last time you downloaded it" (scan-guidance,
updated 2026-05-14) — and `ctag` is the one property delta omits on business drives. Hash is the in-band
substitute, not the documented mechanism.

Client corroboration that it comes from the listing JSON:
- rclone `backend/onedrive/api/types.go:147-151` — `FileFacet{ MimeType, Hashes }`; `onedrive.go:2307-2326`
  reads `file.Hashes.QuickXorHash` off the item, and `onedrive.go:1351` marks that parser "works on both
  normal listings and delta listings" (delta path `/root/delta`, lines 1594, 3139-3166). No extra request.
- abraunegg `src/itemdb.d:149-166` — reads `driveItem["file"]["hashes"]["quickXorHash"]` straight from the
  delta driveItem JSON; falls back to `sha256Hash`.

## 3. Documented / in-code conditions where the hash is ABSENT

1. **OneNote**: `src/sync.d:2364` — "Microsoft OneDrive OneNote file objects will report as files but have
   'application/msonenote' or 'application/octet-stream' as their mime type and **will not have any hash
   entry**"; personal vs business differ in mimeType per 2370-2374. OneNote *packages* have neither file nor
   folder facet (`sync.d:2345`).
2. **No `size` / zero size**: itemdb only parses hashes when `hasFileSize()` is true (`itemdb.d:150-152`),
   else sets size "0"; `sync.d:12870-12876` only expects a hash when `size > 0`.
3. **Arbitrary API inconsistency**: `sync.d:12886` — "WARNING: OneDrive API inconsistency - this file does
   not have any hash" for non-OneNote files. rclone: "If the hash requested does not exist on the object, it
   will be returned as an empty string which is treated as a missing hash" (onedrive.go:374-376).
4. **`$select` without `file`** removes the facet (delta supports `$select`).
5. **False-positive risk, SharePoint-specific**: "It is a known issue that Sharepoint (not OneDrive or
   OneDrive for Business) silently modifies uploaded files, mainly Office files (.docx, .xlsx, etc.),
   causing file size and hash checks to fail" (rclone onedrive.md:1244-1251, citing
   OneDrive/onedrive-api-docs#935). Server-side rewrite changes the hash with no client write.

Not tested: no live business/SharePoint tenant was called; SharePoint-library presence rests on client code
+ absence from delta's omission table, not on a vendor sentence.
