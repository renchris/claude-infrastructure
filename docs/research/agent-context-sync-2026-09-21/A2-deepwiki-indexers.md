# A2 — How code-knowledge indexers refresh a derived layer: DeepWiki, Zoekt, Copilot, Cody, Augment, Sphinx

Date: 2026-09-21. Axis: does the class of "derived pages/indexes over a changing source" regenerate **wholly** or **per affected unit**, and does anything keep a **since-cursor** / expose a **diff of the derived layer**.

## Verdict, first

**Nothing in the DeepWiki class does affected-page regeneration, and DeepWiki specifically has no page↔source dependency graph and no freshness mechanism a consumer can rely on.** The generated-prose layer (DeepWiki, Devin Wiki) is regenerated as **one whole unit**, billed per unit, triggered by a human or an agent tool call, and pinned to a single source commit. The incremental machinery in this space lives entirely in the **mechanical** layers below prose — Zoekt's shard/tombstone indexer, Cody's incremental embeddings, Sphinx's `note_dependency` — and those are the only places a transferable design exists. **The lead's L1→L5 hypothesis is therefore not "like DeepWiki"; it is strictly more capable than DeepWiki, and its L4 (page↔source map) has no vendor precedent in the wiki-generator class at all — the precedent is Sphinx's dependency-tracking build environment and Zoekt's 7-state freshness verdict.**

Empirically measured this session: **12 of 12 public DeepWiki wikis are stale, median ≈1 month, worst 17 months**, and the "add the badge for weekly refresh" claim circulating in blog posts is **refuted** on a badge-carrying repo.

Three conclusions that a design cannot get from the docs:

1. **No cadence exists.** `react` and `langchain` share an identical date (22 Aug) while `pytorch` is same-day and `markitdown` is four months behind — consistent with demand-triggered regeneration plus occasional cohort sweeps, inconsistent with per-push or per-week.
2. **The "add the badge → weekly auto-refresh" claim is refuted.** `AsyncFuncAI/deepwiki-open` carries the badge four times in its README and its wiki is 27 days old with 9 days of unindexed commits. A weekly refresh would have fired ~3 times inside that window. *(Adversarial note: this refutes the claim as circulated in third-party blog posts; I found no first-party page making it, so the correct reading is "the claim has no vendor source and does not hold on the one badge-carrying repo I could test".)*
3. **The provenance pin is per-wiki, not per-page** — one `Last indexed: <date> (<sha>)` in the nav, shared by every page. So even where a page's content is still correct, the wiki cannot tell you *which* pages the last 2 months of commits invalidated. That is the exact hole L4 has to fill, and no vendor fills it.

## Mechanism detail, with quotes

### Zoekt — the reference implementation of "is my derived artifact stale, and how stale"

A 7-state freshness verdict, not a boolean. `index/builder.go:366-374`:

```go
IndexStateMissing  = "missing"      IndexStateCorrupt = "corrupt"
IndexStateVersion  = "version-mismatch"   // index format/feature version moved
IndexStateOption   = "option-mismatch"    // hash of BUILD OPTIONS changed
IndexStateMeta     = "meta-mismatch"      // mutable metadata only → rewrite .meta, don't rebuild
IndexStateContent  = "content-mismatch"   // branch commit shas differ → rebuild
IndexStateEqual    = "equal"              // skip
```

`IncrementalSkipIndexing() == (state == IndexStateEqual)` (`builder.go:389-393`). The content test is literally a sha comparison: `if !reflect.DeepEqual(repo.Branches, o.RepositoryDescription.Branches) { return IndexStateContent }` (`builder.go:434-436`), and the option test is a hash of only the options that can invalidate content — `HashOptions contains only the options in Options that upon modification leads to IndexState of IndexStateMismatch during the next index building` (`builder.go:129`).

**Why this is the single most transferable artifact in the whole axis:** `IndexStateMeta` vs `IndexStateContent` is precisely the operator's *frontmatter-only update* vs *re-convert* split, and `IndexStateOption` is the *converter-version changed, everything must be rebuilt* case that a naive source-hash manifest cannot see.

Delta (file-level) builds, opt-in per repo:

- `// IsDelta is true if this run contains only the changed documents since the last run.` and `// changedOrRemovedFiles is a list of file paths that have been changed or removed since the last indexing job for this repository. These files will be tombstoned in the older shards for this repository.` (`builder.go:105-113`)
- The change set is a git tree diff against the *last indexed* commit: `object.DiffTreeWithOptions(ctx, lastIndexedTree, branchToCurrentTree[branch.Name], &object.DiffTreeOptions{DetectRenames: false})` (`gitindex/index.go:1010`). **`DetectRenames: false`** — a rename is modelled as delete+add. For the operator's "same doc re-uploaded as `v3 FINAL`" case this is the honest default: identity comes from content hash, not from the name, and rename detection is a *later* inference layer.
- Old shards are not rewritten; only their metadata is: tombstones are set on the changed paths and the branch `Version` is advanced (`builder.go:690-740`), via `SetTombstone` / `UnsetTombstone`, described as **idempotent** (`index/tombstones.go:14-22`).
- Guard rails: delta is abandoned and a full build runs on any incompatibility — `log.Printf("delta build: falling back to normal build since delta build failed…"); opts.BuildOptions.IsDelta = false` (`gitindex/index.go:596-597`) — triggered by a changed branch set, a changed options hash, submodules, an `.ignore` file, a compound shard, or too many accumulated delta shards: `DeltaShardNumberFallbackThreshold defines an upper limit (inclusive) on the number of preexisting shards that can exist before attempting another delta build` (`gitindex/index.go:441-447`).
- Deletes are **soft, with restore**: `cleanup trashes shards in indexDir that do not exist in repos. For repos that do not exist in indexDir, but do in indexDir/.trash it will move them back… [removing] shards that have been in the trash for 24 hours` (`cleanup.go:26-29`), and a reappearing repo gets `removing tombstone for %v` + `index.UnsetTombstone` (`cleanup.go:116-130`). Space is reclaimed later by a periodic vacuum: `vacuumInterval is how often indexserver scans compound shards to remove tombstones` (`merge.go:191-193`).
- The scheduler is a poll + priority queue: a goroutine "updates the queue with commits to index" every `Interval`, `s.queue.MaybeRemoveMissing(repos.IDs)` handles disappearance, and `AddOrUpdate` invalidates on option identity alone — `if !reflect.DeepEqual(item.opts, opts) { item.indexed = false; item.opts = opts }` (`queue.go:123-129`).

### Cody embeddings — the debounce, and the cause of death

`Incremental embeddings allow you to update the embeddings for a repository without having to re-embed the entire repository. With incremental embeddings, outdated embeddings of deleted and modified files are removed and new embeddings of the modified and added files are added to the repository's embeddings. This speeds up updates, reduces the data sent to the embedding provider and saves costs.` — default on.

And the rate limiter, which is the part most designs omit: `the repository will be scheduled for embedding with every new commit. By default, there is a 24-hour time interval that must pass between two embeddings… if a repository is scheduled for embedding at 10:00 AM and a new commit happens at 11:00 AM, the next embedding will be scheduled earliest for 10:00 AM the next day` (`minimumInterval`, default `24h`).

Sourcegraph then **deleted the whole layer**, and one of the three stated reasons is freshness cost, not accuracy: *"The process of creating embeddings and keeping them up-to-date introduces complexity that Sourcegraph admins have to manage"* — alongside third-party code egress and vector-search scaling ([blog](https://sourcegraph.com/blog/how-cody-understands-your-codebase)). The replacement *"doesn't require sending code to an embedding processor, it requires zero additional config, and it scales to massive codebases."*

**This is the strongest single argument for the lead's design choice of markdown-in-git as the derived layer.** A vendor with a dedicated team retired its incremental derived index because keeping it fresh was operationally unaffordable, and replaced it with grep-class search over the source of truth. The operator's L3/L5 (deterministic markdown mirror + git) is that same retreat made on purpose, and it is the cheap end of the trade.

### GitHub Copilot — lazy pull, no cursor exposed

`Indexing runs in the background and initial indexing can take up to 60 seconds for a large repository. Once a repository has been indexed for the first time, re-indexing is much quicker and the index will typically be automatically updated to include the latest changes within seconds of you starting a new conversation.` (github/docs, `repository-indexing.md:41`). Trigger is **the read**, not the write. No mechanism, granularity, delete handling or cursor is documented — *undocumented*, and the vendor gives the consumer no way to ask "as of which commit".

Transferable: **freshness-on-read is a legitimate trigger** and it is cheaper to reason about than a watcher, because the check happens exactly when correctness matters. For the operator: a `docs/` staleness check at the top of an agent session ("manifest vs source cursor") beats a daemon, if the check itself is O(changes).

### Augment — continuous, per-user, and the converter-version tax

`we maintain a real-time index of your codebase, for each user` / `Our goal is to update your personal search index within a few seconds of any change to your files` / `Changing branches in git, search-and-replace, and automatic formatting can quickly change 100s of files within a second` / `your branch switch is handled almost instantly`.

Two details that matter more than the latency claim:

- **Content addressing is load-bearing in production**: `the IDE must prove to the backend it knows a file's content by sending a cryptographic hash to our backend before it is allowed to retrieve content from the file` (Proof of Possession), and `we share the parts of search indices that overlap between users from the same tenant`. Hash-keyed derived artifacts are how the duplicate work disappears.
- **The converter is an invalidation axis, and it fires often**: `Another case of bulk uploads is the deployment of new search indices. Our context awareness is constantly improving, which makes this a surprisingly common event.` A model/converter upgrade is a *full* rebuild, and the vendor calls its frequency surprising. Zoekt encodes the same thing as `IndexStateOption`.

### DeepWiki / Devin Wiki — whole-unit generation, and a *manual* page manifest where a dependency graph should be

- The unit of work and of billing is the wiki: `Low (default) Free / Medium ~5-10 ACUs per wiki / High ~20-40 ACUs per wiki`, and `Wiki v2 … shows the ACU cost of the last generation so you can see exactly what each refresh costs`. There is no per-page price, no per-page trigger, and no per-page freshness.
- Page planning is either automatic clustering or a checked-in manifest, and the manifest *replaces* planning entirely: `If a .devin/wiki.json file is found in your repository's root directory during wiki generation, we'll use the provided repo_notes and pages to steer wiki generation… When a config file is present, we bypass the default cluster-based planning and create exactly the pages you specify — so list every page you want.` Limits: `Maximum 30 pages (80 for enterprise)`, `Maximum 100 total notes`, `Maximum 10,000 characters per note`. A page is `{title, purpose, parent, page_notes}` — **`purpose` is prose, not a path set**. There is no field binding a page to source files, so nothing in the format could drive affected-page regeneration even if the backend wanted to.
- Provenance is recorded at generation: `Source citations in Devin Wiki for Azure DevOps repositories now open the correct file, linking to the exact commit the wiki was built from` (release notes, 2026-09-16).
- Regeneration is an *action*, invocable by an agent: `A new card is now displayed in sessions when the generate_wiki MCP tool is invoked, giving better visibility into wiki generation progress.`
- The same vendor ships incremental for the mechanical layer: `The v3 API can now trigger an incremental (diff) scan immediately`, plus a `one-time "Scan new commits" action`. So the whole-unit treatment of the wiki is a considered choice about *generated prose*, not a company-wide blind spot.

**Theoretical (my reasoning, not cited):** the reason prose is regenerated whole is that a page's content depends on a *cluster* of files plus every other page's existence (cross-links, hierarchy, dedupe of narrative). Per-page invalidation would need the dependency edge set to be captured at write time — which is exactly what the citations already are (`[gitindex/index.go:679-873]`) and exactly what nobody is using as an invalidation input. That is the arbitrage available to the operator: **capture the edges you already emit as citations, and you get affected-page regeneration for free.** The cost is that line-ranged citations rot on any insertion, so the edge must be stored as *page → source path (+ content hash)*, with the line range as display-only.

### Sphinx — the one documented page↔source dependency graph in the class

`note_dependency(filename)`: *"Add filename as a dependency of the current document. This means that the document will be rebuilt if this file changes."* A per-document edge set, persisted in the build environment, driving affected-document-only rebuilds. It is 20 years old, boring, and it is the missing L4 primitive.

## What transfers, mapped to the lead's L1–L5

| Pipeline slot | Transferable mechanism | Source |
|---|---|---|
| **L1 acquisition** | Poll for *options+cursor* per subject, not for content; enqueue on option-identity change (`AddOrUpdate`); `MaybeRemoveMissing` to detect disappearance; priority queue with backoff | zoekt `queue.go:123-141`, `main.go:386-432` |
| **L1 trigger choice** | Freshness-on-read is a valid and cheap trigger — check at the moment of consumption rather than running a watcher | Copilot `repository-indexing.md:41` |
| **L2 manifest** | A **multi-state** verdict, not a boolean: missing / corrupt / format-version / **converter-options-hash** / **metadata-only** / **content** / equal. Hash only the options that can change output | zoekt `builder.go:129, 366-448` |
| **L2 change detection** | Diff last-recorded state → current with **renames off**; identity from content hash; rename is an inference layer above delete+add | zoekt `gitindex/index.go:1010` |
| **L3 conversion** | Deterministic, idempotent, and **falls back to a full rebuild on any precondition it cannot satisfy** rather than producing a half-correct incremental result; cap accumulated deltas before forcing a compaction | zoekt `gitindex/index.go:441-447, 593-601` |
| **L3/L5 deletes** | Soft-delete with a restore window (24 h trash), tombstone-then-vacuum, idempotent tombstone set/unset. A source that vanishes for one sync is not a deletion | zoekt `cleanup.go:26-29, 45, 116-130`; `merge.go:191-193`; `tombstones.go:14` |
| **L4 curation** | An explicit page→source edge set captured at write time is what makes affected-page regeneration possible; store paths+hashes, not line numbers | Sphinx `note_dependency`; DeepWiki's citations as the un-exploited raw material |
| **L4 economics** | **Debounce the expensive derived layer per subject** (Cody: min 24 h between runs, regardless of commit rate). Cheap L3 conversion can fire per change; expensive L4 agent curation must not | Cody `minimumInterval` |
| **L4/L5 invalidation axis** | A converter/prompt/model version bump is a full-corpus rebuild event and it happens more often than you plan for — put the converter version in the manifest key and budget the sweep | Augment ("surprisingly common event"); zoekt `IndexStateOption` |
| **L5 consumer contract** | Record the source cursor *in the derived artifact* (`Last indexed: date (sha)`, "links to the exact commit the wiki was built from") — but **per page**, not per corpus, which is where DeepWiki stops | DeepWiki nav; Devin release notes |
| **Whole-design** | Prefer a grep-able derived layer over a vector index you must keep fresh — the freshness burden is what killed the vendor's own embeddings product | Sourcegraph blog |

## Direct answers to the brief's questions

**(a) Does DeepWiki regenerate the whole wiki on every push, or only affected pages? Is there a page↔file dependency graph?**
Neither: it does not regenerate on push at all. Generation is a **whole-wiki unit** triggered by a human ("Refresh this wiki" → "Enter email to refresh"), an onboarding event, or an agent tool call (`generate_wiki`), priced per wiki in ACUs. **No page↔file dependency graph exists in any documented surface**; the only page-level source binding is per-page *citations* emitted as output, and the only page-level *input* control is the hand-written `.devin/wiki.json` page list, whose `purpose` field is prose. Measured staleness: median ~1 month, worst 17 months, across 12 public wikis.

**(b) How does Zoekt incrementally index commits and reclaim deleted files?**
Two layers. Repo-level: `IncrementalSkipIndexing` compares on-disk shard metadata against build options and per-branch commit shas, and skips only on `IndexStateEqual`. File-level (opt-in `-delta`): `git` tree diff from the last indexed commit per branch produces `changedOrRemovedFiles`; new shards are appended with numbering continuing from the last shard so "all the shards [are] discovered as a set", and old shards get **file tombstones** plus an advanced branch `Version` — their content is never rewritten. Reclamation is two-phase: repos absent from the source list go to `.trash` and are restored if they reappear, hard-deleted after 24 h; inside compound shards, repos are tombstoned and reclaimed by a periodic **vacuum**; compound shards below `minSizeBytes` are dismantled. Delta refuses and falls back to a full build on branch-set change, options-hash change, submodules, `.ignore` files, compound shards, or too many accumulated delta shards.

**(c) Which systems keep a "since" cursor, and which rescan?**
Cursor: **Zoekt** (per-branch commit sha stored in shard metadata — a real, inspectable cursor, and the diff is computed against it), **Cody embeddings** (scheduled per new commit, debounced 24 h), **DeepWiki/Devin** (records one commit sha per wiki, but the cursor is *provenance only* — the next refresh does not diff against it). Rescan / opaque: **Copilot** (no cursor surfaced; refreshes lazily at conversation start), **Augment** (no commit cursor by design — it indexes the uncommitted working state from file events).

**(d) Does anything expose the diff of the *derived* layer to the consumer?**
**No.** No system in this sample publishes a changelog of its derived pages. The closest instances are (i) DeepWiki's `Last indexed: <date> (<sha>)`, from which a consumer can derive the *source* diff themselves, and (ii) Devin's **security scans**, which expose an explicit `incremental (diff) scan` endpoint and a "Scan new commits" action — the mechanical layer, not the prose layer. **This is a genuine gap, and the lead's L5 (git-tracked `docs/`, so "what changed since I last looked" is `git diff`) is strictly better than every product surveyed** — it makes the derived-layer diff a first-class, queryable artifact that no vendor offers.

## Failure modes this evidence predicts for the L1–L5 design

1. **Converter-version churn dominates source churn.** Every prompt/converter/frontmatter-schema tweak invalidates the whole corpus (zoekt `IndexStateOption`; Augment's "surprisingly common event"). Without an options hash in the manifest, the mirror silently mixes outputs of three converter generations; with one, you need a bounded full-sweep path and a budget for it.
2. **Delta accumulation degrades the read side.** Zoekt caps preexisting delta shards and falls back to a full build for exactly this reason. A `docs/` tree whose pages are patched incrementally forever accumulates drift against what a from-scratch generation would produce; schedule periodic full regeneration of a page (a "compaction") and record when it last happened.
3. **A missing source is not a deleted source.** Zoekt's 24 h trash + restore exists because sync sources lie transiently — and a Graph `delta` token expiry or a throttled page will look exactly like mass deletion. Hard-deleting markdown on first absence is the failure; tombstone with a restore window.
4. **Renames are not detected for you.** `DetectRenames: false` is the production default in zoekt. "Q3 Report v2.docx" → "Q3 Report FINAL.docx" arrives as delete+add, and only a content hash can rejoin them. Plan the rename inference as a separate, auditable step whose false positives are cheap.
5. **The expensive layer must be debounced, not event-driven.** Cody's 24 h `minimumInterval` is the vendor conceding that per-commit regeneration of an LLM-derived layer is unaffordable. An L4 that fires per changed file will burn quota on a corpus where one PowerPoint re-upload touches 40 slides.
6. **Line-ranged provenance rots.** DeepWiki's citations are `path:NNN-NNN`; any insertion above invalidates them, and the wiki has no mechanism to notice. Store the edge as path+content-hash; render lines as a convenience only.
7. **Per-corpus provenance hides per-page staleness.** A single `Last indexed` for 30 pages cannot tell a reader which pages the last 2 months of changes invalidated — the observed DeepWiki failure. Frontmatter must carry the cursor **per page**.
8. **Whole-unit generation is the vendor default for a reason.** Prose pages depend on a cluster of sources *and on each other* (hierarchy, cross-links, non-duplication). Affected-page regeneration will produce cross-page incoherence unless the map also records page→page edges, which nothing surveyed does.

## Alternatives considered and ruled out

- **Greptile** — its public docs no longer document repository indexing (the surviving `llms.txt` indexes only code-review, MCP tools and webhooks for review sessions). Indexing granularity: **undocumented**; not guessed.
- **Mintlify-style doc generators** — build the whole site per commit in CI; the incremental question lives in the static-site builder, not the generator, and adds nothing beyond Sphinx (which documents the mechanism explicitly). Ruled out as redundant.
- **Cursor / turbopuffer** — assigned to a sibling axis; the one thing needed here is that the *retrieval* layer's diff story is orthogonal to the *derived-pages* layer's. Cursor's documentation now describes "Instant Grep [that] builds and queries its index on your machine" and states `Cursor does not upload file paths or code to build a search index` — I could not retrieve a first-party Merkle-tree statement from the current docs, so **the widely-repeated "Cursor uses a Merkle tree to send only changed files" claim is left uncited here**, and any third-party restatement of it (including for Augment) should be treated as unverified.
- **deepwiki-open / third-party DeepWiki clones** — do advertise incremental re-indexing and file watchers, but they are reimplementations, not evidence about the vendor's architecture. Excluded from the table.

## Open questions / blockers

- **Enterprise Devin Wiki cadence is undocumented.** Nothing in `docs.devin.ai` (incl. `llms.txt`, `index-repo.md`, `deepwiki.md`) or ~135 KB of release notes states when a wiki is regenerated after onboarding. Only resolvable from inside a tenant.
- **Whether DeepWiki reuses anything across generations** (page-level caching, unchanged-page skip) is invisible from outside; the per-wiki ACU pricing is consistent with whole regeneration but does not prove it.
- **Whether the displayed `Last indexed` sha is the *wiki's* build commit or the *search index's*** is not documented; I treat it as the wiki's because the citation-link release note describes citations resolving against "the exact commit the wiki was built from".
- **Zoekt delta builds' production status.** The code paths are gated per repo (`UseDelta` "should only be true for repositories we explicitly enable") and carry several `TODO`/`HACK` markers (submodules, ignore files). Treat file-level delta as *reference design*, repo-level `IncrementalSkipIndexing` as the battle-tested part.
- **Copilot's internal granularity** — undocumented; the only observable is that refresh is read-triggered and fast.
