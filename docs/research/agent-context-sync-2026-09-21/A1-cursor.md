# A1 — Cursor's incremental index sync: what is actually documented, and what transfers to a `/docs` pipeline

Axis: how Cursor detects and syncs ONLY changed content (Merkle tree, chunk hashing, turbopuffer, cadence, path obfuscation), from primary sources, mapped onto the lead's L1–L5 hypothesis.

**Headline (and it cuts against a naive copy of Cursor):** Cursor's diff engine is a **two-level content-addressed store — file-level hashes for the *sync*, chunk-content hashes for the *expensive derived artifact*** — and the Merkle *tree* exists for reasons the operator does not have (a remote peer, cryptographic access proofs, 80M tenants). For `docs-source → docs` on one machine, the tree is ceremony; the **two-level hashing is the whole lesson**, and Cursor's own current docs now say its default search index is built **locally with no embeddings at all** — which is the strongest available evidence for "markdown + grep, not a vector store."

## 2. What turbopuffer contributes *beyond* the Merkle sync (all primary, [turbopuffer.com/docs/write](https://turbopuffer.com/docs/write), [/docs/architecture](https://turbopuffer.com/docs/architecture), [/docs/limits](https://turbopuffer.com/docs/limits))

- **Upsert-by-id is the update primitive**: "Within a namespace, documents are uniquely referred to by their ID." · "Existing documents with matching IDs are overwritten entirely." So the diff engine only has to name ids; the store needs no notion of "change".
- **Three write shapes, priced differently** — and this is the cost model for renames vs edits: `upsert` (whole doc), `patch` ("updates one or more attributes of an existing document"; "Patches are billed for the size of the patched attributes (not the full written documents)"), `delete` by id, plus `delete_by_filter` / `patch_by_filter`. Caveat that matters: "Vector attributes currently cannot be patched. You currently need to retrieve and upsert the entire document." and "Any patches to IDs that don't already exist in the namespace will be ignored; patches will not create any missing documents."
- **Copy / branch = index reuse primitives**, i.e. M8's server side: `copy_from_namespace` ("Copying is billed at up to a 75% write discount… a faster, cheaper alternative to re-upserting documents") and `branch_from_namespace` ("Creates an instant copy-on-write clone… billed at a flat rate of $0.032").
- **Batch, don't drip**: "Large batches of writes are highly encouraged to maximize throughput and minimize cost. Write requests can have a payload size of up to 512 MB." and per namespace: "Each namespace can currently write 1 WAL entry per second. Concurrent writes to the same namespace are batched into the same entry." Max per-namespace write throughput is "10k writes/s @ 32 MB/s". ⇒ **a per-file write loop is architecturally wrong; one write per sync cycle is right.**
- **Async indexing with an explicit unindexed window**: "After data is committed to the log, it is asynchronously indexed"; backpressure kicks in via HTTP 429 "when unindexed data exceeds 2 GB or 1 million rows"; "Eventually consistent queries search only the first 128 MiB of unindexed data"; progress readable via `unindexed_bytes`. ⇒ freshness is *observable*, not assumed.
- **Cold/warm asymmetry**: "The first query to a namespace reads object storage directly and is slow (p50=874 ms for 1M documents), but subsequent, cached queries to that node are faster (p50=14 ms)". Write latency "p50=165 ms for 500kB".
- **Scale, primary rather than second-hand**: limits page reports max documents global "Unlimited (seen: 1T+ @ 3PB+)" and max namespaces "Unlimited (seen: 250M+)".

## 3. Published numbers on sync / change cost

| Number | Meaning | Source |
|---|---|---|
| ~3.2 MB | "In a workspace with fifty thousand files, just the filenames and SHA-256 hashes add up to roughly 3.2 MB. Without the tree, you would move that data on every update." | blog |
| 92% | "clones of the same codebase average 92% similarity across users within an organization" — the premise of index reuse | blog |
| TTFQ median **7.87 s → 525 ms**; p90 **2.82 min → 1.87 s**; p99 **4.03 hrs → 21 s** | effect of reusing a teammate's index instead of building one | blog |
| 80% | "semantic search isn't available until at least 80% of that work is finished" — indexing has a usability threshold, not a linear ramp | blog |
| +12.5% avg (6.5–23.5%) answer accuracy; code retention **+0.3% overall, +2.6% on codebases ≥1,000 files**; **+2.2%** dissatisfied follow-ups without semantic search | semantic search *vs grep alone* | [cursor.com/blog/semsearch](https://cursor.com/blog/semsearch) (Nov 6, 2025) |

**Read the last row adversarially, because it is the one that sets the operator's build/skip decision:** the retention gain from embeddings is **+0.3%** overall and only reaches +2.6% past 1,000 files. A curated `/docs` mirror of a corporate document set is *small* in file count. Cursor's own numbers say grep-class retrieval over a well-named tree is within a couple of percent of a trained-embedding vector store on that scale — and Cursor's live docs (M14) now ship a **local** index as the default. *Empirical for the deltas; the transfer to markdown corpora is my reasoning.*

## 4. What transfers to a `docs-source → docs` pipeline (and what does not)

**Transfers, load-bearing:**

1. **Two-level content addressing is the entire mechanism worth copying.** Hash the *source bytes* to decide whether to re-run a converter (M1), and hash the *derived chunk/section content* to decide whether to re-do the expensive downstream step (M7 — for Cursor, embedding; for the operator, LLM curation/summarisation tokens). Cursor's cheap incrementality comes from the second hash, not the first: the first only says "this file moved", the second says "and only 2 of its 40 chunks actually differ." This is the direct answer to *"a same-named file was overwritten"*: the file hash changes, the chunk hashes mostly do not, and only the changed chunks cost anything. Maps to **L2 + L4**.
2. **Diff as a set comparison, not an event log** (M3). Missing-on-left ⇒ delete; missing-on-right ⇒ create; hash-differs ⇒ update. A manifest comparison is self-healing: a dropped FS event, a crashed run, or a machine that was asleep for a week all reconcile on the next pass. Event streams (Graph webhooks, fswatch) should be treated as *hints that shorten the poll interval*, never as the source of truth — which is exactly the shape of Cursor's design: a 10-minute poll (M4) over a hash tree, not a watcher.
3. **Store the pointer, not the payload** (M12): per derived unit keep `source path + byte/line range + source hash`. That is what makes "which docs pages must be re-curated because source X changed" a lookup rather than a re-scan (the lead's page↔source dependency map, **L4**).
4. **Git as the "what changed since I last looked" layer is what Cursor does too** (M13) — commit SHAs + parent links indexed as a first-class structure, content deliberately excluded. Validates **L5**.
5. **One batched write per cycle**, and let freshness be *measurable* (turbopuffer's `unindexed_bytes`). The operator's analogue: one git commit per sync cycle with a machine-readable sync-state file (last token, counts, failures) — never a commit per file.
6. **Declared exclusion set in-tree** (M5, `.gitignore`/`.cursorignore` semantics) ⇒ `docs-source/.syncignore` checked into the repo, so the indexed population is reviewable.
7. **Near-duplicate reuse across corpora** (M8 + `copy_from_namespace`): the messy-version-suffix problem (`Deck v3 FINAL (2).pptx`) is Cursor's 92%-similarity case. A simhash/minhash over the chunk-hash set identifies "this is a re-upload of that file" *before* any conversion, letting the pipeline emit a supersedes-link rather than a second page.

**Does not transfer:**

- **The tree structure itself.** Its payoff is "don't ship the 3.2 MB manifest across the network" (M2) and "hashes as capability proofs" (M9). `docs-source` and `docs` sit on one filesystem: a **flat content-addressed manifest** (`path → {size, mtime, sha256}`, with mtime+size as the fast path and sha256 as the authority) is O(changes) for the same reason and is far easier to audit. Adopt a directory-rollup hash only if a *remote* peer must be diffed cheaply (e.g. a SharePoint/Graph mirror where you want to skip whole subtrees). *Theoretical.*
- **Path obfuscation (M10)** — it exists because a multi-tenant server holds other people's paths. Locally it destroys the thing the operator is optimising for (greppable, semantically-named paths). Its *residual* lesson is the inverse: because Cursor could only ever filter on an encrypted path, it had to buy natural-language retrieval with a trained embedding model. **A local corpus can spend that budget on naming and directory structure instead**, which is the cheaper and more inspectable of the two.
- **The embedding index at all, as a first build.** See §3's last row and M14.

## 6. Adversarial pass — the three places a Cursor-shaped design fails on *this* corpus

1. **A rename is not a move, and Cursor's own users feel it.** M3's set semantics turn a rename into delete+add; the file hash is unchanged so re-embedding is free (M7), but every path-keyed metadata row must be rewritten, and path is encrypted per-segment (M10) so there is nothing to "move". Observed in the wild: a user reports "Cursor's codebase search… seem to be using an outdated index. When I rename files or move functions, the AI still references the old structure", and Cursor staff answer with a manual rebuild — "Cursor Settings > Indexing & Docs > Delete Index > Compute index" ([forum.cursor.com/t/144970](https://forum.cursor.com/t/codebase-indexing-not-updating-after-file-changes/144970), Dec 2025). Cursor also concedes the pipeline drops work under load: "Our indexing feature often experiences heavy load, which can cause many requests to fail. This means that sometimes, files will need to be uploaded several times before they get fully indexed." *Empirical.* ⇒ **Design the docs pipeline so a rename is a first-class event**: detect it as `same content hash, different path` in the manifest diff (cheap, and something a flat manifest does *better* than a tree), and emit a `moved-from:` field in the page's frontmatter plus a stub redirect — never a silent delete+create, which would destroy the git history that L5 depends on. For OneDrive/SharePoint the Graph `driveItem` id is stable across renames and is the better key than the path.
2. **OOXML over-triggers a byte-hash.** `.docx/.xlsx/.pptx` are ZIP containers: re-saving, or a sync-client round-trip, rewrites compressed bytes and embedded timestamps with **no content change**, so a source-byte hash reports "changed" and a naive pipeline pays the full converter + curation cost. Cursor never hits this (source files are plain text). *Theoretical, but mechanical.* ⇒ The **post-converter hash (M7's layer) must be the gate on all downstream token spend**: `source_sha` decides whether to run the (cheap, deterministic) converter; `extracted_text_sha` / per-section hash decides whether to touch the markdown or re-curate. Keep both in frontmatter. This is also what makes "updated in place, same filename" and "re-uploaded as v2" collapse to the same cheap case.
3. **Poll-only cadence is a *bounded staleness* decision, and the bound has to be stated.** Cursor chose 10 minutes and still ships a manual "Compute index" escape hatch. ⇒ the operator's pipeline needs the same two things: a documented staleness bound, and a **forced full reconcile** command that ignores the manifest — plus a rule that any converter/prompt version bump invalidates the derived-hash namespace (Cursor's chunk cache has this hazard too: an embedding-model change makes every cached vector wrong, which is precisely why the cache key should include the *producer version*, not only the content hash).
