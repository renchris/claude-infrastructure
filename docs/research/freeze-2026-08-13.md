# The 2026-08-13 21:22:39 freeze — a no-panic wedge, and the reader that was blind to it

**Verdict.** The box wedged hard at **21:22:39 PDT while the operator was actively using it**, stayed
dead for 80 minutes, and was recovered by **holding the power button** at 22:42:29. It was **not** a
kernel panic, **not** sleep, **not** memory exhaustion, and **not** the VM-compressor segment class
that `compressor-sentinel.sh` was built for after the four panics of 2026-07-30 → 08-09. The trigger
itself is **unrecoverable from disk** — a forced power-off is a power cut, so nothing in flight ever
reached storage. What *is* recoverable, and what this incident changed, is that the machine now
records the event at all.

## What is established, with the artifact that proves each

| Claim | Evidence |
|---|---|

| **No panic was written** — the region was empty, not unreadable | At boot `DumpPanic` read 3,145,728 bytes of the NVMe panic region and found it **all zeros**; both SOCD paths returned no data. `ShutdownWatchdogEnabled = Yes`, so the watchdog was armed and simply never fired |
| **Not sleep** | `pmset -g log` records no sleep/wake between 21:21:58 and the 22:43 boot; machine on AC at 100% |

**Nearest matching prior incident:** 2026-07-30 ~21:53, the WindowServer/CoreAnimation lock-storm GUI

`grep`ping `scripts/` and `launchd/` for `windowserver` still returns nothing. This incident is that
class, not the guarded one.

## The defect this incident exposed, and the fix

`panic_scan()` globs `*.panic`. A forced power-off writes no such file, so it correctly reported
`none` — and **`panic-attribution.jsonl` recorded nothing at all** for the worst stability event
since the compressor panics. Its newest row is still the 2026-08-09 panic. The ledger built so that
"the next death is attributable" was structurally blind to a death that leaves no report, and
re-deriving the above by hand cost a full session of log forensics.

`freeze_scan()` (this diff) closes it. At the same startup moment as the panic reader, it:

- keys on the PMU's own `Boot faults:` line — `force_off`/`btn_rst` **is** the record that a human
  had to reach for the case, and nothing in software can fake it;
- **defers** on `wdog` and on a force-off that *did* leave a fresh report, so one death never becomes
  two incidents;
- reconstructs the **dark window** from the samplers' last pre-boot rows, and stores every sampler's
  final tick verbatim — the table above is exactly what a future row will already contain.

Replayed against tonight: `dark_minutes: 79.6`, `signature_source: "resetcounter"`, both
capacity-alarm's and the sentinel's last ticks captured.

**Two traps worth carrying forward,** both found by running the reader against the live machine
rather than by reading it:

1. **`.*sec = ` is greedy and matches `usec = `.** `kern.boottime` is
   `{ sec = 1786686149, usec = 597125 }`; the first draft returned **597125** as the boot epoch — all
   digits, every type check passed, wrong by fifty-six years. Anchored at `^{` now, with a
   plausibility floor of 10⁹ as the guard for the *next* format change.
2. **`kern.shutdownreason` carries an `ap_panic` token on a boot where no panic occurred**
   (`btn_rst,finger_reset force_off ap_panic`). Classifying on the sysctl alone calls this freeze a
   panic. The dated `.diag` is per-incident and does not lie; both are stored raw so a later reader
   can re-adjudicate rather than inherit this one's reading.

## What would make the next one diagnosable

The freeze reader gives the *boundary* and the last 60-second sample. It cannot give the last
*second*, because a power cut loses whatever never reached disk. Closing that would need a
higher-resolution, fsync'd pre-freeze ring buffer — and the honest prerequisite is a second data
point, which this ledger now guarantees we will have.

## 2026-09-09 — the ledger said two, the machine had frozen once

The section above closes on a promise: the ring buffer's *"honest prerequisite is a second data
point, which this ledger now guarantees we will have."* Twenty-six days later the ledger holds **two
`kind:"freeze"` rows** — and they are **one incident**.

| | row 1 | row 2 |
|---|---|---|
| recorded | 2026-08-14T06:48:44Z | 2026-08-22T04:28:33Z |
| `boot` | 1786686149 | **1786686150** |
| `signature_source` | `resetcounter` | `kern.shutdownreason` (the fallback, whose `ap_panic` token lies) |
| `reset_report` | the dated `.diag` | *empty* |
| `dark_minutes` | 79.6 | *null* |
| `last_ticks` | both samplers | `{}` |

One second of `kern.boottime` jitter, and the exact-match dedupe re-recorded the 2026-08-13 wedge as
a fresh incident eight days later — degraded in every field, because by then the `.diag` had aged out
of `freeze_boot_faults`' 120 s floor and the samplers had no pre-boot row left to find. `9d5e64de7`
made `freeze_boot_already` tolerant to ±5 s and stopped the *next* duplicate. It did not, and should
not, retract the row already written: this store is append-only.

**So the count and the truth diverged permanently, in the direction that ends the wait early.**
`grep -c '"kind":"freeze"'` answers **2** for a box that has frozen **once** — and 2 is exactly the
threshold this section set for designing the ring buffer. The next reader to ask "do we have the
second data point yet?" gets *yes*, and designs a high-resolution sampler against a sample of one.
That reader was this session, for the first twenty minutes.

`compressor-sentinel.sh --freeze-incidents` now answers the question that was actually being asked.
It clusters rows on the **same ±5 s rule `freeze_boot_already` dedupes with** — reused, not restated,
because two spellings of "is this the same boot" that can drift apart is a defect this repo has
already paid for twice. Against the live ledger it prints **1**.

**The prerequisite is therefore still unmet, and n = 1 stands.** The box has been up since
2026-08-25 (`kern.boottime` 1787642176), so there has been no boot at which a second freeze could
have been captured. Nothing about the 2026-07-30 lock-storm class has changed either: `scripts/` and
`launchd/` still hold **no detector** for it — today's `windowserver` grep hits are CPU-accounting
comments in `capacity-admit.sh`, `spawn-presence.sh`, `render-census.sh` and `handoff-fire.sh`, not a
sensor. The item's conclusion holds; only its stated grep has gone stale as a test.

What changed is that the wait is now **self-terminating rather than permanent**. Backlog row
`dabe706c9d79` carried no falsifier, so no probe connected a future freeze row to the item that was
waiting for it — the ledger's "guarantee" was real and nothing read it. The row now carries

```
[ "$(bash "$HOME/.claude/scripts/compressor-sentinel.sh" --freeze-incidents 2>/dev/null)" -ge 2 ]
```

which exits 1 today and 0 on the first genuinely distinct second incident, both arms measured rather
than assumed. **The design question is unchanged and still correctly deferred; what was broken was
the instrument that decides when the deferral ends.**

## 2026-09-09 (second pass) — the falsifier prescribed above is INVERTED, was never written, and its probe is inert

The section above ends by declaring the wait *"self-terminating rather than permanent"* on the
strength of a probe it says the row now carries. Re-read from trunk against the live stores, that
remedy has **three independent defects, and none of them announces itself.** The first is the one
that matters: had the probe been written as prescribed, the second freeze would have **deleted** the
item it was supposed to release.

### 1. The polarity is backwards — a passing falsifier RETRACTS

`cc-backlog`'s `cmd_falsify` header states the contract in its own words:

> run_falsifier's contract is deliberately asymmetric: non-zero is advisory (the item proceeds),
> **exit 0 RETRACTS.**

A falsifier answers *"is this item still real?"* — exit 0 means **dead, close it**. The prescribed
probe

```
[ "$(… compressor-sentinel.sh --freeze-incidents)" -ge 2 ]
```

exits 0 exactly when the second freeze **arrives** — i.e. at the moment the deferred design work
becomes *doable*. `cc-premise sweep --close-falsified` would then run `cc-backlog done` on it. Its
candidate filter skips only `done` and (with one structural exception) `claimed` rows: **`blocked` is
not skipped**, so parking the row first would not have saved it either.

So the probe is not weak coverage, it is a **loaded retraction of the exact event it waits for**.
This is the repo's own `falsifier-polarity-inverted-under-no-run` class, in the direction that costs
the work rather than a re-run: the ledger reaches n = 2, the sweep closes the row citing
`falsifier passed`, and the detector nobody has built stops being asked for.

### 2. It was never written — claimed, not checked

*"The row now carries"* describes an intended write. `grep dabe706c9d79 ~/.claude/autonomy/backlog.jsonl`
returns **six records and zero `falsify` events** (the store holds 1,037 of them elsewhere, so the
verb works and was simply never run here). `cc-backlog list --json` folds the row with no
`falsifier` field. The harm above is therefore **latent, not live** — this pass is the one that gets
to decide, and it decides not to write it.

### 3. The probe's dependency is not in the live layer, and the failure is silent

`--freeze-incidents` is on trunk (`scripts/compressor-sentinel.sh:288`) and prints `1` from a
current worktree. The probe as written calls the **durable** path, which is the symlink into the
shared checkout — and that checkout sits 7 commits behind trunk:

```
$ bash "$HOME/.claude/scripts/compressor-sentinel.sh" --freeze-incidents
compressor-sentinel.sh: unknown arg '--freeze-incidents'      # rc 64, EMPTY stdout
```

`[ "" -ge 2 ]` is not false, it is a **bash error** — which `if` cannot distinguish from false
(memory: `predicate-error-exit-is-indistinguishable-from-false`). A landed-but-not-live dependency
therefore renders the probe permanently "not yet", silently, which is the *permanent* wait the
section above believed it had abolished. Same `🚀` lesson as
`durable-path-in-a-generated-launcher-executes-the-live-layer`: a durable path executes the live
layer, whatever the worktree that composed the call could do.

### What was actually wrong, and what this pass changed

The row is a correct `not-yet-true` deferral — re-verified: `--freeze-incidents` still reads **1**,
and `scripts/` and `launchd/` still hold no sensor for the 2026-07-30 lock-storm class (the
`windowserver` hits remain CPU-accounting comments). Nothing about the design question has changed.

What was broken is narrower and purely mechanical: **a correctly-deferred row has no way to say "not
yet" to the dispatcher.** `cc-dispatch` keeps only `status == "open"` (its own selftest case (k)),
so the previous pass's `reopen` at 11:49:10Z put it straight back in the wave; it was re-claimed at
13:05:24Z and burned a second worker slot on a question whose answer had not moved. That loop, not
the missing probe, is what this item was costing.

This pass therefore:

- **does not write the falsifier** — an absent falsifier is honest, and every probe available here
  retracts in the wrong direction;
- **parks the row `blocked`**, the only status that leaves the dispatch wave, with a `--needs` that
  states the external event plainly and the one command that re-tests it, so re-entry is a read
  rather than a memory;
- records the polarity trap here, because the prescription it replaces is written on trunk in the
  imperative and the next reader would have executed it faithfully.

**The prerequisite is still unmet and n = 1 still stands.** The difference is that waiting now costs
nothing per wave instead of one worker slot.
