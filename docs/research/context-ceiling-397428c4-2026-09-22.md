### 5.1 The payload (MEASURED)

29 `<task-notification>` payloads, delivered as `queued_command` attachments (key `prompt`, `commandMode: task-notification`), each carrying `<output-file>` (the harness's persisted copy under `…/tasks/<task-id>.output`) AND the full `<result>` inline:

### 5.2 Verdict: earned at the wrong tier

- **The subagents' work was real.** `<usage>` blocks: **7,477,818 tokens** spent across 28 notifications (mean 267 K each), 1,501 tool uses, 174 minutes of aggregate agent time — against the lead's 1 M window. The design put the heavy reading where it belongs.
- **The lead's own output was modest.** 226,656 output tokens over 200 calls, of which the resident text + tool_use is 445,904 chars (17 %); the `.cjs` stages and merge maps are the lead's legitimate synthesis.
- **The return was the defect.** A subagent's final message is delivered in full, so "return one JSON object" put 42 K chars per agent into the window that the lead then re-read from a file. The two critics show the floor: a pointer-shaped return costs < 1 K. Had all 29 returned pointers, the payload term falls from ~450 K to ~10 K tokens and the session peaks near **55 %**.

So H3 is confirmed as the dominant term and the finding is the opposite of H1/H2's: **no Stop hook could have saved it, and the defect is architectural** — in the Agent tool's delivery contract as this fleet uses it, and in the resident rule that describes that contract backwards (§ 6.2).

### 5.3 What "parallelize more" would and would not have done

This session was itself the dispatched, parallelized locus (fired peer `cf-reso-actions-500`); the originator's window was protected exactly as § Agent Teams intends. A second level of dispatch — verification wave in its own session — would have saved it, and that is what § 9 P1's refusal text names. More subagents on the same lead would have killed it sooner.

## 6. H4 — the `CLAUDE.md` gap

### 6.1 The exemption is not the gap

*"Read-only research fan-out is unaffected — subagents return findings, not implementations."* This sentence is about WHOSE window the wave runs in, and it was honoured: the wave ran in a dispatched session. What it does not say — and what no resident rule says — is that **a fan-out lead is itself a lead**: its subagents' returns land in ITS window in full, and the size of that landing is knowable at spawn time. The missing rule is not "dispatch the synthesis too" (the synthesis here was small: 34 decisions, four `.cjs` stages ≈ 90 K tokens); it is two mechanical bounds:

1. **Return size**: a research subagent returns a POINTER; the payload goes to the file its field-7 delivery path names.
2. **Spawn fill floor**: no subagent spawn past a fill threshold, or when the in-flight returns cannot fit.

### 6.2 The skill's premise is inverted for the case that matters (MEASURED on 2.1.260)

`skills/research-subagents/SKILL.md:228`: *"🚨 A subagent's prose is invisible. Only a file is delivered."* — repeated by `hooks/agent-teams-enforce.sh:688` and by the `research-precognition-nudge` UserPromptSubmit hook on every prompt. For an UNNAMED in-process subagent this is backwards: the prose is delivered **in full**, as the `<result>` of a `task-notification`, and that is precisely the cost. The rule is right for NAMED teammates (the enforce hook's own lifecycle advisory: *"Leave it UNNAMED and the identical work runs in-process, returns through a task notification"*), and the 2026-08-05 incident it cites ("4 of 5 agents lost their reports") is consistent with named members. The skill conflates the two, and a lead reading it has no reason to bound the return. INFERRED: the observation that produced the rule predates the current delivery path or was made on named agents; not re-measured on older binaries here.

### 6.3 Block count vs fill floor

The resident rules already record that `CLAUDE_CONTINUE_MAX` bounds only the mechanical arm and that a re-arming chain never trips a cap (0 trips in 11 days vs one chain of 311). A count cap would not have helped here: the 8th block landed at 06:02:25 at 58 % fill, and releasing that Stop changes nothing — the model re-arms with a fresh `set` (which zeroes the counter, by design), or simply takes the next notification. **The bound that was missing is a FILL floor, and it has to sit on the actuator that owns the turn** (`session-continue.sh set` refusing past the floor) **and on the act that commits the future** (the spawn). A floor on the advisory hook alone is what we have today, and it abstains whenever the chain is armed.

### 6.4 Where the rule should live

Not in `CLAUDE.md` prose. Prose is tier 1 of the three tiers the lead measured (a description read once, competing with 220 K chars of other instructions; a front-door command that dispatches; a refusal at the act). Everything in § 9 is tier 3.

## 8. The third deliverable — "how do we make this deterministic rather than recommended?"

The specimen (measured by the lead, cured narrowly on branch `cc-lr-routing-refusal`): the limit-recover command's description was widened in PROSE to *"USE IT FOR EVERY NON-QUOTA INTERRUPTION TOO, because the audit engine was never limit-specific — only this description was"*. The PREDICATE at `cc-lr:214` was not widened. At the act, the refusal won and the doctrine lost — the model read the correct rule in the description, met the tool's refusal, and improvised a false fact about the world from it.

### 8.1 The generator, named

Steer-then-backstop (`cc-unattended-ask-guard.sh`: *"the executable half of what was, until now, prose-only"*) was never applied to the recovery path **because the recovery path already had a backstop-shaped surface**. `cc-lr` refuses; a refusal reads as enforcement. Nobody asked whether the EXISTING enforcer agreed with the WIDENED claim, because the pattern as shipped pairs a doctrine with a NEW gate — it has no step for "a doc change that contradicts an old gate". The defect class is therefore **drift between a claim and its enforcer**, not absence of an enforcer, and a lint that only checks "does an enforcer exist" would have passed this specimen.

This is the same shape as § 3.2 (the compose-guard was a fix that became the suppression) and § 6.2 (a rule true for one agent class, inverted for the other). Each time, the prose and the predicate were written by different hands at different times and nothing linked them.

### 8.2 The parity lint — design

**Name:** `claim-enforcer-parity-lint` (shape of `tests/deploy-parity.bats`, which pins an ABSENCE; `tests/effort-parity.bats`; `tests/bats-shim-parity-lint.bats`, whose NO-DATA is rc 3, never folded into 0).

**(a) The admissible claim class — a grammar, not a sentiment.** A sentence in `commands/*.md`, `skills/*/SKILL.md` frontmatter/description, or `hooks/*.sh` header prose is a BEHAVIORAL CLAIM iff it predicates one of two machine-checkable behaviours of a named executable:

| class | grammar (regex over the sentence, entry point resolved from the doc's own frontmatter or first `bin/`/`scripts/`/`hooks/` reference) | what the enforcer must do |
|---|---|---|
| **C1 ADMISSION** | `\b(use (it|this) (for|when)|also use|handles|covers|accepts|recovers?)\b … <input class>` | drive the entry point with a fixture of that input class and assert it is **not refused** (exit code / structured field) |
| **C2 REFUSAL** | `\b(refuses?|denies|blocks?|never|is refused|abstains?)\b` … naming an executable, flag, env or exit code in backticks | attempt the act against a fixture and assert the refusal (exit code, `decision`, `verdict=` token — never a grep for prose) |

Everything else is DOCTRINE and the lint **abstains** on it, counted. This is defensible because both classes are precisely the ones whose truth is an exit code, and the specimen is C1 (the description claimed admission of a non-quota interruption; no fixture ever drove one through `cc-lr`).

**(b) What counts as an enforcer.** An executable artifact that (i) drives the NAMED entry point, not a re-implementation of its logic (`memory: make-the-actuator-the-arbiter`); (ii) with a fixture of the claimed input class; (iii) asserts by exit code or structured field, never by phrase; (iv) is WIRED — a `@test` selected by `ship-land`'s gate, or a hook whose registered `settings.json` path resolves to the current file (registration, not executability: `docs/lessons`, `registration-precondition-must-assert-version-not-executability`). A refusal string inside the tool's own source is NOT an enforcer of a description claim — it is the thing the claim is about. **Linkage is explicit, never inferred:** each C1/C2 sentence carries an adjacent machine-readable anchor, `<!-- enforcer: tests/<file>.bats::"<test name>" -->`, and the lint resolves it. No NLP guesses which test "covers" a sentence.

**(c) Discriminating power, reported by the run itself.** Two measures, printed every run, per the saturation lesson (`docs/lessons/a-rubric-that-saturates-has-not-ranked-anything.md`):

- *Claim tier*: sentences scanned · C1 · C2 · doctrine (abstained) · anchored · unanchored · waived — and the max-bucket share. `doctrine ≥ 95 %` means the grammar caught nothing (a dead lint); `unanchored ≥ 80 % of claims` at rollout means the lint will be satisfied by anchoring trivially.
- *Enforcer tier — the mutant.* For every anchored claim the lint runs the anchored `@test` once more with the entry point shadowed on `PATH` by a stub that inverts the claim (C1: refuse everything, exit 2; C2: accept everything, exit 0). **The test must go red.** A test that survives its mutant does not drive the entry point on that axis and is DECORATIVE; the lint fails it by name. Printed: `mutants killed / anchored`. This is what stops the anchor from being a rubber stamp — an anchor to a test that would pass either way is caught at lint time, mechanically. (Shape: `docs/lessons/green-in-both-arms-is-an-equivalence-guard-not-a-red-proof.md`; the stub must carry a shebang, `docs/lessons/a-shebang-less-stub-seals-only-the-shell-arm.md`.)

**(d) False-positive budget and kill switch.** A RATCHET, not an absolute: the baseline count of unanchored C1/C2 claims is recorded at adoption (`tests/fixtures/claim-parity.baseline`); a land fails only if the count INCREASES or a mutant survives. Explicit waivers `<!-- enforcer: none — <reason> -->` are counted and rendered, never silent (a waiver is a filed row). Rollout: shadow mode (report only, rc 0) for one week of lands, then gating. Kill switch `CC_CLAIM_PARITY_LINT=off`; NO-DATA (no docs matched, grammar file missing) is rc 3, never 0. Expected first-run histogram, INFERRED from a skim of `commands/limit-recover.md`: ~10–20 C1/C2 sentences per large command doc, the rest doctrine — the lint has variance to work with; if a first run shows otherwise, that number, not the design, is the finding.

**Why the specimen is caught:** the widened description sentence matches C1 (`USE IT FOR … TOO`), carries no anchor → unanchored count rises by one → land fails, naming the sentence and the entry point (`bin/cc-lr`). The fix that satisfies the lint is a bats case that feeds a context-death transcript to `cc-lr` and asserts it is not refused with "not LIMITED" — which is the exact test whose absence produced the incident.
