# What actually caps concurrent sessions on this box — and the path to 150+

Measured 2026-08-09, worktree `scale-150`, on the live 10-core (M1 Max, 8P+2E) / 64 GiB box.
Method note: every number below is a live read taken this session unless marked `[D]` (repo doc) or
`[I]` (inference). Instantaneous CPU is `top -l 2` **second sample** — `ps -o pcpu` is a *lifetime
average* and is the wrong instrument for bursty daemons, which is how the prior model went wrong.

---

## 1 · The answer

**The binding constraint is runnable-thread pressure produced by the fleet's own tooling fork rate —
roughly 50 forks/second per active session — and the admission gate keys on exactly that number.
Claude inference is not the load, the filesystem is not the load, and memory is not the load.**

Measured, at 12 live sessions: **676 forks/sec** system-wide (3 trials: 685 / 648 / 695). At ~25
active agents earlier in the session: **~1,130/sec**. That is ~50 forks/sec/session of `bash → timeout
→ bash → git/jq/grep/sleep` chains — hooks, statuslines, `$( )` substitutions, pollers, reapers.

Every fork is kernel-heavy: fork+exec, dyld, sandbox evaluation, and a Gatekeeper/XProtect
code-signing assessment. That is why the box runs **43.9% sys time against 44.9% user** (20 samples)
— half of this machine's CPU is in the kernel servicing process creation, and `XprotectService`
averages **31.0%** (peak 101.3%), roughly 3× fseventsd and 2.6× Spotlight combined.

Darwin's load average counts **runnable threads only** — never disk-wait. Verified against XNU
`osfmk/kern/sched_average.c`: the sampled quantity is `sched_run_buckets[TH_BUCKET_RUN]` fed through
an EWMA. Thousands of short-lived runnable threads per second on 10 cores is precisely what produces
load 18–20 while no individual process looks busy.

So load average is **not** a broken signal — it is faithfully measuring the fork storm. The defect is
that the fork storm is generated by *tooling overhead*, not by useful work, and the gate therefore
refuses new sessions because the existing sessions' hooks are noisy.

## 2 · What was refuted (the brief's premises, tested)

### 2.1 Spotlight indexing of `~/Development/.worktrees` — REFUTED, and the lever is a no-op

The decisive test is a per-directory index census, not `mdutil -s` (which returns "unknown indexing
state" for any path that is not a volume root — that message means *"not a volume"*, not *"unknown"*):

| Directory | Indexed `*.md` files |
|---|---|
| `~/Development` | **116,601** |
| `~/Documents` | 2,149 |
| `~/Development/claude-infrastructure` | 337 |
| **`~/Development/.worktrees`** | **0** |
| `~/.claude` | **0** |

Both dot-directories return zero while their non-dot siblings return thousands. **Spotlight does not
index dot-directories.** `~/Development/.worktrees` is *already* excluded, by construction, for free.

⇒ Lever 1 in the brief (`mdutil -i off` / `.metadata_never_index` / `.noindex` on the worktrees tree)
has **zero available gain**. It cannot be the biggest win; it cannot be any win. Do not stage it.
(It would also cost nothing to break, since nothing there is findable today — but there is no
upside to buy with that.)

*Caveat, and it is a real one:* `~/Development` proper **is** indexed with 116,601 `.md` files
(node_modules across every project). That is a standing Spotlight cost, but it is not the *churning*
tree and it is not what the brief targeted.

### 2.2 "Load is disk-wait" — REFUTED at the mechanism level

The brief states *"Load average on macOS counts uninterruptible I/O wait."* That is Linux semantics
(`TASK_UNINTERRUPTIBLE`) applied to XNU. XNU has no uninterruptible term. Corroborated live: only
1–7 U-state processes exist at any instant — even if they counted, they could not move a load of 20.

### 2.3 FS churn as the load source — REFUTED by controlled A/B

The brief's own prescribed decisive test, run at constant session count (11 sessions throughout):

| Phase | Condition | Load (6 samples, mean) |
|---|---|---|
| A | quiesced — no FS walk | **18.13** |
| B | active `find` over all 382 worktrees | **18.94** |
| C | recovery | 18.39 |

**Δ = +0.81 load units (+4.5%)** — noise, against a load that swings 2.05× at constant session count
`[D: MACHINE_CAPACITY_V2.md §9.5]`. A full walk of the 200 GB tree is not measurably a load source.

**Correction to my own earlier inference:** mid-session I observed load fall 38 → 11 as a `du` on the
worktrees finished, and read that as causal. It was not. Six research subagents — full Claude sessions
doing active tool work — started and finished across the same window. The controlled test above
isolates the walk and finds nothing. The load-38 excursion was *agent fork traffic*, which is the same
conclusion §1 reaches by a different route.

### 2.4 Memory — the brief's numbers are wrong in both directions

- The brief's **"33.7 GB free"** is wrong: live `top` reads 56 G used / **6.4 G unused** / 4.6 G
  compressor, with **1.14 GB swap in use** and 11.7 GB of data held compressed. The sampler shows
  unused RAM declining monotonically (4588 → 4115 MB) across the run.
- The brief's **"546–986 MB per session"** is also wrong — it is `ps` RSS, which double-counts the
  ~992 MB of shared read-only libraries once per session. Against `vmmap` **phys_footprint** (agreeing
  with `top`'s MEM column to within a few MB on 4/4 processes), the truth is **216 MB fresh, median
  232 MB, mean 283 MB, max 548 MB at 26 h**. 19 sessions = **5.25 GB actual, not 12.9 GB RSS**.

Both errors point the same way: **Claude's memory cost is ~2.5× smaller than believed, and the box's
free memory is ~5× smaller than believed.** The non-Claude baseline — Dia (24 helper processes,
5.0 GB), Chrome, WindowServer, kitty (1.6 GB) — is the memory hog, not the session fleet.

This also vindicates the repo's own prior figure of *"215 MB and 0.036 cores per session"*
`[D: TERMINAL_AGNOSTIC_L3_L4.md:42]`, and invalidates the two published capacity ceilings that were
built on `ps` RSS (`~50 sessions` `[D: MACHINE_CAPACITY_V2.md:63]`; *"100 local sessions is not
reachable"* `[D: concurrency-census-2026-08-07.md:11]`). Both used the exact instrument that
`capacity-alarm.sh:23` bans in-source. Corrected, RAM permits far more than either claims.

### 2.5 Terminal render — UNDER-stated by 5×, not over-stated

The brief measured 7.9% and concluded this was a small lever. Under real streaming load across 20
samples: **mean 42.2%, peak 55.5%** (WindowServer + kitty) — **0.42 cores**, and rising with pane
count. That is ~43% of what all Claude processes consume combined. It is a *real* lever, not a small
one. (Separately `[D: terminal-config-30-sessions-decision-2026-07-30.md]`: iTerm2's Metal renderer
hard-disables at **≥6 panes per tab**, disassembled from the shipped binary — a display ceiling
orthogonal to compute.)

## 3 · Where the CPU actually goes

20 samples, ~6 minutes, 13–19 live sessions, instantaneous `top`:

| Term | Mean %CPU | Min | Max | = cores |
|---|---|---|---|---|
| **All Claude sessions combined** | **99.2** | 55.3 | 139.0 | **0.99** |
| kernel_task | 44.6 | 27.6 | 65.6 | 0.45 |
| Terminal render (WindowServer + kitty) | 42.2 | 28.1 | 55.5 | 0.42 |
| XProtect + syspolicyd | 31.0 | 4.0 | 101.3 | 0.31 |
| Spotlight (mds/mdworker) | 11.9 | 1.0 | 65.6 | 0.12 |
| fseventsd | 11.3 | 0.5 | 60.2 | 0.11 |
| *CPU idle* | *11.3%* | *0.2%* | *45.9%* | — |

Claude at ~17 sessions = **0.058 cores/session** — the brief's "0.8 cores, all sessions" is directionally
right and is the one premise that survives. But note idle bottoms out at **0.2%**: the box *is*
saturated much of the time, just not by Claude. kernel_task + XProtect + syspolicyd — all three driven
by process creation — together exceed Claude's entire footprint.

## 4 · The gate is refusing on the right measurement for the wrong reason

| Fact | Value |
|---|---|
| Formula | `REFUSE ⟺ (vm.loadavg[1min] / hw.ncpu) > 2.0` — `capacity-admit.sh:186` |
| Refusals ever, from the **load** term | **127 of 127** |
| Refusals ever, from the **memory headroom** term | **0** |
| Gate-reported headroom, live | **29.79 GB** |
| Actually unused RAM, same moment | **6.4 GB** (+ 1.14 GB swap already in use) |
| Memory floor | 4 GB (gate) · WARN 8 GB / ALARM 3 GB (alarm only — pages, never refuses) |

Two defects, both consequential:

1. **The safety line cannot fire.** Headroom is computed as
   `free + speculative + inactive + purgeable`. `Pages inactive` (18.5 GB here, **62% of the reported
   headroom**) includes *dirty anonymous* pages, whose reclaim path is compression and then swap. The
   gate is structurally blind to the compressor, to `vm.swapusage`, and to memorystatus pressure. A box
   compressing 11.7 GB and swapping reports 29.79 GB free to the admission gate — 7.4× above a floor it
   can therefore never reach. **The memory floors are the stated real safety line and they are inert.**
2. **The gate's ceiling sits below the box's resting load.** Measured resting load at 11–13 sessions is
   **17.6–20.0 = 1.76–2.00/core**, against a 2.0 ceiling. The box is at or over its own admission
   ceiling with a dozen sessions running. Refusal is terminal — `exit 9`, no queue, no wait.

Per the brief's constraint I am **not** changing any default. The evidence-backed proposal is §6.

## 5 · Off-box is the only arithmetic path to 150 — and it is not built

`cc-sessions` lists 12+ `offbox` rows, which reads as an existing capability. It is not one yet:

- **The fire path has no create.** `handoff-fire.sh --cloud` parses the flag, gates it default-off,
  and prices it against account headroom — then never invokes a create, never calls `cc-cloud declare`,
  never touches the claude binary.
- **Zero off-box sessions have ever executed.** Across 17 declared sessions on ≥2 accounts, the number
  that pushed any ref, opened any PR, or produced any remote-visible artifact is **zero**;
  `git ls-remote --heads origin` returns exactly one head, `refs/heads/main`.
- The observed states bear this out: of the rows visible now, most are `NOT-STARTED` or `ABANDONED`.

The surrounding machinery is real and tested (account scoping, reconcile, landing, eligibility
predicate, ceiling probe). Creates *do* succeed from a script with a pty and a retry (~50–75% per
attempt). What is missing is the one step everything else sits downstream of. This matches the
repo's own recent conclusion `[D: commit dc5bf230, "the next step is the create, not the GitHub App"]`.

**Off-box genuinely costs this box zero CPU, zero RAM and zero fork traffic** — so it is the correct
primary path. It is simply a *build*, not a *config change*.

## 6 · Levers, ranked by measured effect

| # | Lever | Measured effect | Verdict |
|---|---|---|---|
| 1 | **Cut forks/session in the hook + statusline path** | ~50 forks/s/session is the binding term; 10× reduction moves the local ceiling ~10× | **Highest local lever.** Not yet attempted. |
| 2 | **Build the off-box create** | Removes 100% of per-session local cost | **Only path to 150.** Blocked on one missing step. |
| 3 | **Headless / non-TUI sessions** | Render = 0.42 cores at ~17 panes ⇒ ~3.7 cores at 150; also dodges iTerm2's ≥6-panes-per-tab Metal cliff | Real, 5× larger than the brief assumed |
| 4 | **Fix the memory floor to read compressor + swap** | Restores the only safety term that can bound RAM; currently inert (0/127 firings) | Safety, not capacity — but it is the line that must survive §6.2 |
| 5 | **Replace/augment the load term** (see §6.2) | Gate refuses at the box's resting load today | Proposal only; operator decides |
| 6 | Worktree `node_modules` / shared store | Disk already ruled out — 116 GiB = 1.56% of volume, 44× free `[D: WORKTREE_MANAGEMENT_V2.md]`; FS walk = +4.5% load | **Low.** Not a capacity lever. |
| 7 | Spotlight exclusion for `.worktrees` | **0 indexed files — already excluded** | **No-op. Zero gain.** |
| 8 | `taskpolicy -c background` for sessions | **84–89× tax**; confines to 2 E-cores; "does not yield politely, it fails to finish" `[D: cc-bats:28-37]` | **Rejected — already measured and reverted.** `utility` (PRI 20) costs 2.4×. |

### 6.2 The admission-signal proposal (evidence, not a change)

Load average is measuring something real, so it should not simply be discarded. The defect is that it
conflates *useful concurrency* with *tooling overhead*. A better admission predicate, in priority order:

1. **A memory term that can actually fire** — `free + purgeable` only, plus an explicit refusal when
   `vm.swapusage.used` is rising or compressor occupancy exceeds a threshold. This is the real safety
   line and today it is inert. It must be fixed *before* any load ceiling is loosened, or loosening the
   load term removes the only backstop that is currently firing at all.
2. **A Claude-specific CPU term** — sum of `claude.exe` CPU ÷ ncpu. Measured 0.058 cores/session, so a
   ceiling of, say, 6.0 cores admits ~100 sessions on compute while still refusing a genuinely busy box.
3. **Keep load as a *secondary* term with a raised ceiling**, since it is the only signal that sees
   fork-storm pathology — but at a ceiling above the box's resting 1.76–2.00/core, or it refuses at
   idle.

Every one of these needs a test plus a mutation check per the brief's constraint 4. None is staged
here; the operator decides the numbers.

## 7 · The honest ceiling

**Local, as the box is configured today:** ~**12–15** sessions, because the gate refuses at a resting
load the fleet's own tooling already produces. This matches the operator's observed ~15.

**Local, with lever 1 + 3 (fork reduction + headless):** bounded by, in order —

| Bound | Arithmetic | Ceiling |
|---|---|---|
| CPU (Claude only) | 0.058 cores/session × N ≤ ~8 usable cores | ~**140** if all thinking simultaneously; higher with realistic duty cycle |
| RAM (phys_footprint) | 283 MB mean × N + ~20 GB non-Claude baseline ≤ 64 GiB | ~**155** — *if* the browsers are closed; Dia alone holds 5.0 GB |
| Fork rate | 50/s/session × N; box is at load ~19 with 676/s today | **~25–40** unless lever 1 lands |
| Render | 0.42 cores at 17 panes ⇒ ~3.7 cores at 150 | forces headless well before 150 |

⇒ **The fork rate is the binding local term, and it caps the local box at roughly 25–40 sessions even
after the memory and CPU myths are corrected.** 150 concurrent local TUI sessions is **not achievable
on this hardware** — not for RAM reasons (RAM allows it) and not for inference-CPU reasons (CPU nearly
allows it), but because ~7,500 forks/second of tooling overhead and 3.7 cores of terminal rendering are
not survivable, and iTerm2's renderer gives out at 6 panes per tab regardless.

**150+ requires off-box, which requires building the create step.** That is the single highest-value
piece of work identified here, and it is one missing call on a path where everything downstream is
already built and tested.

## 8 · Unknowns / not established

- **Fork attribution is inferential.** ~50 forks/s/session is measured; *which* hooks dominate is not.
  Exact attribution needs `sudo dtrace -n 'proc:::exec-success'` or `spindump` — both require sudo,
  skipped per constraints. This is the highest-value next measurement, because lever 1 is sized by it.
- **`powermetrics` skipped** (needs sudo). `pmset -g therm` is clean and the chip is Apple Silicon
  (frequency-scaling, not the Intel kernel_task-spin mechanism), so thermal throttling is *not
  indicated* — but not positively excluded at the frequency level.
- **Duty cycle unmeasured.** Every CPU ceiling above assumes simultaneity. Real sessions idle while
  waiting on the API; the true concurrent ceiling is higher than the arithmetic by an unmeasured factor.
- **My own subagents contaminated the early samples** (6 concurrent research agents, plus a `du` at
  30–34% CPU). The §2.3 controlled A/B and the §3 table were taken to isolate this, but the first
  sampler decile is inflated.
- The 2.0/core ceiling has already survived one retract-and-restore cycle `[D: MACHINE_CAPACITY_V2.md
  §8.5.2 → §9.5]`. **Do not re-litigate it from a single window** — that document's own closing lesson
  is that loadavg swings 2.05× at constant session count.

## 9 · Addendum — independent corroboration and the worktree census

The Spotlight refutation in §2.1 was reproduced independently, by a different method, on a different
control set: `mdfind` returns **0** for every query under `~/Development/.worktrees` while returning
459 / 11,760 / 76,898 hits on three control paths. Two independent measurements, same verdict.

**The 200 GB is not where the worktree count is** (all 382 measured, parallelised walk):

| Parent repo | worktrees | % of dirs | GB | % of GB | FS entries | % of entries |
|---|---|---|---|---|---|---|
| reso-management-app | 71 | 18.6% | **141.3** | **70.5%** | **6,602,899** | **73.6%** |
| doc_classifier | 59 | 15.4% | 39.3 | 19.6% | 1,795,848 | 20.0% |
| claude-infrastructure | **236** | **61.8%** | 16.8 | 8.4% | 388,129 | **4.3%** |
| orphaned (no `.git`) | 9 | 2.4% | 0.4 | — | 7,426 | 0.1% |
| **TOTAL** | **382** | 100% | **200.4** | 100% | **8,968,869** | 100% |

Two things follow. First, **this repo's own 236 worktrees — 62% of the directory count — are 4.3% of
the inodes.** The mass is 71 `reso-management-app` trees at ~93k entries each (`node_modules`). So even
if FS pressure *were* the constraint (§2.3 says it is not), pruning claude-infrastructure worktrees
would be aiming at the wrong 62%.

Second, a method correction worth keeping: **the brief's `du -sh` 120-second timeout does not
reproduce.** Parallelised (`xargs -P 12`, per-item `timeout 60`), all 382 completed in under 200 s with
zero timeouts. Serial `du` over a 9-million-entry tree is what hangs — not the tree. The hazard in
constraint 5 of the brief is real but its cause was misattributed, and the "200 GB is pathological"
framing rests partly on that timeout.
