# Verify the memory cost model, and settle cap-vs-recycle

*Axis `cost-model` of the context-economy 100th-percentile assessment `wf_5e9f820e-438`. Verdict: [`../context-economy-100p-2026-08-11.md`](../context-economy-100p-2026-08-11.md).*

**At 100th percentile:** `PARTIAL`

**Verdict.** The operator's no-cap position is correct and now measured — but for a stronger reason than the brief assumed: the published 0.343 MB/K-token coefficient overstates the real context term by ~6-8x (causally measured at 0.027-0.06, panel-measured at 0.10-0.15), the window SETTING costs 0 MB at zero fill, and the dominant per-session memory term is neither tokens nor age but per-session activity residue that ONLY a process restart clears — which a cap cannot touch and a recycle zeroes.

**Load-bearing claim.** A static window cap is not "equivalent-or-worse" to recycling — it is nearly worthless: the entire context term at a FULL 1M window is 27-45 MB (measured), not the 343 MB the repo publishes, while the term that actually explains today's 810 MB of fleet excess is activity residue that only a process restart (i.e. a recycle) can reclaim.

**Shortest fix.** Correct one number in three places and the conclusion follows by itself: replace the 0.343 MB/K-token coefficient with the causally-measured 0.045 (range 0.027-0.147) in docs/research/memory-econ-rearchitecture-2026-08-10/session-cost.md:55,60 and docs/research/memory-econ-rearchitecture-2026-08-10.md:259, and rewrite the G7 row (session-cost.md:114) from "-274 MB of ceiling, risk High" to "-20 to -48 MB of ceiling, and 0 MB at zero fill (measured) — REJECT". Then add the one line the repo does not have: the reclaimable term is the +54 MB mean / +118 MB max activity residue per session (810 MB fleet-wide today), which is why a RECYCLE (exit+relaunch, handoff-fire.sh:5877) recovers memory a cap structurally cannot.

**Skeptic: REFUTED** (confidence high)

> The claim's DIRECTION survives (and is understated); its "measured" specifics and its comparative conclusion do not. Corrected form: the published 0.343 MB/K-token context coefficient (docs/research/memory-econ-rearchitecture-2026-08-10/session-cost.md:55) overstates the causal context term by >=7x and plausibly ~18x — measured at 0.019 MB/K-token within-session on physical footprint, and statistically indistinguishable from zero (-0.05..+0.05) both causally and cross-sectionally — because it is an RSS-SHAPED coefficient (rss grows 0.302 MB/K-token over the same edges, 16x the footprint slope) fitted on an age-matched single-wave teammate cohort. So a static window cap buys ~0.1 GB fleet-wide and the operator's no-cap position costs essentially nothing in RAM. BUT the symmetric half, which the claim omits, is equally true: recycling is not a memory lever either. Sigma footprint over the live CC fleet is 4.49 GB, ~62% of it a per-process floor (a fresh single-turn CC process peaks at 188-202 MB) that neither lever touches; the entire above-floor term is ~1.6 GB against 34.5 GB of reclaimable headroom and 0 B swap. Three specifics fail outright: (1) "27-45 MB at a FULL 1M window (measured)" is NOT measured — nothing on this box has been observed above 679 K tokens / 68% fill, the probe was refused at 300 K, and the Opus 1M path was never probed; it converts a null into a positive two-significant-figure range extrapolated 1.5-6x past its support, the same out-of-sample defect as the 343 MB it corrects. (2) "panel-measured at 0.10-0.15" matches no instrument on this box: the fleet's own panel (idl.jsonl rss_mb, n=173/10 sessions, session fixed effects) gives +0.438, ABOVE the published number, while the footprint panel gives 0.019. (3) "activity residue that only a process restart can reclaim" is a residual, not a measurement — it is defined as what survives after a floor, an age term and a token term the claim itself shrank, so shrinking the coefficient inflates it by construction; it is unidentifiable because 0 of 74 within-session fill edges are downward (auto-compact off, a recycle mints a new sid), making tokens/time/activity perfectly collinear; the "only a restart reclaims it" half is untested though the test is one vmmap before and after a handoff-fire --recycle; and the 810 MB figure appears in no artifact in docs/ or ~/.claude/logs/. Cap-vs-recycle is settled by capability and by the "Prompt is too long" death (a pure token-count event with zero memory content), not by megabytes — the memory model should be retired from this axis, not re-fitted.

## Findings

### `[MEASURED][STRENGTH]` The regressor in the published model IS actual resident input tokens, not a window setting — so cap and recycle act through the same single channel, and the cap has no independent channel.

- **Evidence:** docs/research/memory-econ-rearchitecture-2026-08-10/session-cost.md:51-52 — 'n = 21 distinct live sessions, joined /tmp/cc-telemetry/<sid>.json (.pid, .input_tokens, .window) <-> vmmap --summary <pid> <-> ps -o etime='. The fitted term is .input_tokens. Line 67 adds the fatal caveat for the cap question: 'Every live session runs window: 1000000' — the window variable had ZERO variance in that sample, so the fit says nothing at all about the window setting.
- **Source:** `docs/research/memory-econ-rearchitecture-2026-08-10/session-cost.md:51-52,67`

### `[MEASURED][GAP]` The 0.343 MB per K-token coefficient does not reproduce. Causal probe: loading 250K and 458K real input tokens into a fresh CC process adds 14.9 MB and 20.5 MB over a 190.5 MB zero-token baseline — 0.060 and 0.045 MB/K-token, with a marginal slope between the two loaded points of 0.027.

- **Evidence:** Own probe, /private/tmp/.../scratchpad/slopeprobe.sh, run 2026-08-10 23:30: baseline n=8 headless runs mean 190.5 MB peak vmmap physical footprint; p120 = 249,815 tokens (234,111 cache_creation + 15,702 cache_read, from --output-format json usage) -> 205.4 MB peak; p250 = 457,773 tokens -> 211.0 MB peak. Same binary (~/.claude-220/.../claude.exe), same model (claude-opus-5), same instrument (vmmap --summary, Physical footprint) as the published model.
- **Source:** `scratchpad/slopeprobe.sh + probe3/results.tsv (p120 249815 tok 205.4 MB; p250 457775 tok 211.0 MB)`

### `[MEASURED][GAP]` Today's live fleet refutes the published model directly: it over-predicts the highest-token session by 216 MB (81%). The three highest-token live sessions are among the CHEAPEST.

- **Evidence:** Own join of /tmp/cc-telemetry/*.json -> vmmap --summary -> ps etime, 2026-08-10 23:20-23:35, n=15 fresh. pid 76386: 680K tokens, 313 min, ACTUAL 267.5 MB; published model predicts 228 + 0.343*680 + 0.071*313 = 483 MB. pid 52732 (574K, 311 min) = 271.3 MB; pid 15655 (543K, 314 min) = 260.1 MB. Meanwhile pid 46062 at only 335K tokens and 122 min = 347.9 MB. Re-fitting the published specification on today's n=18 gives FP = 255.9 + 0.034*Ktok + 0.119*min, R2=0.30 (tokens-only R2=0.11) — the coefficient is an order of magnitude smaller and the fit has almost no explanatory power.
- **Source:** `scratchpad/join.py + rows_t1.json; compare docs/research/memory-econ-rearchitecture-2026-08-10/session-cost.md:55`

### `[MEASURED][GAP]` The interactive upper bound is still far below 0.343. A within-session panel (fixed effects, the strongest free instrument) over an 11-minute interval gives 0.147 MB/K-token, or 0.098 excluding one activity outlier.

- **Evidence:** Two full joins 10.6 min apart, same 16 pids. Sessions that grew >5K tokens: n=8, sum dFP = +58.1 MB over sum dTok = +396.5K => 0.147 MB/Ktok. Dropping pid 20495 (+20.7K tok but +21.4 MB — activity, not context) gives 36.7/375.8 = 0.098. Sessions with zero token growth moved -0.6 to +0.9 MB, confirming instrument noise is ~1 MB.
- **Source:** `scratchpad/rows_t0.json vs rows_t1.json panel diff`

### `[MEASURED][STRENGTH]` The window SETTING costs nothing at zero fill. A 1M-eligible session and a CLAUDE_CODE_DISABLE_1M_CONTEXT=1 session at the same near-zero token count are indistinguishable — the capped arm is nominally HIGHER. This is the single fact the brief said would decide whether the cap has independent value: it does not.

- **Evidence:** Own interleaved A/B probe, 4 reps each, identical prompt/model/cwd, peak vmmap physical footprint: A (1M eligible) 186.9 / 193.7 / 191.7 / 189.6 MB, mean 190.5; B (1M disabled) 192.9 / 192.8 / 191.5 / 194.2 MB, mean 192.9. Difference +2.4 MB in FAVOUR of the uncapped arm, inside the 7 MB within-arm spread. No preallocation by window size exists.
- **Source:** `scratchpad/windowprobe2.sh + probe2/results.tsv`

### `[MEASURED][STRENGTH]` The dominant variable term is neither tokens nor age — it is per-session activity residue, and only a process restart clears it. That is the real memory case for recycling, and a cap cannot touch it.

- **Evidence:** Decomposing the 15 fresh live sessions as fp - 215 (measured interactive floor: pid 34548, 0 tokens, 43 min, 215.1 MB) - 0.045*Ktok leaves a residual of +7 to +118 MB, median +53, total 810 MB. It does not track age: the three oldest sessions (311-314 min) carry +21 to +30 MB (0.07-0.10 MB/min) while pid 46062 at 122 min carries +118 MB (0.97 MB/min) and pid 20495 at 83 min carries +109 MB (1.32 MB/min). A recycle is exit-then-relaunch of the process in the same pane (scripts/handoff-fire.sh:5877 'recycle mode pre-pass: exit + relaunch in the CURRENT pane'; :6758 'exit-then-relaunch via recycle_fire'), so it returns the session to the ~215 MB floor and zeroes this term. A window cap leaves 100% of it in place.
- **Source:** `scratchpad/rows_t1.json decomposition; scripts/handoff-fire.sh:5877,6758`

### `[MEASURED][NEUTRAL]` THE CURVE: moving the recycle threshold across the entire 30-60% band is worth ~110 MB across a 16-session fleet — 0.17% of 64 GiB. Abolishing the policy entirely (ride every session to 1M) costs 0.25 GB.

- **Evidence:** Assuming linear growth from a ~30K fresh-session floor to threshold X and reset, mean resident tokens = (30 + 1000X)/2 K. At the causal slope 0.045 MB/Ktok on a 215 MB floor: X=30% -> 165K mean -> 222.4 MB/session -> 3.48 GB over 16; X=40% -> 224.7 -> 3.51 GB; X=50% -> 226.9 -> 3.55 GB; X=60% -> 229.2 -> 3.58 GB; no policy (1M) -> 238.2 -> 3.72 GB. Per-session CEILING (every session simultaneously at threshold): 228.5 / 233.0 / 237.5 / 242.0 / 260.0 MB. At the conservative panel slope 0.147 the same band is 3.74 -> 4.08 GB (diff 0.35 GB); even at the REFUTED 0.343 it is only 4.24 -> 5.05 GB. Machine state now: 12.6 GB free + 22.8 GB inactive + purgeable, 0.00 M swap in use, all CC processes ~5.4 GB of 64 GiB — memory is not a binding constraint at any point on this curve.
- **Source:** `scratchpad curve computation over own slope; vm_stat / sysctl vm.swapusage 2026-08-10 23:35`

### `[MEASURED][GAP]` The published model's own adversarial pass already flagged the weakness that turned out to be fatal, and the correction it applied was insufficient.

Adding one control to a 21-point sample where high-token sessions were also long-lived and heavily-active does not separate tokens from activity — and today's data contains the counterexample class it needed: three 300+ minute, 540-680K-token sessions sitting at 260-271 MB.
- **Source:** `docs/research/memory-econ-rearchitecture-2026-08-10/session-cost.md:184-187`

### `[MEASURED][STRENGTH]` Corrected reading of the brief's premise: it is NOT true that 'a cap and recycling reach the same memory outcome by different means'. They reach different outcomes, and recycling is strictly better on the measurement.

- **Evidence:** Three measured legs: (1) the window setting alone costs 0 MB (A/B probe), so a cap acts only by bounding tokens; (2) bounding tokens is worth 0.045 MB/K-token, i.e. 45 MB even from 1M to 0 — the entire prize a cap can win per session; (3) the 810 MB of live fleet excess sits in an activity term a cap cannot reach and a process restart fully reclaims. So the cap wins at most ~45 MB/session in a regime nothing reaches (0 of 61 sessions above 85%), while paying the doctrine cost session-cost.md:114 itself names ('invalidates the whole Context-Stewardship threshold system ... forces ~5x more handoffs').
- **Source:** `synthesis of the probes above + docs/research/memory-econ-rearchitecture-2026-08-10/session-cost.md:114`

## Unknowns

- Whether the original n=21 dataset would reproduce 0.343 if re-fit — the joined data was not persisted (only the fitted line survives in session-cost.md:55), so I can refute the coefficient against today's fleet and against a causal probe, but I cannot audit the original arithmetic.
- Whether my causal probe understates interactive residency. A `claude -p` single-turn process holds the prompt but not rendered TUI scrollback, accumulated tool_result objects, or long-lived subagent state. The panel estimate (0.098-0.147) is the interactive-side bound; the true interactive slope is somewhere in 0.045-0.147 and I did not narrow it further.
- What the +7 to +118 MB per-session activity residue actually IS. It does not track age or tokens; candidates are JavaScriptCore heap fragmentation, retained tool_result buffers, and per-tool-call transients. Whether it plateaus or grows unbounded over multi-day sessions is UNMEASURED — the longest live session here is 12.6 h.
- Whether today's median 36% peak fill is caused BY the recycle rails firing, or merely reflects sessions that end for other reasons before reaching a threshold. I measured the outcome distribution, not the mechanism; attributing it to waiting-recycle.sh/boundary-handoff.sh requires the fire-count evidence that belongs to the actuator axis.
- Whether /tmp/cc-telemetry/*.hist (61 sessions, epoch/fill%/tokens time series since the Aug 9 boot) is a supported instrument or an accident. It is the best trajectory data on the box and I found no consumer of it in the memory-econ research; it also inherits the reboot-wipe fragility of the .json telemetry.
- Whether CLAUDE_CODE_MAX_CONTEXT_TOKENS clamps anything (session-cost.md:197-200 leaves it UNVERIFIED). It is moot for memory given the measured slope, but it remains unknown for token-budget purposes.
