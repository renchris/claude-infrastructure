# The 2026-08-13 21:22 wedge — an 80-minute dead shutdown, not a memory storm

**Date:** 2026-08-13 (written the same night, post-reboot)
**Status:** cause chain EVIDENCED from primary instruments; the wedged phase itself is in a window
that macOS structurally cannot log (see §5). Completes the incident ledger in
`crash-rootcause-2026-08-09.md` (this is incident **#7**, and it is a **different class** from the
six before it).
**Instruments:** compressor-sentinel jsonl (the one through-window recorder), unified log
(persisted store), loginwindow TAL logs, APFS snapshot XIDs, `/Library/Updates` mtimes,
postgresql@14's own server log, per-process log-volume histograms. Times PDT.

## 1. Verdict

**The machine did not freeze in place — a restart was initiated at 21:21:3x and the shutdown
never completed.** The user, locked out at the lock screen (Touch ID no-match + "INCORRECT
password" at 21:21:05), initiated a restart; the session tore down in perfect order (app-quit
sweep 21:21:37–40, TAL save 21:21:53, logd teardown 21:22:39, user-agent teardown ≤21:22:54); the
shutdown then entered the phase where the **macOS update staged in `/Library/Updates/140-66475`
since Jul 28** gets prepared (`com.apple.os.update-MSUPrepareUpdate` APFS snapshot — the newest
XID on the volume) — and wedged there, kernel alive, screen dead, for **80 minutes**, until the
power button at ~22:42.

Why it looked like the old killer and is not: no watchdog panic fired across 80 minutes (the six
prior deaths panicked in 91–94 **seconds**) because nothing starved — the VM was healthy — and
update phases run with the shutdown-stall watchdog quiescent. Why nothing logged: logd is torn
down *early* in an orderly shutdown, so a wedge after that point erases its own evidence forward,
by design.

## 4. Exonerations and corrections (things the evidence now settles)

- **Not the compressor/storm class** (§2). Task #151's generator problem (reso `next dev`/postcss
  worker leak) remains real and open — it just did not kill the box tonight.
- **postgresql@14 was not "respawning every 10s" as a death cause** — its own server log has NO
  start entries between 08-05 00:20 and today's 22:44 boot. It was silently DOWN for 8 days
  (start attempt died pre-logging; self-healed on today's boot; WAL recovery clean). The
  every-10s pattern in launchd land was the *supervisor's* retry loop, invisible to postgres's
  log — chronic churn, not tonight's wedge. Filed to backlog for its own diagnosis.
- **The chrome_crashpad_handler flood is Cursor's**, not a browser-automation leftover:
  `.ips procPath` = Cursor.app's Electron Framework helper, `responsible: Cursor`. Chronic since
  ≥08-12 23:23, ~5/s while Cursor runs. Dormant now only because Cursor isn't running post-boot.
  Its Crashpad DB is clean (settings.dat only), so the classic corrupt-database cause is out —
  diagnose live on next Cursor launch. Real cost: ReportCrash + diagnosticservicesd were two of
  the top log producers all evening.
- **kitty, the CC fleet, Karabiner: not implicated.** Fleet footprint at wedge: 19 node procs /
  1 GB. Karabiner lines in the window are steady BTM/lsd hum (36–50 per 20 s, no spike); its
  presence in the final persisted lines is coincidence of an ongoing churn, not causation.

## 5. What is structurally unprovable, and the one falsifiable follow-up

The wedged phase itself (MSU prepare vs. late unmount vs. dext quiesce) left no record: logd is
torn down before it, the stall watchdog is quiescent through update phases, and a hard power-off
discards whatever page cache held. The MSU attribution rests on: payload staged Jul 28 + prepare
snapshot = newest XID + first orderly restart since staging (both 08-09 exits were panics = dirty
boots) + softwareupdated visibly recovering staging state 2 minutes after boot + 80 min with no
stall panic. **Falsifiable test:** run Software Update deliberately and watch — a second wedge at
"preparing/restarting" confirms; a clean install closes it. Either way the staged-state limbo
ends, which is the actual fix.
