# Grade the operator bottleneck statement clause by clause

*Axis `bottleneck-audit` of the jcode due-diligence wave `wf_363ad50b-f2b`. Synthesis: [`../jcode-due-diligence-2026-08-11.md`](../jcode-due-diligence-2026-08-11.md).*

**Verdict.** Six of nine clauses survive with corrections and three do not — C2/C3/C4/C6/C7 hold as arithmetic, C5's number is right but its cause is a policy constant not "10 cores", C8's sentinel has now demonstrably fired once but is running non-HEAD bytes again and freezes nothing session-shaped, and C1 is the weakest clause in the paragraph because "per-session memory" is not what any live admission control gates on, is not where the memory mass actually sits, and directly contradicts C7 in the same sentence.

**Load-bearing claim.** Every remedy in the operator's statement targets a term that no live admission control in this repo reads, so swapping the agent runtime for a lighter one cannot change the number of sessions this box actually admits — the binding integers today are loadavg 2.0/core, router KMAX 32, and dispatcher ceiling 6, and none of them is a memory term.

**Why it matters.** It is refutable in one grep and it inverts the decision. If someone shows an admission path keyed on resident memory, MCP footprint, or active-session count, the memory argument for migrating becomes live. I read the shipped gate (scripts/lib/capacity-admit.sh:261-381) and it reads exactly two sysctl-derived terms, both fail-open; the panel's independent grep found the same; 127/127 historic refusals came from the load term and 0 from memory, and the memory term is built on a quantity (free+speculative+inactive+purgeable) the repo has separately proved cannot bind. Meanwhile the two integers that DO refuse — KMAX=8×4 and CEILING=6 — are one-line edits requiring no migration. So the paragraph's causal chain ("memory caps us ⇒ slim the footprint ⇒ reach 150") skips the layer where refusal happens, and jcode's headline advantage lands entirely inside that skipped layer.

**Skeptic (adversarial re-check): REFUTED** — confidence high.

> The live Agent-tool spawn gate reads EXACTLY ONE term, and it is the memory term. `hooks/agent-teams-enforce.sh:183` invokes `CC_ADMIT_LOAD_TERM=off cc_capacity_admit agent-tool "<type> spawn"` — the load term is deliberately disabled on the repo's highest-volume spawn surface, leaving `cc_hw_headroom_gb()` (free+speculative+inactive+purgeable vs a 4 GB floor, `capacity-admit.sh:168-181,340-372`) as the sole evaluated predicate, and its own denial text reads "This is memory pressure, not policy" (`agent-teams-enforce.sh:188`). Separately, `bin/cc-dispatch:51-52` admits on `free_slots = max(0, CEILING − live_workers)` — an ACTIVE-CONCURRENCY term, which is precisely the operator's second remedy ("admitting on active count"). So the correct statement is a BINDING claim, not a READS claim: "Two of the operator's three remedies target terms that live admission control already reads — memory headroom on the Agent path and active worker count in the dispatcher — but neither has ever refused: 0 capacity-admit refusals of any term across 40,395 IDL rows, with the memory term reading 30.28–32.02 GB against a 4 GB floor at every one of its 11 live evaluations. A lighter runtime therefore moves the number the gate actually reads, monotonically and in the right direction; whether it moves it across a floor it currently sits 9× above is unproven, and the repo's own roadmap (T3.2) says the term must first be corrected because `inactive` conflates file-backed with compress-only-reclaimable pages."

Skeptic evidence: MEASURED, instrument named in each case.

1. THE KILL — a live admission path keyed on memory, which the claimant named as its own falsification condition. `hooks/agent-teams-enforce.sh:183` (read directly): `if ! CC_ADMIT_LOAD_TERM=off cc_capacity_admit agent-tool "${SUBAGENT_TYPE:-subagent} spawn"; then` → `permissionDecision: "deny"`. The hook's comment block at :151-158 states the reason in the repo's own voice: "WHY THE LOAD TERM IS OFF HERE… Memory headroom is the sheddable, session-attributable quantity §8.5.2's retraction asked for: a subagent's footprint IS reclaimable by not spawning it, so this term's refusal can actually change what it reads — which the loadavg term's cannot." The gate body confirms the single-term path: `capacity-admit.sh:330-337` skips the load verdict when `CC_ADMIT_LOAD_TERM=off`, `:352-372` evaluates headroom and refuses via `_cc_admit_spend … "headroom"`, and `:376-381` records basis `headroom-only`. The repo chose the memory term BECAUSE it is session-attributable — the exact opposite of the claim's premise.

2. LEDGER PROOF IT RUNS LIVE (instrument: `~/.claude/autonomy/idl.jsonl`, 8.9 MB, 40,395 rows, plus 8 rotated .gz generations). `grep -c 'headroom-only'` = 11. The 127 traces to `docs/research/session-capacity-ceiling-2026-08-09.md:152` and `docs/research/scaling-bottlenecks-2026-08-09/09-adv-constants.md:38`, i.e. handoff-fire's SIBLING gate `capacity_gate()` (`scripts/handoff-fire.sh:3692`), which writes handoffs.jsonl through its own `emit_fire_refusal`, is unbounded, and uses the `CC_FIRE_*` namespace. `capacity-admit.sh:96-108` explicitly forbids conflating the two ("Both are correct FOR THEIR CALLERS; folding them into one gate would re-commit the refuted fix"). Worse, that population structurally EXCLUDES the Agent-tool path, since the load term is off there — so a 127-load/0-memory split is measured on exactly the population where the memory term is not the deciding term.

4. SELF-CONTRADICTION ON THE ACTIVE-COUNT REMEDY. `bin/cc-dispatch:51-52`: "ADMISSION — the ONLY capacity-bound step. free_slots = max(0, CEILING − live_workers)"; `:314` `CEILING="${CC_DISPATCH_CEILING:-6}"`; `scripts/dispatch-acceptance.sh:204-209` asserts no admit at or above it. 5. STALE PREMISE. `docs/research/memory-econ-rearchitecture-2026-08-10.md:95` (T1.5) prescribes extending this exact gate with an agent-process-COUNT term, and `:127` (T3.2) prescribes correcting `cc_hw_headroom_gb()` to exclude anonymous-inactive. The claim asserts "no admission control reads memory" about a gate whose in-flight design work is to make its memory term bind harder.

WHAT SURVIVES, NARROWED: the memory term has never refused, and at 36 GB reclaimable vs a 4 GB floor it is 9× from binding — so "swapping the runtime cannot change today's admits" is defensible as an arithmetic statement about the CURRENT floor. What does not survive is the causal chain the claim built on it: the gate does read a memory quantity, that quantity is monotone in per-session resident footprint, and the claim's supporting refusal statistic belongs to a different gate.

**Instrument defect found:** Two, both fatal to the claim's evidence base. (a) POPULATION MISMATCH: the "127/127 refusals from load, 0 from memory" figure is handoff-fire's `capacity_gate()` ledger (handoffs.jsonl, `emit_fire_refusal`, CC_FIRE_* namespace), not `capacity-admit.sh`'s IDL — a conflation `capacity-admit.sh:96-108` explicitly names as a defect, and one whose denominator structurally excludes the Agent-tool path where the memory term is the SOLE term. The live IDL shows 0 capacity-admit refusals of either term, so the 127 cannot be attributed to the load term of the gate under discussion. (b) NON-BINDING READ AS NOT-READ: 0 refusals across 11 evaluations at 30–32 GB against a 4 GB floor is evidence the box was far above the floor at every sample, not evidence the term is unread or unreadable — a control that could only pass. The claim needs "not read" to reach its conclusion; its data supports only "not currently binding."

## Findings

### `[MEASURED]` C1 'true bottleneck is per-session memory' — PARTLY-SUPPORTED, and internally contradictory with C7

- **Evidence:** MEASURED/DOC: memory is wall #1 only for the RESIDENT-count target (scaling-bottlenecks §2 row 1). Every historic admission refusal came from the LOAD term — 127/127, with 0 from memory (session-capacity-ceiling §4 table, instrument: gate's own refusal ledger). The memory term is not merely unfired but 'built on a quantity that cannot bind' (blind-terms §2). And 'per-session' mislocates the mass inside the memory wall: the session PROCESS is 235 MB median / 239 mean / 402 max (n=10, top -l 1 MEM col cross-checked 4/4 against vmmap phys_footprint, 09-adv-constants row 6), and row 8 explicitly CORRECTS the 2.2 GB/active figure to 'session ≈ 0.24–0.4 GB; the rest is the per-WORKLOAD spawned tree'. Finally §11 of the ceiling doc: 'at steady state a session compresses nothing, so seg_pct stays ~0 regardless of session count' — so C1's memory story and C7's crash story bind at different design points and cannot both be 'the true bottleneck'.
- **Source:** `docs/research/scaling-bottlenecks-2026-08-09.md:30-37; docs/research/session-capacity-ceiling-2026-08-09.md:149-168, 396-411; docs/research/scaling-bottlenecks-2026-08-09/09-adv-constants.md rows 6,8; docs/research/session-capacity-blind-terms-2026-08-09.md:63-83`
- **Decision relevance:** jcode's headline value proposition is per-session RAM (27.8–167 MB vs Claude Code 386 MB). That attacks the one term this repo has measured as NOT binding today and NOT enforced by any live gate. Migrating for C1 buys arithmetic headroom on an axis nothing refuses on.

### `[MEASURED]` C2 '~340 MB per resident session' — SUPPORTED as the arrival cost, with a category caveat

- **Evidence:** CLAIMED-in-doc/MEASURED: 340 MB is a paired differential over n=1,194 arrival/departure transitions (axis 01), reproduced in the README. It is NOT the claude process footprint: vmmap phys_footprint gives 216 MB fresh / 232 median / 283 mean / 548 max at 26 h (ceiling doc §2.4, which bans ps RSS as double-counting ~992 MB shared libs/session), and the independent re-derivation gives 235 median / 402 max. So 340 = process + helpers, and it is the correct constant for a budget denominator but the wrong one for 'per-session memory'.
- **Source:** `docs/research/scaling-bottlenecks-2026-08-09.md:30; README.md:568 ("The machine is not the constraint" table, per-session footprint row); docs/research/session-capacity-ceiling-2026-08-09.md:100-113`
- **Decision relevance:** Any jcode-vs-Claude-Code RAM comparison must compare arrival differentials or phys_footprint on the same instrument. jcode's README table is PSS on Linux — a third instrument on a different OS. Comparing 27.8 MB PSS to 340 MB arrival-delta is a category error, and this repo has already been burned by exactly that (ps RSS, iTerm2-on-kitty render census).

## Unknowns

- The 507 MB MCP figure rests on ONE snapshot (22 chrome-devtools-mcp procs / 5.1 GB at 10 sessions) with no named instrument. It is the number that forecloses 150-resident, and it has never been re-measured with vmmap phys_footprint.
- No concurrency above 31 sessions has ever been observed on this box. Every figure from ~40 to ~155 is arithmetic extrapolation; the D1 ramp (19→40→80→150) named in the drive plan has not been run.
- Whether the running compressor-sentinel's 42,679 bytes differ FUNCTIONALLY from HEAD's 52,618 — I proved the inodes and sizes differ but could not read the running image, so the materiality of the drift is unknown.
- The claude.exe self-burst trigger: 54 processes exceeded 4 GB in 11 days, max 41 GB, ramping ~8 GB/min, cause unidentified. At 150 resident that is ~3 events/hour and any one erases the burst margin — this is an unbounded term in the agent process itself, and it is the one term a lighter runtime might actually address, but nobody knows what causes it.
- Per-session token draw for the cloud lane (T3) is unmeasured, so the off-box capacity number is UNKNOWN — the docs' own '~10, not 110' is a placeholder, and the round-trip doc supersedes the 'zero have ever executed' premise without supplying a rate.
- Whether the 4–8 active bound would move at all under a different runtime: it is derived against a policy ceiling of 20, and the box was measured running at load 44.4 'degraded but alive' — the actual degradation curve above the policy line has never been characterised.
