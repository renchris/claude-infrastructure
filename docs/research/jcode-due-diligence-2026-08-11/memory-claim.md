# Adversarial verification of the RAM benchmark

*Axis `memory-claim` of the jcode due-diligence wave `wf_363ad50b-f2b`. Synthesis: [`../jcode-due-diligence-2026-08-11.md`](../jcode-due-diligence-2026-08-11.md).*

**Verdict.** The benchmark's headline (386.6 MB Claude Code, "13.9× more RAM") is an artifact of N=1 PSS accounting plus a non-default jcode config and should be discarded, but the marginal row buried at README lines 227-241 is methodologically sound, corroborated by this repo's own instrument to within 1.6%, and yields an honest default-vs-default saving of roughly 200-260 MB per resident session — which removes RAM from this box's risk register without touching the active-concurrency limit the operator's own statement names second.

**Load-bearing claim.** jcode's Claude Code figure does not contradict this repo's measurement — at the margin the two agree to 1.6% (212.7 MB Linux PSS vs 216 MB macOS phys_footprint), and the entire apparent 1.4-1.8× disagreement is ~174 MB of one-time startup image that N=1 PSS bills to a single session.

**Why it matters.** This is the hinge of the whole proposal. If jcode's Claude Code number were instrument-inflated (an RSS-class figure), the saving would be fictional and the migration case collapses. It is not: derive the marginal from the vendor's own two published points — (2300.6 − 386.6)/9 = 212.7 MB/session — and it lands 1.6% from this repo's independently measured 216 MB fresh phys_footprint, across two operating systems, two instruments, and two Claude Code versions (2.1.86 vs 2.1.220). That cross-validation simultaneously (a) vindicates this repo's own banned-ps-RSS correction, (b) proves the vendor's harness is not cheating on the competitor side, and (c) relocates the real reading of the table from the headline to the marginal row. Refute it by measuring jcode default on this M1 Max with vmmap phys_footprint at 1 and 10 sessions, with a populated memory graph, after 6+ hours resident: a marginal above ~62 MB breaks the band.

**Skeptic (adversarial re-check): REFUTED** — confidence high.

> jcode's Claude Code N=1 figure is not RSS-class inflation — but the "1.6% cross-validation" is an artifact of comparing a MARGINAL to a LEVEL, and the level chosen was the minimum of a measured saturating curve. What survives, in its strongest correct form: (a) the README's 13.9× headline IS an N=1 PSS-accounting artifact and should be discarded — the repo's own instrument reads Claude Code at 216-221 MB fresh, nowhere near 386.6 MB, so the vendor's competitor-side harness is not obviously cheating; (b) the vendor's ~212.7 MB/session marginal row is arithmetically sound as a restatement of its own two published points (it is a secant, NOT an independent measurement); (c) it does NOT agree with this repo's instrument to 1.6% — like-for-like, this repo's own paired-differential ARRIVAL cost is 340 MB/session over n=1,194 transitions (scaling-bottlenecks-2026-08-09.md:30), a 60% disagreement, and the resident object this box actually carries plateaus at ~450 MB within 1.5 h (census-fleet.md:176-186). (d) Consequently the "200-260 MB per resident session saving" is UNKNOWN in magnitude: every jcode number in the corpus is t≈0, and jcode's default config adds a per-turn embedding + memory-graph growth mechanism whose t>0 curve is published nowhere. Direction plausible; magnitude unestablished; the falsification test the original investigator specified (jcode under vmmap phys_footprint on this M1 Max at 6+ h) remains UNRUN, so by this wave's own discipline the claim stands unverified rather than confirmed.

Skeptic evidence: 1. THE COMPARATOR IS WRONG, AND THE RIGHT ONE EXISTS. The vendor's 212.7 MB is a marginal (slope). The claim matched it against 216 MB, which is a LEVEL — one fresh session's whole standalone footprint (docs/research/session-capacity-ceiling-2026-08-09.md:102-103, MEASURED, vmmap phys_footprint). This repo also measures the marginal directly: session arrival cost **340 MB** by paired differential, n=1,194 transitions, "the process itself is 235–270 MB, the rest helpers" (docs/research/scaling-bottlenecks-2026-08-09.md:30, MEASURED; re-affirmed as the settled baseline at docs/research/memory-econ-rearchitecture-2026-08-10/census-fleet.md:347). Marginal-vs-marginal the disagreement is 340/212.7 = **1.60×, i.e. 60%** — not 1.6%. The decimal point is the entire finding.

2. THE LEVEL THE CLAIM PICKED IS THE MINIMUM OF A CURVE THE SAME REPO FITTED. census-fleet.md:176-186 (MEASURED, phys_footprint vs process age, n=16 MAIN): `foot ≈ −177 + 63.3·ln(age_s)`, r²=0.695 — 10 min → 228 MB (obs 218-221), 1 h → 342 MB (obs 343-410), 4 h → 430 MB (obs 447-463), plateau **~450 MB within ~1.5 h, flat for the next 18.5 h**. "216 MB fresh" is the t≈10-min end of that curve. This box's problem is *resident* sessions; the claim applied a t≈0 delta to a population whose settled object is 340 MB at arrival and ~450 MB at plateau.

3. THE VENDOR'S MARGINAL ROW IS NOT AN INDEPENDENT MEASUREMENT. Every entry in /tmp/jcode-README.md:231-241 is exactly (N10−N1)/9 of the two tables above it: jcode-off (117.0−27.8)/9=9.91 vs "~9.9"; jcode (260.8−167.1)/9=10.41 vs "~10.4"; pi (833.0−144.4)/9=76.51 vs "~76.5"; Claude Code (2300.6−386.6)/9=212.67 vs "~212.7". It is a two-point secant, so it inherits every defect of the N=10 point and adds a linearity assumption. Calling it "the buried methodologically sound row" credits it with an independence it does not have.

4. THE 174 MB "ONE-TIME STARTUP IMAGE" IS A RESIDUAL, NOT A MEASURED OBJECT — and the same subtraction refutes the story. Implied intercepts (N1 − marginal) across the README's five JS-runtime CLIs: OpenCode 53.1 · Cursor Agent 57.4 · Antigravity 157.3 · Claude Code 173.9 · Copilot CLI 175.2 MB. A 3.3× spread in what is supposedly a shared runtime image. Nothing in the README measures, names, or decomposes that term (INFERRED, by me, from README lines 71-179).

5. THE TWO ENDPOINTS ARE TWO SEPARATE RERUNS WITH DOCUMENTED VERSION DRIFT. README line ~250 states verbatim: "`GitHub Copilot CLI 1.0.24` for the 1-session rerun, `GitHub Copilot CLI 1.0.27` for the 10-session rerun". A secant whose endpoints are known to have been taken at different times, with at least one subject changing version between them, cannot carry a 1.6% precision claim. Host is named only as "this Linux machine" (README:206, 225) — no RAM size, kernel, distro, CPU, page size, ZRAM/zswap state, or reclaim state at 10× concurrency.

6. THE INSTRUMENT ASYMMETRIES ALL POINT THE SAME WAY, AND IT IS THE WAY THAT MANUFACTURES THE COINCIDENCE. Linux `Pss` counts only resident pages — anonymous pages pushed out move to `SwapPss` and leave PSS. macOS `phys_footprint` explicitly INCLUDES compressed pages, and this box compresses heavily: at the time of the repo's own measurement, 4.6 G compressor / 1.14 GB swap in use / 11.7 GB held compressed (session-capacity-ceiling-2026-08-09.md:97-99, MEASURED via top/vm_stat); census-fleet.md:43 records a 2.4:1 compressor ratio. Second one-way bias: arm64 macOS uses 16 KiB pages (census-fleet.md:23 does its own reconciliation at "1,742,970 × 16 KiB") vs 4 KiB on x86 Linux, which inflates macOS anonymous footprint for identical allocation behavior. Both biases say macOS should read materially HIGHER than Linux PSS for the same program. It reads 1.6% LOWER. The raw near-equality is therefore evidence the two quantities differ, not that they agree.

7. TRUE-BUT-DOES-NOT-SUPPORT, on the operator's own question. The verdict's payoff — "removes RAM from this box's risk register" — is not the vendor's to deliver: this repo's own instrument correction already did it (session-capacity-ceiling-2026-08-09.md:105-113 — 19 sessions = 5.25 GB actual, not 12.9 GB RSS; the two published ceilings built on ps RSS were invalidated). And the terms that actually bind are invariant under a CLI swap: MCP children re-measured to "18 hosts × 325 MB ≈ 5.9 GB, not 49 GB… MCP children do not foreclose 150-resident. The *leak* does" (census-fleet.md:398-399), plus claude.exe self-bursts to 41 GB (scaling-bottlenecks:32) whose named trigger is an argv[0]=`ugrep` re-exec (census-fleet.md, addendum A1) — i.e. a shell/toolchain artifact, and the crash mechanism is compressor-segment exhaustion (census-fleet.md:88-107), not per-session resident RAM. Swapping the CLI does not touch any of those.

INSTRUMENTS NAMED: vendor = Linux PSS (smaps-class), unnamed Linux host, 1 and 10 "active sessions", Claude Code 2.1.86, CLAIMED. Repo = macOS `vmmap`/`footprint` phys_footprint (cross-checked to top MEM within ±1% on 5 pids, census-fleet.md:24-28), M1 Max, Claude Code ~2.1.220, MEASURED. Nothing on this box was measured for jcode at any N — that remains UNKNOWN.

**Instrument defect found:** Four, compounding. (1) COMPARATOR MISMATCH — a marginal (Linux PSS secant, N=1→10) was compared to a level (macOS phys_footprint of one fresh session); the repo's actual marginal, a paired differential over n=1,194 arrivals, is 340 MB and was not used, which turns the headline "1.6%" into 60%. (2) SUMMARY STATISTIC CHOSEN AFTER THE ANSWER — 216 MB is the minimum of the repo's own published distribution (216 fresh / 232 median / 283 mean / 548 max at 26 h) and of a fitted saturating curve plateauing at ~450 MB; median gives 8.4%, mean 33%, arrival cost 60%, plateau 112%. Only the minimum yields 1.6%. (3) UNCONTROLLED SECANT — the two endpoints are separate reruns on an unspecified Linux host, with the README itself admitting a subject version changed between them (Copilot CLI 1.0.24 → 1.0.27), and no statement of memory pressure or reclaim state at N=10, which is precisely what sets PSS. (4) TWO INSTRUMENTS THAT DISAGREE BY CONSTRUCTION IN ONE DIRECTION — Linux PSS drops swapped/compressed anonymous pages (SwapPss is a separate field) while macOS phys_footprint counts compressed pages, and arm64 macOS 16 KiB pages vs x86 4 KiB inflates the macOS side; both make macOS the higher reading for identical behavior, so near-equality is a signal of category difference, not of cross-validation. Additionally, the "~174 MB one-time startup image" that carries the whole reconciliation is never measured — it is N1 minus the secant slope, and the same subtraction over the README's five JS-runtime CLIs yields intercepts spanning 53.1–175.2 MB.

## Findings

### `[MEASURED]` The entire RAM table was measured on Linux using /proc/<pid>/smaps_rollup PSS. There is no macOS number anywhere, and jcode's own platform table rates macOS a tier below Linux.

- **Evidence:** MEASURED-by-vendor, Linux-only. Harness reads Path(f"/proc/{pid}/smaps_rollup") and parses the "Pss:" line (bench_memory_cli.py:309-317); process enumeration walks /proc (:267-284). README states "Measured on this Linux machine across 10 interactive PTY launches" for the timing runs (lines 206, 225). Platform table: Linux x86_64/aarch64 = "Fully supported"; macOS Apple Silicon = "Supported" (README:886-887). No hardware, kernel, distro, CPU or RAM spec is published for the bench machine.
- **Source:** `https://github.com/1jehuang/jcode/blob/main/scripts/bench_memory_cli.py#L309-L317 ; /tmp/jcode-README.md:206,886-887`
- **Decision relevance:** Every figure must be transferred to arm64 macOS before it means anything here. macOS has no PSS at all; the nearest analogue is vmmap phys_footprint, which this repo already uses. Two named mechanisms move the number: macOS arm64 uses 16 KiB pages vs Linux x86_64 4 KiB (per-mapping rounding waste, material at a ~10 MB working set), and phys_footprint excludes shared clean file-backed pages entirely while PSS divides them by N. For the many-client case both accounting rules point the same way (small marginal), so the transfer is plausible but unproven for jcode.

### `[MEASURED]` The 386.6 MB Claude Code headline and this repo's 216/232/283 MB are not in conflict. At N=1, PSS degenerates to the full RSS of the process tree, because every shared page is divided by one and billed to the only session present.

- **Evidence:** MEASURED both sides, INFERRED reconciliation. Vendor's own two points give the marginal: (2300.6 − 386.6)/9 = 212.67 MB, matching the vendor's published ~212.7 MB (README:240). Fixed first-session cost = 386.6 − 212.7 = 173.9 MB. This repo: 216 MB fresh, median 232, mean 283, max 548 at 26 h by vmmap phys_footprint, agreeing with top's MEM column on 4/4 processes (session-capacity-ceiling-2026-08-09.md:101-103). 386.6/216 = 1.79 and 386.6/283 = 1.37 — the operator's 1.4-1.8× band exactly. But 212.7 vs 216 = 1.6% apart.
- **Source:** `/Users/chrisren/Development/claude-infrastructure/docs/research/session-capacity-ceiling-2026-08-09.md:101-103 ; /tmp/jcode-README.md:113,173,240`
- **Decision relevance:** Kills the temptation to dismiss the benchmark as ps-RSS-class marketing. It is not. It also means the ONLY defensible way to read the table for a 15-150 session fleet is the marginal row — the headline bills a one-time 174 MB startup image to session one and is meaningless at N>1.

### `[MEASURED]` "1 active session" means a cold PTY launch, ~4.5 seconds old, with five characters typed into the input box and never submitted. No prompt is sent, no model call is made, no tool runs, and context is zero.

- **Evidence:** MEASURED from harness source. PROBE = "jqx92" (bench_memory_cli.py:20) is written to the pty the moment any meaningful screen content appears (:240-245); the loop breaks as soon as the probe echoes back (:246-248); then time.sleep(settle_s) with DEFAULT_SETTLE_S = 1.0 (:22, :251-252); PSS is sampled immediately after (:426). Session age at sample ≈ time-to-first-input + settle ≈ 3.5 s + 1.0 s for Claude Code (README:221).
- **Source:** `https://github.com/1jehuang/jcode/blob/main/scripts/bench_memory_cli.py#L20-L22,#L240-L252,#L426`
- **Decision relevance:** This is the benchmark's largest silent scope limit. It measures startup image, not resident cost. This repo has MEASURED Claude Code growing 216 → 232 median → 283 mean → 548 MB at 26 h — a 1.07× median / 1.31× mean / 2.54× tail multiplier that the benchmark cannot see on either side. Claude Code's growth curve is known; jcode's is entirely unpublished, so the saving band must borrow Claude Code's own growth envelope for jcode, which is the widest single source of uncertainty in the estimate.

### `[MEASURED]` Child processes ARE counted — the harness sums PSS over the full descendant tree plus process-group members — and the vendor corrected the table for exactly this defect in April, which moved Claude Code's marginal by 41%.

- **Evidence:** MEASURED. sum_tree_pss unions collect_descendants (ppid walk) with collect_process_group_pids (bench_memory_cli.py:287-330). Commit d6d18473 "docs: correct memory benchmarks with process-tree accounting" (2026-04-12) replaced the note "the PSS number includes both client memory and the incremental memory growth of the shared server" with "remeasured using full launched process-tree PSS accounting, so launcher and child runtime processes are included instead of only the top-level PID". Claude Code's marginal across three published reruns by the same author on the same machine: ~309.6 → ~183.2 → ~212.7 MB. jcode's: ~14.6 → ~9.7 → ~10.4 MB.
- **Source:** `https://github.com/1jehuang/jcode/commit/d6d18473 ; https://github.com/1jehuang/jcode/blob/main/scripts/bench_memory_cli.py#L287-L330`
- **Decision relevance:** Acquits the benchmark of the void-comparison charge in the operator's question 4 — neither side is being measured top-PID-only. But the absolutes have swung ±30% across three reruns while the RATIO held near 20× (21.2×, 19.0×, 21.5×). Trust the ratio, never a specific megabyte figure from this table.

### `[INFERRED]` No MCP servers were running for any tool. The bench cwd's project MCP config is empty, so Claude Code's 212.7 MB marginal almost certainly excludes MCP children entirely — and MCP is a config term that migrates to jcode unchanged.

- **Evidence:** MEASURED (config) + INFERRED (consequence). jcode's own .claude/mcp.json is literally {"servers":{}}. Competitors are launched with a bare os.environ.copy() and no home isolation (bench_memory_cli.py:412-414), so they load the author's real dotfiles; whether ~/.claude.json declared user-level servers is UNKNOWN. Nothing in the harness measures jcode under MCP load at all.
- **Source:** `https://github.com/1jehuang/jcode/blob/main/.claude/mcp.json ; https://github.com/1jehuang/jcode/blob/main/scripts/bench_memory_cli.py#L412-L414`
- **Decision relevance:** The single highest-value checkable unknown in the whole proposal: does jcode's shared server host ONE MCP stack fleet-wide, or one per session? If per-session, the MCP term transfers untouched and jcode's harness saving is the only saving. Worth ~5.9 GB at 150 sessions by this repo's own re-projection.

### `[MEASURED]` CHALLENGE TO GROUND TRUTH — the brief's "~507 MB of MCP server children that no budget counted" is refuted by this repo's own later measurement. The real figure is 62 MB/session fleet-wide, and MCP does not foreclose 150.

- **Evidence:** MEASURED, argv[0]-anchored, each proc rooted to a session by ppid-walk, 2026-08-10: 33 live sessions, 12 MCP-class processes, 2.00 GB total = 62 MB per live session. Only 4 of 33 sessions (12%) host a stack at all, because only one project's mcpServers declares chrome-devtools. Per hosting session = 140 MB RSS / ~325 MB footprint. 76% of the class total (1,519 of 2,000 MB) sat in ONE leaked pid. Re-projected: 18 hosts × 325 MB ≈ 5.9 GB at 150, not 49 GB. Verbatim: "MCP children do not foreclose 150-resident. The leak does." The 507 figure traces to a single earlier wave (22 chrome-devtools-mcp procs / 5.1 GB at 10 sessions).
- **Source:** `/Users/chrisren/Development/claude-infrastructure/docs/research/memory-econ-rearchitecture-2026-08-10/census-fleet.md:391-398 ; docs/research/scaling-bottlenecks-2026-08-09.md:31`
- **Decision relevance:** Removes 43 GB of phantom pressure from the migrate case. The bottleneck statement's largest single term is 8× overstated and is a heavy-tailed leak plus a per-project config choice, not a per-session constant. A harness swap does not fix a leak, and it does not fix a project's mcpServers declaration. Also note the brief's "~340 MB per resident session" is an RSS-class figure (bottleneck-refute.md:61 labels it "Session RSS (main+helpers, 340MB)"); the phys_footprint truth is 283 mean.

### `[MEASURED]` This fleet would run jcode DEFAULT, not the 27.8 MB embedding-off headline — and the honest default-vs-default ratio is 2.3× at one session, not 13.9×.

- **Evidence:** MEASURED arithmetic on the vendor's own table. Default-vs-default: 386.6/167.1 = 2.31× at N=1; 2300.6/260.8 = 8.82× at N=10; extrapolated to N=150, 32,079/1,717 = 18.7×. The 13.9× cell compares Claude Code default against jcode with JCODE_MEMORY_ENABLED=0 (bench_memory_cli.py:98). Config choice is forced by this fleet's own practice: a semantic memory graph over prior turns plus embedding-triggered skill injection (README:268-276, 616) is the feature set this repo already depends on in MEMORY.md/skills form.
- **Source:** `/tmp/jcode-README.md:78,83,113,138,143,173 ; https://github.com/1jehuang/jcode/blob/main/scripts/bench_memory_cli.py#L98`
- **Decision relevance:** Good news on net: jcode default's 6× penalty is a ~156.7 MB fixed cost in the SHARED server (167.1 − 10.4), which amortizes to ~1 MB/session at 150. So enabling the memory feature is nearly free at fleet scale, and the honest default-vs-default marginal delta is 212.7 − 10.4 = 202.3 MB/session (Linux, cold). Do not quote 13.9× to anyone.

### `[MEASURED]` jcode's measured configuration has an EMPTY memory graph and an empty home. The headline feature is measured carrying zero data.

- **Evidence:** MEASURED from harness source. Every jcode run gets tempfile.mkdtemp() as JCODE_HOME and JCODE_RUNTIME_DIR (bench_memory_cli.py:356-365), into which only auth files and config.toml are symlinked (:366-376), plus a models symlink for the memory-on arm (:377-381). No memory database, no session history, no prior turns. Also JCODE_TEMP_SERVER=1 (:362) — a non-default temp-server mode. jcode-memory-on additionally receives more settle time than any competitor: max(settle,5.0) after server start and max(settle,2.0) per session vs 1.0 s for others (:395-397).
- **Source:** `https://github.com/1jehuang/jcode/blob/main/scripts/bench_memory_cli.py#L356-L397`
- **Decision relevance:** Cuts both ways and both matter. The extra settle time works AGAINST jcode (more lazy init completes before sampling), which is fair. The empty memory graph works FOR it: the growth of a semantic graph over months of 150-session history is completely unmeasured, and it is the exact thing jcode's own MEMORY_INCIDENT_RUNBOOK sets thresholds for (PSS growth 256 MiB/15 min warn, 1 GiB critical) while naming "headless or detached sessions greatly outnumber attached clients" as an incident precondition — a verbatim description of the regime this fleet would run.

### `[MEASURED]` jcode is measured as one shared server plus N thin clients, while every competitor is N independent processes. This is a genuine architectural difference, fairly accounted, but it relocates where resident context lives — into the one process whose growth curve is unpublished.

- **Evidence:** MEASURED. The harness starts a single `serve --socket` process (bench_memory_cli.py:383-392), waits for the socket, then launches N clients each with `--socket <path>` (:398-407); root_pids includes server_proc.pid (:409) and sample_pgids includes the server's pgid (:392, :410), so the server IS counted. Competitors take the plain branch: N full launches, no shared parent (:415-418). The pre-correction README note said so explicitly: "For jcode, the PSS number includes both client memory and the incremental memory growth of the shared server."
- **Source:** `https://github.com/1jehuang/jcode/blob/main/scripts/bench_memory_cli.py#L383-L419`
- **Decision relevance:** The accounting is honest — the server is not hidden. But the ~10.4 MB marginal is a TUI client's footprint at t≈4.5 s with zero conversation. Every session's transcript, context and memory state lives server-side, so the term that grows over 26 hours has been moved into a single process and then sampled before it could grow. This is why the resident-point band below is wide and why a trial must sample at hour 6+, not at second 5.

### `[INFERRED]` HONEST SAVING ON THIS BOX: roughly 200-260 MB per resident session, central estimate ~230 MB, against a 283 MB mean / 232 MB median Claude Code baseline — i.e. jcode plausibly removes 75-95% of per-session harness footprint.

- **Evidence:** INFERRED, composed from measured parts. Claude Code resident marginal = 283 MB mean / 232 median (MEASURED, vmmap phys_footprint, this repo). jcode resident marginal = 10.4 MB (MEASURED, Linux PSS, cold) × [1.0-2.4 platform/instrument transfer, INFERRED from 16 KiB page rounding and the PSS-vs-phys_footprint accounting difference] × [1.0-2.5 resident growth, INFERRED by borrowing Claude Code's own measured 26 h envelope because jcode publishes none] = 10-62 MB, central ~25 MB. Saving = 283 − 25 ≈ 258 MB central; band 221-273 MB against the mean, 170-222 MB against the median.
- **Source:** `/Users/chrisren/Development/claude-infrastructure/docs/research/session-capacity-ceiling-2026-08-09.md:101-103 ; /tmp/jcode-README.md:240`
- **Decision relevance:** This is the number to put in the migrate/do-not-migrate decision. State it as a band, never a point. Its lower bound rests entirely on an unmeasured jcode growth curve, which is the one thing a trial on this box would settle in an afternoon.

### `[INFERRED]` SESSIONS GAINED AT 64 GB: from ~155 to roughly 730-1,800 — but the target is 150, so RAM was already non-binding after this repo's own instrument correction.

- **Evidence:** MEASURED baseline + INFERRED projection. This repo's model: 283 MB × N + ~20 GB non-Claude baseline ≤ 64 GiB ⇒ ~155 sessions (session-capacity-ceiling-2026-08-09.md:239); my arithmetic on 65,536 − 20,480 = 45,056 MiB gives 159. Substituting the jcode band: @25 MB central → ~1,800 sessions; @62 MB pessimistic → ~727; @10 MB optimistic → ~4,506. Same doc, same correction, notes the non-Claude baseline is the real hog: Dia alone holds 5.0 GB across 24 helpers, kitty 1.6 GB.
- **Source:** `/Users/chrisren/Development/claude-infrastructure/docs/research/session-capacity-ceiling-2026-08-09.md:239`
- **Decision relevance:** The decisive framing for the operator's question. jcode does not take this box from 15 to 150 on memory — this repo's own corrected measurement already puts the RAM ceiling at ~155, three percent above the 150 target. What jcode buys is margin: it converts RAM from 'barely sufficient, one browser away from breaking' into '10-30× headroom, permanently irrelevant'. That is genuinely worth something on a box where closing Dia moves the ceiling more than the harness does. It buys nothing at all against the operator's own second clause — 4-8 simultaneously ACTIVE sessions on 10 cores and 4 account quotas — which no memory benchmark can address and which caps useful concurrency far below either RAM ceiling.

## Unknowns

- jcode's memory footprint on arm64 macOS: ZERO published figures. Every number in the table is Linux x86_64-class PSS. jcode's own platform table rates macOS "Supported" against Linux "Fully supported" (README:886-887) — a tier distinction the vendor chose to make.
- jcode's resident growth curve over hours. No published data at any horizon beyond ~4.5 seconds. The vendor ships docs/MEMORY_INCIDENT_RUNBOOK.md with server thresholds (PSS growth 256 MiB/15 min warn, 1 GiB critical), named failure modes session_payload_growth / non_heap_or_mapping_growth / allocator retention, and an explicit incident precondition of "headless or detached sessions greatly outnumber attached clients" — i.e. jcode's own documentation treats this fleet's exact regime as a memory-incident risk class.
- jcode carrying a POPULATED memory graph. Every bench run uses a fresh temp JCODE_HOME, so the semantic graph has zero entries at sample time. Growth over months of 150-session history is unmeasured, and it is the headline feature.
- Whether jcode's shared server hosts ONE MCP stack fleet-wide or one per session. Unmeasured on both sides — the bench cwd declares {"servers":{}} — and it is the highest-value checkable unknown, worth ~5.9 GB at 150 sessions by this repo's own re-projection.
- The bench machine: "this Linux machine" with no CPU, RAM, kernel, distro or page-size disclosed; and the invocation is unpublished, so whether the released figures used the default --settle 1.0 / --timeout 20.0 is unknown.
- Version skew: the table's Claude Code is 2.1.86 against this fleet's running 2.1.220, and jcode's entry is a dev build (v0.9.1888-dev, be386f2), not the v0.75.0 release. Whether either has moved is unmeasured.
- Whether the jcode figures reproduce at all outside the author's machine. All 6,836 of 6,849 commits are one author's, the harness is self-run, and there is no CI job, no third-party replication, and no published raw JSON for the released table.
