# Risk, maturity, supply chain, and whether the benchmarks are independently reproduced

*Axis `risk-maturity` of the jcode due-diligence wave `wf_363ad50b-f2b`. Synthesis: [`../jcode-due-diligence-2026-08-11.md`](../jcode-due-diligence-2026-08-11.md).*

**Verdict.** No — jcode fails as a production dependency today on grounds that are independent of whether its RAM claims are true: its current release shipped 44 minutes after its own CI failed on that exact commit, its memory numbers are Linux-only PSS from an unreleased dev build with no published methodology and zero independent reproduction, and no macOS memory number for jcode exists anywhere — including from the vendor.

**Load-bearing claim.** Every number that would justify migrating is a Linux PSS measurement of an unreleased dev build, published with no methodology and never independently reproduced — and PSS does not exist on macOS, so jcode's memory footprint on this fleet's actual platform (macOS/arm64, measured by vmmap phys_footprint) is unmeasured by anyone, vendor included.

**Why it matters.** It is the load-bearing claim because the ENTIRE migration rationale is the RAM delta, and this reduces that delta to an unmeasured quantity on the target platform rather than a contested one. It is refutable by exactly one artifact: a macOS/arm64 phys_footprint measurement of jcode under a comparable workload, by anyone. Until that exists, comparing jcode's 27.8 MB (Linux PSS, /proc/smaps, dev build v0.9.1888-dev) against this repo's 216-548 MB (macOS vmmap phys_footprint) is a two-way category error — different metric, different OS — and this repo's own instrument doc already BANS the looser comparison (ps RSS) for exactly this reason. Note the direction of the error is unknown, not favorable: it could go either way, which is precisely the problem.

**Skeptic (adversarial re-check): REFUTED** — confidence high.

> The migration-justifying numbers are NOT unmethodical, NOT unreproduced, and the PSS-vs-phys_footprint gap is NOT unknown in direction — all three sub-claims fail at primary source. The methodology is a 475-line public harness (github.com/1jehuang/jcode `scripts/bench_memory_cli.py`, master), backed by `docs/MEMORY_BUDGET.md`, `scripts/memory_probe.sh` and a standing `scripts/memory_regression_gate.sh` CI gate, with all nine tool versions pinned in the README. Its Claude Code row has ALREADY been independently reproduced on this fleet's own platform with this fleet's own sanctioned instrument: README marginal PSS = (2300.6−386.6)/9 = 212.7 MB/session (Linux, /proc/smaps_rollup) vs this repo's 216 MB fresh (macOS/arm64 vmmap phys_footprint, session-capacity-ceiling-2026-08-09.md:102) and its earlier independent 215 MB (TERMINAL_AGNOSTIC_L3_L4.md:42) — three numbers, two OSes, two instruments, 1.5% spread. PSS also does not belong to the metric family this repo bans: ps RSS was banned for double-counting ~992 MB of shared libraries per session, and PSS is the metric invented to fix exactly that, so pairing it with phys_footprint is the closest correct cross-platform pairing, not a category error. What IS fatally unmeasured is different, worse, and directional in jcode's favour: the harness samples a ~1-second-old idle prompt (launch → probe "jqx92" → sleep settle_s=1.0 → read), so there is no aging term for any tool, while this repo measures working sessions at 216 fresh → 232 median → 283 mean → 548 MB at 26 h; it starts ONE shared jcode `serve` process and attaches N thin clients, counting that server once, while every competitor gets N independent full processes, so "~9.9 MB per added session" and "~212.7 MB per added session" are different units (extra client on a warm server vs extra complete runtime); jcode runs with JCODE_HOME set to a fresh tempfile.mkdtemp(), i.e. its headline memory-graph/embedding feature carries zero accumulated state; and jcode gets max(settle,5.0)s server + max(settle,2.0)s per-session settle against 1.0s for everyone else, with jemalloc decay tuning returning pages during exactly that window. Porting the harness to macOS/vmmap would reproduce all four defects unchanged. So: jcode's macOS/arm64 footprint under real work is unmeasured by anyone — but that unknown is ELECTIVE (a macOS Homebrew formula ships and README lists macOS Apple Silicon as Supported), retireable in an afternoon, and a macOS number alone would not make the 21.5× headline mean what a 150-session budget needs it to mean.

- **Decision relevance:** Three compounding signals: (1) pinning a version is unreliable — JCODE_VERSION=v0.70.0 falls through to a from-source build; (2) a security-relevant credential-scoping change shipped as a bullet point with no advisory, and with no SECURITY.md there is no channel where such things are announced, so a fleet cannot subscribe to security-relevant releases; (3) engineering attention is going to a desktop app while the CLI's CI is red — the surface is widening, not consolidating, which is the opposite of what a pre-1.0 dependency needs before production adoption.

### `[INFERRED]` The RAM tables are launch-time snapshots and structurally cannot speak to the soak behaviour that actually sets a 150-session ceiling.

- **Evidence:** The README reports exactly two operating points — '1 active session' and '10 active sessions' (/tmp/jcode-README.md:66,126) — plus a marginal figure of ~9.9-10.4 MB per added session (:231-234), with timing 'across 10 interactive PTY launches' (:206). No duration, no soak, no long-run drift figure appears anywhere in the tables. By contrast this repo's own macOS measurement of Claude Code is a distribution over session age: 216 MB fresh, median 232 MB, mean 283 MB, max 548 MB at 26h — a 2.5x fresh-to-tail spread.
- **Source:** `/tmp/jcode-README.md:66,126,206,231-234 ; docs/research/session-capacity-ceiling-2026-08-09.md §2.4`
- **Decision relevance:** Even granting every vendor number at face value and on the right OS, a launch snapshot cannot predict a resident ceiling. This repo's own data shows the tail is 2.5x the fresh figure and the tail is what fills 64 GiB. The linear ~10 MB/session extrapolation to 150 sessions is therefore not supported by the published measurements — it is supported by an assumption of no drift that nobody has tested. Labelled INFERRED: I am asserting the benchmark's silence on duration, not that jcode necessarily drifts.

### `[MEASURED]` The question 'migrate from kitty to jcode' contains a layer error that materially understates the blast radius.

- **Evidence:** kitty is a terminal emulator occupying this repo's L3/L4 pane layer (README section 6; docs/plans/TERMINAL_AGNOSTIC_L3_L4.md D1-D6, where iTerm2 and kitty are both first-class and terminal migration is on HOLD). jcode is a coding-agent harness — it replaces Claude Code, the process running INSIDE the pane. jcode's own README positions it against Claude Code, Codex CLI, OpenCode, Copilot CLI, Cursor Agent (/tmp/jcode-README.md:76-120), not against terminals. It has no terminal-emulation capability; its overlapping surface is session spawning ('swarm', :311-325) and a desktop app, not pty rendering.
- **Source:** `/tmp/jcode-README.md:76-120,311-325 ; README.md section 6 ; docs/plans/TERMINAL_AGNOSTIC_L3_L4.md`
- **Decision relevance:** Reframes the risk by an order of magnitude. Adopting jcode is not swapping a terminal behind an existing seam — it is replacing the harness that every hook, skill, slash command, session-close ledger, and the 4-account routing model is built on, none of which jcode implements. The 'it2 -> kitty -> jcode' shim framing is therefore the wrong question: there is no third shim layer, because jcode does not sit where kitty sits. Whatever else is decided, this correction should be made before section-6 rigor is spent.

## Unknowns

- jcode's actual macOS/arm64 memory footprint under any workload, by vmmap phys_footprint or any other macOS-valid instrument — unmeasured by the vendor, by this fleet, and by any third party I could find. This is the single measurement that would make the migration question answerable.
- jcode's memory behaviour over session AGE (soak). Every published figure is a launch-time snapshot; no drift, leak, or long-run figure exists. This repo's own CC data shows a 2.5x fresh-to-tail spread, so the tail is the decision-relevant quantity and it is entirely unknown for jcode.
- Whether jcode reduces the ~507 MB of MCP server CHILD processes named in the bottleneck statement. jcode spawns MCP servers too (31 open MCP issues; #802 hardcoded 30s timeout; v0.68.0 credential-inheritance fix); no data exists either way, and MCP children are per-server OS processes whose footprint is largely independent of the harness language.
- The star-history SHAPE. The stargazers endpoint 404s for my token, and a control against rust-lang/rust and cli/cli 404s identically — so this is my instrument's scope limit, NOT evidence the repo hides data. Trendshift and smooth fork growth support organic acquisition, but I cannot see the daily curve and am not inferring one.
- Whether the 43 CI failures are one flaky non-blocking job or a genuinely red suite. I read run-level conclusions only; I did not open job-level logs. This is the most load-bearing thing a follow-up could cheaply resolve, and it could partially exonerate the release-over-red finding.
- Whether the shipped binaries contain network endpoints beyond telemetry.jcode.sh and api.jcode.sh. I read one crate (jcode-telemetry-core) from source, not the whole tree, and I did not run strings on a downloaded binary — so this is a partial audit, not a clean bill.
- Whether issue #834 (SDK dies on Claude subscription OAuth) is actually fixed. It is labelled 'triage: fixed-pending-release' but I did not confirm the fix landed in v0.75.0; the alternative it names (a per-token API key) is refused by this repo's hard cost gate.
- Whether jcode can authenticate 4 separate Claude Max accounts concurrently at all. Issue #883 shows a single hardcoded ~/.claude credential path with CLAUDE_CONFIG_DIR ignored, which suggests one-account-at-a-time, but I found no positive evidence either way and did not test it.
