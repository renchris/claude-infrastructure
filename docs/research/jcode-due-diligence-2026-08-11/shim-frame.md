# Is "another shim layer" even the right frame

*Axis `shim-frame` of the jcode due-diligence wave `wf_363ad50b-f2b`. Synthesis: [`../jcode-due-diligence-2026-08-11.md`](../jcode-due-diligence-2026-08-11.md).*

**Verdict.** No — the frame is a layer error: jcode is a HARNESS (Claude Code's layer), not a terminal, so it can never be a third shim under kitty; and the console face README §6 says is missing is not in jcode either (it exists only as a "Status: Proposed" doc, and by its own non-goals could only ever render jcode's own sessions) — that face already ships, today, in herdr and cmux, neither of which requires replacing the harness.

**Load-bearing claim.** jcode cannot be a third shim layer under kitty because it is not a terminal — it is a harness at Claude Code's own layer, running INSIDE kitty; and the console README §6 says is missing is not in jcode either (Status: Proposed, and non-goaled out of ever showing a non-jcode session), while it does already ship in herdr and cmux, neither of which requires changing the harness.

**Why it matters.** It is the claim that decides the operator's question by dissolving it rather than answering it, and it is the one most exposed to refutation: a single counter-artifact kills it. Show me a jcode pane/window API, a `jcode sessions list` that enumerates non-jcode agents, or a shipped multi-session workspace on macOS, and the framing survives. I looked in the four places such a thing would have to live — the README, docs/SERVER_ARCHITECTURE.md, docs/MULTI_SESSION_CLIENT_ARCHITECTURE.md, and jcode.sh/docs — and found instead a single-server/single-surface-per-client model, an explicit non-goal of being a multiplexer for arbitrary applications, and a workspace design still marked Proposed. The strongest thing I found FOR jcode on this axis (spawn_hook: the it2-kitty problem solved by config) cuts the same way, because it routes only jcode's own spawns.

**Skeptic (adversarial re-check): REFUTED** — confidence high.

## Findings

### `[MEASURED]` jcode occupies Claude Code's layer, not kitty's — so "it2 → kitty → jcode" stacks two things that are not in the same stack.

- **Evidence:** MEASURED by reading jcode's own architecture doc: "jcode uses a single-server, multi-client architecture. One server process manages all sessions and state; TUI clients connect over a Unix socket." The clients are TUI programs that RUN INSIDE a terminal (kitty/wezterm/alacritty/iTerm are enumerated as host emulators it detects). jcode has no pane API, no window objects, and no VT — it is an agent harness competing with Claude Code, Codex CLI and OpenCode (the exact set its own RAM table benchmarks against). The correct stack is: terminal (iTerm2 | kitty | Ghostty | cmux) → harness (Claude Code | jcode) → shim (it2-kitty, needed only because Claude Code's pane backend hardcodes iTerm2).
- **Source:** `https://github.com/1jehuang/jcode/blob/master/docs/SERVER_ARCHITECTURE.md (Overview); /tmp/jcode-README.md:63-120 (RAM table peers)`
- **Decision relevance:** Kills the framing outright. "Is a third shim worth it" cannot be answered because there is no third shim on offer — adopting jcode is a HARNESS migration, which is governed by the cost gate and the 79-hook/7,065-test Claude Code coupling, not by the pane layer at all.

### `[MEASURED]` There is no it2-shaped surface on jcode to shim, because jcode already ships the seam natively — by config, not by decompilation.

- **Evidence:** MEASURED in docs/SPAWN_HOOK.md: `[terminal] spawn_hook` (env `JCODE_SPAWN_HOOK`) takes over EVERY headed spawn — swarm agents, resume-in-new-terminal, self-dev, restart. Contract is `<spawn_hook> <jcode-binary> <args...>`, with `JCODE_SPAWN_KIND/SESSION_ID/TITLE/CWD/COMMAND` in env, a matching `focus_hook`, and a documented kitty example verbatim: `spawn_hook = "kitty @ --to unix:/tmp/kitty.sock launch --type=tab --"`. It also forwards the CLIENT's terminal env (KITTY_WINDOW_ID, TMUX, ZELLIJ_SESSION_NAME…) to the long-lived server so hooks target the terminal the user is actually attached to (issue #405).
- **Source:** `https://github.com/1jehuang/jcode/blob/master/docs/SPAWN_HOOK.md`
- **Decision relevance:** This is the one genuinely superior architectural fact about jcode on this axis, and it is worth naming honestly: what bin/it2-kitty (1,003 lines, born from decompiling Claude Code 2.1.219) achieves by impersonation, jcode grants as a supported extension point. But it transfers NOTHING to the current fleet — it routes jcode's spawns only. It is an argument for what Claude Code should ship, not an argument for migrating.

### `[MEASURED]` Even for a real terminal, "another shim LAYER" overstates the cost by an order of magnitude — the repo's seam already makes it one sibling file.

- **Evidence:** MEASURED at bin/cc-pane:27-30: "DRIVER RESOLUTION (plan §6.5). This file is front-end + dispatcher AND carries the `iterm2` driver as the built-in incumbent. Any other driver X resolves to a sibling executable `cc-pane-X` — so `headless` → bin/cc-pane-headless, and D4's future kitty/cmux drivers drop in with ZERO edits here." D4 sizes such a driver at "~150 lines each behind a proven interface".
- **Source:** `/Users/chrisren/Development/claude-infrastructure/bin/cc-pane:27-30; docs/plans/TERMINAL_AGNOSTIC_L3_L4.md:31 (D4)`
- **Decision relevance:** The operator's cost intuition ("another shim layer") is priced against the it2-kitty experience — 1,003 lines, four seams, each a measured outage. That price was paid ONCE, to defeat a hardcoded vendor gate. Adding a terminal today is one ~150-line sibling driver. So terminal cost should not be what decides this; the harness coupling should.

### `[MEASURED]` jcode does NOT deliver README §6's console today. The three features that look like it are all single-session, in-session UI.

- **Evidence:** MEASURED against the README: the side panel is "a place for auxiliary information" written by THAT session's agent (file loading, diff viewer, mermaid) — it is a second column inside one session, not a fleet view. Info widgets "only ever take up the negative space on the screen" of one session. Swarm is agent-to-agent messaging (DM/broadcast, conflict notification, coordinator/worker spawn) — a coordination substrate, functionally analogous to this repo's two-way comms, with no operator-facing session roster at all. Corroborating negative: WebFetch of https://jcode.sh/docs returned "No session manager, dashboard, or multi-session workspace tool is documented on this page" (CLAIMED — small-model read of one docs page).
- **Source:** `/tmp/jcode-README.md:292-325; https://jcode.sh/docs`
- **Decision relevance:** Removes the strongest possible non-RAM argument for jcode. If the pitch were "jcode accidentally ships the console", that would outrank the RAM table; it does not ship it.

### `[MEASURED]` jcode's console EXISTS as a design — and it is remarkably close to §6's shape — but it is unbuilt, and its own non-goals mean it could never render a Claude Code session.

- **Evidence:** MEASURED in docs/MULTI_SESSION_CLIENT_ARCHITECTURE.md, first line: "Status: Proposed". The design is startlingly aligned with §6: a workspace-map info widget that is "shape-first and text-light", one rectangle per session, encoded idle=dim / focused=bright / running=animated border / completed=green / waiting=yellow / error=red / detached=dashed; and explicitly "not a tiled multi-pane dashboard where many sessions are all visible at once" but a Niri-style camera showing "one full-size session at a time" — i.e. §6's "one row per session, zoom on demand". But the same doc's Non-Goals include "Building a general-purpose terminal multiplexer for arbitrary applications", and surfaces attach to "server-owned" jcode sessions only.
- **Source:** `https://github.com/1jehuang/jcode/blob/master/docs/MULTI_SESSION_CLIENT_ARCHITECTURE.md`
- **Decision relevance:** Two independent disqualifiers on the console axis, either fatal. (1) Unshipped — a Proposed doc is not a face. (2) Structurally exclusive — its surfaces are views of jcode sessions, so it can only be the fleet console if the whole fleet becomes jcode. §6's console must render Claude Code sessions on four Max accounts; jcode's cannot, ever, by design.

### `[MEASURED]` cmux beats jcode on the console axis by a CATEGORY, not a margin — because cmux is a terminal, its console renders whatever runs in it, including today's Claude Code fleet.

- **Evidence:** MEASURED in this repo's own §6 table: cmux ships "built in — sidebar row per pane, blue ring on attention, notifications panel, `notify` CLI" plus "`CMUX_SURFACE_ID` + full socket API" (README.md:653), and external drive was proven end-to-end from an iTerm2-parented shell — `cmux list-panes`, `cmux new-split right`, `cmux send` verified by an independent on-disk oracle, with the `cmuxOnly` default as negative control (TERMINAL_AGNOSTIC_L3_L4.md:236-256). Unmeasured for both: cmux "not run under load" (README.md:653).
- **Source:** `/Users/chrisren/Development/claude-infrastructure/README.md:653,659; docs/plans/TERMINAL_AGNOSTIC_L3_L4.md:236-263`
- **Decision relevance:** If the console is what the operator actually wants, cmux is already the candidate, is already unblocked for external control, and needs no harness change and no cost-gate exemption. Ranking jcode above it on this axis would invert the evidence.

### `[MEASURED]` The console §6 says is missing already ships as a product that natively recognizes Claude Code with zero hooks — herdr — and jcode's own documentation treats herdr as the layer ABOVE it.

- **Evidence:** MEASURED: herdrdev/herdr — Rust, Apache-2.0, 27,171 stars, created 2026-03-27, 141 open issues, "the runtime your coding agents live on" (gh api repos/herdrdev/herdr, read 2026-08-10). CLAIMED (press, not measured here): a sidebar rolling every agent up to blocked / working / done / idle with zero configuration and no hooks, recognizing Claude Code, Codex, Cursor Agent, pi, OpenCode, Copilot CLI and others, each pane a real terminal. MEASURED from jcode's side: docs/HERDR.md is jcode asking to be integrated INTO herdr — it forwards `HERDR_PANE_ID`/`HERDR_SOCKET_PATH`/`HERDR_TAB_ID`, splits the calling pane on `HERDR_ENV=1`, and describes a newline-delimited JSON-RPC `pane.report_agent_session` against `HERDR_SOCKET_PATH` "matching Herdr's Claude Code and Codex model". A plugin ecosystem exists (herdr-reviewr 383★, herdr-file-viewer 376★, herdr-remote 218★).
- **Source:** `gh api repos/herdrdev/herdr; https://github.com/1jehuang/jcode/blob/master/docs/HERDR.md; https://www.shareuhack.com/en/posts/herdr-terminal-agent-multiplexer-guide-2026`
- **Decision relevance:** This is the axis's actionable output and it is bigger than the jcode question. §6 says the beacon is built and "has no face"; herdr is a shipping face that already classifies Claude Code panes into exactly the four states the beacon needs, with a pane-id socket API that is cc-pane-shaped (`HERDR_PANE_ID` ≈ `KITTY_WINDOW_ID` ≈ `CMUX_SURFACE_ID`). It is a stronger lead than jcode on every question this axis was asked, and it costs no harness migration.

### `[CLAIMED]` herdr is NOT literally §6's stated shape, and the difference is the one §6 was careful to specify.

- **Evidence:** §6 asks for "a CONSOLE, not a terminal — one row per session, zoom on demand, no VT implementation, driving kitty underneath" (README.md:534 alt-text / §6 diagram). herdr is described as a terminal multiplexer whose "panes are real terminals" — i.e. it IMPLEMENTS VT and would DISPLACE kitty's pane layer rather than drive it (CLAIMED — from press coverage; not verified against herdr's source).
- **Source:** `/Users/chrisren/Development/claude-infrastructure/README.md §6 diagram alt-text; https://flaviocopes.com/herdr/`
- **Decision relevance:** Prevents a second category error in the opposite direction. herdr delivers §6's OPERATOR EXPERIENCE but not §6's ARCHITECTURE — adopting it re-opens the cost question §6 measured (surfaces-per-window, cadence, threads/pane) against an unmeasured multiplexer, and would sit between kitty and Claude Code, which is exactly where the it2 pane backend lives. Evaluate it on §6's own bench before believing it.

### `[MEASURED]` jcode's documented control surface is real but thin and single-session — it is not a fleet-drivable seam today.

- **Evidence:** MEASURED: `jcode serve` / `jcode connect` (Unix socket), `jcode run` (non-interactive), `jcode --resume <name>`, `jcode --socket … -C … --remote-working-dir` (SSH forwarding), `jcode pair` (WebSocket gateway), `jcode api-bridge` (TypeScript SDK entry). Lifecycle hooks exist (docs/HOOKS.md): turn_end / session_start / session_end / post_tool as detached observers, pre_tool as a gate with a timeout, all env-overridable. No documented `sessions list`, no send-to-session, no address/close verbs.
- **Source:** `https://github.com/1jehuang/jcode/blob/master/docs/HOOKS.md; https://jcode.sh/docs; /tmp/jcode-README.md:643-660`
- **Decision relevance:** A hypothetical `cc-pane-jcode` driver has no `address`/`send`/`close`/`list` to bind to — only spawn (via spawn_hook) and observe (via hooks). Compared to `kitten @` (launch/focus-window/send-text/get-text/close-window, all id-matched) and the iTerm2 Python API, jcode's surface is missing three of cc-pane's five verbs. That is the concrete answer to "could a cc-pane-shaped seam drive it": not today.

## Unknowns

- jcode's macOS server socket path. docs/SERVER_ARCHITECTURE.md documents only `/run/user/$UID/jcode.sock` — a Linux XDG_RUNTIME_DIR path that does not exist on macOS. The README shows `--socket /tmp/jcode.sock` is overridable and the platform badge claims macOS, so this is a documentation gap, not evidence of breakage — but the default is UNKNOWN and untested here.
- Whether Claude Code's Agent-Teams pane backend functions inside herdr AT ALL. D5 measured 40 ITermBackend / 32 TmuxBackend / 0 KittyBackend / 0 GhosttyBackend references in the binary; there is certainly no HerdrBackend. Adopting herdr therefore either needs its own `it2-herdr` (repeating the 1,003-line exercise), or needs herdr to set `$TMUX` convincingly enough for TmuxBackend, or needs herdr to run inside kitty with the existing divert intact. None of these three is measured. This is the single largest hole in the herdr lead.
- herdr under load on this box. Same gap as cmux: no threads/pane, no loaded-app-CPU on scripts/terminal-bench.sh, no memory reading, no multi-hour drift. §6's own ruler has never been pointed at it.
- jcode's TypeScript SDK / `jcode api-bridge` capability surface — not read. If it exposes session enumeration and text injection, the "missing three of five cc-pane verbs" finding weakens (though the layer error stands regardless).
- Whether jcode's swarm coordinator surfaces a worker roster to the OPERATOR (as opposed to to the coordinating agent). docs/SWARM_ARCHITECTURE.md (12.7 KB) and SWARM_TASK_GRAPH.md (29.4 KB) were not read; the README's swarm section describes agent-to-agent messaging only.
