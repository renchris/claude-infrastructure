# The MCP children term — 60% of the footprint, and whether jcode can touch it

*Axis `mcp-term` of the jcode due-diligence wave `wf_363ad50b-f2b`. Synthesis: [`../jcode-due-diligence-2026-08-11.md`](../jcode-due-diligence-2026-08-11.md).*

**Verdict.** No on both halves: the MCP term is ~19-21% of resident cost (measured 1,050 MB total across the WHOLE box today, from exactly 3 sessions), not 60%, and jcode's real shared-MCP pool is unreachable in the pane-per-process model this fleet runs while its stdio-only transport would delete the three HTTP servers that already cost zero — so the counterfactual (one JSON edit in a different repo) strictly dominates jcode on this axis.

**Load-bearing claim.** The ~507 MB/session MCP figure is a dead number: it was ps RSS (an instrument this repo's own §2.4 bans), it was never per-session, and it does not reproduce — today the entire box carries 1,050 MB of MCP children, all of it from 3 sessions, all of it traceable to ONE stdio server declared in a DIFFERENT repo's .mcp.json.

**Why it matters.** It is the load-bearing input to the operator's own arithmetic. At 507 MB the MCP children are 60% of resident cost and "foreclose 150-resident on their own" — which is what makes "MCP consolidation" a named pillar of the 150+ plan and makes jcode's pool look like the answer. At the measured ~75-88 MB/live-session the term drops to ~19-21%, stops being the dominant term, and is removable in full by editing one file — so the pillar it supports collapses whether or not jcode is adopted. Refute it by re-running an argv[0]-anchored, ppid-rooted census with phys_footprint and finding ≥400 MB/live-session.

**Skeptic (adversarial re-check): REFUTED** — confidence high.

## Findings

### `[CLAIMED]` The 507 MB/session figure was measured with ps RSS — the instrument this repo explicitly bans for exactly this purpose — over a 10-session sample, and was flagged med-confidence by its own author.

- **Evidence:** '22 `chrome-devtools-mcp` processes = 2.2 per session, **5,073 MB** ps-RSS = 507 MB/session', with the author's own caveat 'MCP presence is a per-project config fact (browsermcp / chrome-devtools-mcp), not a per-session constant.' The repo's session-capacity-ceiling doc §2.4 bans ps RSS (double-counts ~992 MB shared libs/session) in favour of vmmap phys_footprint. The figure then propagated verbatim into README.md:521 and README.md:569 as a settled constant.
- **Source:** `docs/research/scaling-bottlenecks-2026-08-09/08-platform-terms.md:97 and :23; README.md:521, README.md:569`
- **Decision relevance:** The 60% share in the bottleneck statement is computed from this number. It is not a MEASURED per-session constant, so the arithmetic that makes MCP the dominant term has no verified input.

### `[MEASURED]` This repo already refuted 507 MB/session one day ago, at 8x lower, and the operator's bottleneck statement did not absorb the refutation.

- **Evidence:** Re-census (argv[0]-anchored, each proc ppid-rooted to a session): 33 live sessions, 12 MCP-class procs, 2.00 GB, = 62 MB per live session; 4 of 33 sessions (12%) host a stack; 140 MB RSS / ~325 MB footprint per HOSTING session; 76% of the class total sat in ONE leaked pid. Verbatim finding: 'The 507 MB/session constant is not a per-session term at all... Re-projected: at 150 sessions with today's 12% coverage, MCP = 18 hosts x 325 MB ~= 5.9 GB, not 49 GB. MCP children do not foreclose 150-resident.'
- **Source:** `docs/research/memory-econ-rearchitecture-2026-08-10/census-fleet.md:391, :398`
- **Decision relevance:** The premise 'MCP consolidation is required for 150+' was already disproved internally on 2026-08-10. Any jcode decision justified by that premise is being justified by a superseded number.

### `[MEASURED]` Independent live re-measurement today confirms the refutation and tightens it: 1,050 MB of MCP children on the entire box, from 3 sessions, ~350 MB per HOSTING session.

- **Evidence:** Live census 2026-08-11 ~05:22 UTC. Nine node procs, three 3-process stacks (npm-exec -> chrome-devtools-mcp -> telemetry watchdog), each rooted by ppid to a claude session. phys_footprint via `vmmap | grep 'Physical footprint:'` — 117.3M+98.2M+106.6M = 322.1 MB (host pid 88196), 114.3M+185.5M+107.6M = 407.4 MB (host 6687), 117M+97M+106M = 320 MB (host 58413, top -l1 MEM; the two instruments agreed to 0.3 MB on all six overlapping pids). Total 1,049.5 MB. ps RSS for the same set read 865 MB — RSS UNDER-reads here, so the 507 figure is not even conservative in the safe direction. Live sessions 12-14 (a `ucomm` filter reads 14; a parent/child claude-pair analysis reads ~13) => 75-88 MB per live session.
- **Source:** `live: ps -axwwo pid=,ppid=,rss=,ucomm=,args= + vmmap + top -l 1 -o mem, this box, 2026-08-11`
- **Decision relevance:** Replaces 507 with 75-88 MB/live-session. Against the repo's own 340 MB arrival cost the MCP share is 19-21%, not 60%. MCP is the third term, not the dominant one.

### `[MEASURED]` The whole MCP term is ONE stdio server declared in a DIFFERENT repo, auto-enabled fleet-wide; claude-infrastructure sessions spawn zero MCP children.

- **Evidence:** Every hosting session's cwd resolves to a reso-management-app worktree (`git remote get-url origin` -> git@github.com:renchris/reso-management-app.git for wt-cc-232530-26432, wt-cc-224824-17983, wt-w2-provisioning-console). Source is the repo-root `.mcp.json`: four servers, of which THREE are `"type":"http"` (uidotsh, motion, motion-plus — zero child processes, zero resident bytes) and exactly ONE is stdio (`chrome-devtools` -> `bash scripts/mcp/chrome-devtools-mcp.sh`). Config dirs of the hosting sessions are .claude-tertiary / .claude-secondary, whose own `.claude.json` declares only motion/motion-plus (both HTTP) — so the stdio server arrives purely via the project file plus `enableAllProjectMcpServers`/`enabledMcpjsonServers`. This session's own config dir (.claude-next) has 238 projects and ZERO with mcpServers.
- **Source:** `/Users/chrisren/Development/.worktrees/wt-cc-232530-26432/.mcp.json; ~/.claude-tertiary/.claude.json; ~/.claude-next/settings.json:425-427`
- **Decision relevance:** The term is not a property of Claude Code, of the harness, or of this repo. It is one line in another repo's config. A harness migration cannot be the right lever for a config fact.

### `[MEASURED]` jcode DOES ship a real, refcounted shared MCP pool — this is implemented code, not marketing.

- **Evidence:** `crates/jcode-base/src/mcp/pool.rs`, 526 lines: 'Manages a global pool of MCP server processes that are shared across all jcode sessions. Instead of each session spawning its own set of MCP servers (N sessions x M servers = N x M processes), sessions share a single pool (M processes total).' `struct SharedMcpPool` holds clients/handles/ref_counts; `acquire_handles(session_id)` / `release_handles` do the refcounting; `static SHARED_POOL: OnceCell<Arc<SharedMcpPool>>` with `init_shared_pool()` documented 'Call once at daemon startup.' The `shared` flag defaults to TRUE, including when parsing Claude Code configs (`.and_then(|v| v.as_bool()).unwrap_or(true)`).
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/crates/jcode-base/src/mcp/pool.rs:1-10, :34-38, :182-220, :406-414; .../protocol.rs:199-203, :252-254, :506`
- **Decision relevance:** The capability is genuinely there and is the ONE thing jcode has that Claude Code does not on this axis. It must be priced honestly before being discounted — which the next two findings do.

### `[MEASURED]` jcode's pool is DAEMON-ONLY: in the standalone TUI (one process per pane — this fleet's actual model) every server is spawned per-session exactly as Claude Code does, so the saving is zero unless the fleet also migrates to a serve/connect architecture.

- **Evidence:** `manager.rs:133`: `.partition(|(_, config)| config.shared && self.pool.is_some())` — a server reaches the pool only if `self.pool` is Some. `pool` is Some only via `with_shared_pool` / `with_shared_pool_for_dir` ('Create a manager backed by a shared pool (daemon mode)'); the plain constructor sets `pool: None`. Module header: 'In daemon mode with a shared pool, servers marked `shared: true` (the default) are managed by the pool and reused across sessions.' The README exposes this as `jcode serve` + `jcode connect`, a separate mode from plain `jcode`.
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/crates/jcode-base/src/mcp/manager.rs:3-5, :49-51, :66, :76-89, :133; /tmp/jcode-README.md:652-653`
- **Decision relevance:** Answers the operator's Q4 directly: adopting jcode as a drop-in pane harness buys NOTHING on the MCP term. Capturing it requires abandoning process-per-pane for a daemon + thin clients — a far larger change than a terminal swap, and one that collides with /handoff, per-pane account identity, and Agent-Team pane isolation.

### `[MEASURED]` jcode's transport support is inverted against this fleet's config: it runs stdio ONLY and silently skips HTTP/SSE, so migrating would delete the three servers that cost nothing and keep the one that costs everything.

- **Evidence:** README: 'jcode currently supports stdio (command-based) servers only; HTTP/SSE entries ("type": "http"/"sse") are recognized and skipped with a log line.' Source confirms: `url` field carries the comment 'URL for HTTP/SSE servers (Claude Code compat). Unused by jcode today.' Our live config is 3 HTTP + 1 stdio at reso and 2 HTTP (motion, motion-plus) globally in every config dir. Net effect of migration: uidotsh + motion + motion-plus become unavailable (capability loss, 0 MB saved, since HTTP servers spawn no child); chrome-devtools still spawns.
- **Source:** `/tmp/jcode-README.md:528; https://raw.githubusercontent.com/1jehuang/jcode/master/crates/jcode-base/src/mcp/protocol.rs:204-209`
- **Decision relevance:** Turns jcode's MCP story from a partial win into a negative on this axis. The consolidation lever the operator wants — move stdio to shared HTTP — is the one jcode structurally cannot express.

### `[MEASURED]` Even in jcode's best case, its own design guidance says the ONE server that costs us anything should NOT be pooled.

- **Evidence:** protocol.rs:199-202: 'Whether this server can be shared across sessions (default: true). Stateless API wrappers (Todoist, Canvas) should be shared. Stateful servers (Playwright browser) should not be shared.' chrome-devtools-mcp is a stateful browser-driver — the named class. pool.rs:87-89 hard-excludes it once so marked: 'Non-shared servers are owned per-session (with the session cwd) and must never be spawned in the daemon-global pool (issue #557).' So the correct jcode config for our only stdio server is `shared: false` => per-session spawn => zero saving. Taking the permissive default instead means one browser session's state is shared across all sessions.
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/crates/jcode-base/src/mcp/protocol.rs:199-203; .../pool.rs:87-89, :498-519`
- **Decision relevance:** Closes the last escape route. jcode's pool cannot correctly pool the only server we run — the saving is 0 MB even after a daemon migration, unless we accept cross-session browser-state bleed.

### `[MEASURED]` THE COUNTERFACTUAL: MCP consolidation on Claude Code alone REMOVES the term rather than pooling it — ~11 GB and ~33 resident sessions at 150, for one JSON edit, and it dominates jcode's best case by 3x.

- **Evidence:** Same units throughout, at the repo's own 340 MB/session arrival cost. TODAY: term = 1,050 MB (measured). jcode best case (daemon + pooled, ignoring the shared:false objection) collapses 3 stacks to 1 => 700 MB freed ~= 2 sessions. Opt-in gating of chrome-devtools (remove from reso's `.mcp.json`, or `enabled:false` + per-session `--mcp-config` for the sessions that actually drive a browser) => 1,050 MB freed ~= 3 sessions. AT 150 sessions, holding today's ~21% hosting rate (32 hosts x 350 MB = 11.2 GB): jcode pooling leaves one 350 MB stack => 10.85 GB ~= 32 sessions; opt-in gating leaves 0 => 11.2 GB ~= 33 sessions, AND retains the 3 HTTP servers, AND needs no harness change. Second lever, larger than either: the heavy tail — stack B measured 407 MB against 320/322 MB for the two identical stacks, and census-fleet measured one instance at phys_footprint 1,929 MB / peak 3,213 MB, 76% of that day's class total in a single pid. Third: the 'switch stdio to shared HTTP' lever is ALREADY 75% applied (3 of 4 reso servers are HTTP and cost 0), and the remaining 25% is unavailable because chrome-devtools-mcp ships stdio only.
- **Source:** `live census (this box, 2026-08-11) + docs/research/memory-econ-rearchitecture-2026-08-10/census-fleet.md:398 + /Users/chrisren/Development/.worktrees/wt-cc-232530-26432/.mcp.json`
- **Decision relevance:** This is the decision. The counterfactual is cheaper (one file), larger (removes vs pools), non-destructive (keeps 3 HTTP servers), and available today with zero migration risk. jcode's pool cannot beat it, so the MCP term supplies NO argument for migrating.

### `[INFERRED]` jcode's headline RAM table is silent on MCP children entirely, so it cannot be read as evidence on this axis in either direction.

- **Evidence:** The table reports one number per harness per session (jcode default 167.1 MB, Claude Code 386.6 MB) labelled PSS, with no MCP servers configured and no statement of OS or workload. PSS is a Linux /proc/*/smaps_rollup metric with no native macOS equivalent, and the README names no operating system. Our own measured MCP term (75-88 MB/live session, 350 MB/hosting session) is a separate additive term that would land identically under either harness in per-session mode.
- **Source:** `/tmp/jcode-README.md:59-124, :227-241`
- **Decision relevance:** Prevents a category error: the 2.3x harness-RAM claim and the MCP term are different layers. Whatever the table proves about the 340 MB half, it says nothing about the ~19-21% MCP half — the half the operator called dominant.

## Unknowns

- Whether a single jcode daemon can serve sessions across MANY project dirs correctly. pool.rs:42-44 keeps ONE `config_dir` per daemon, commented 'Keep it stable across reloads because the daemon may serve sessions in many dirs' — but project-local `.mcp.json` resolution is per-dir. `with_shared_pool_for_dir` exists for the per-session OWNED path; the POOL's config appears daemon-global. Unresolved from the three files read: a fleet-wide daemon spanning reso worktrees + claude-infrastructure + 238 projects might spawn reso's chrome-devtools for EVERY session (strictly worse than today) or for none. Resolving this needs client.rs + the serve entrypoint, and ideally a 2-session trial in two different repos.
- The `"shared": true` field appears exactly once in the jcode README (line 539, in an unexplained example) and jcode.sh/docs has no text on MCP process lifetime, sharing, pooling, or per-session spawning at all (WebFetch confirmed). The entire mechanism is source-only and undocumented for operators — so an adopter following the docs would never know the pool exists or that it is daemon-gated.
- jcode issue #557 (cited in pool.rs:88) and #436 (cited at pool.rs:82) indicate the shared/non-shared split and the disabled-server path have both been live bug surfaces. Their current status was not checked — GitHub API rate limit was exhausted mid-investigation.
- Whether the leaked chrome-devtools instance (stack B, 407 MB vs 320/322 MB for two identical siblings; census-fleet measured one at 1,929 MB / peak 3,213 MB) is an upstream chrome-devtools-mcp leak or a Claude Code lifecycle failure to reap. This matters more than the constant — it is the term with the fat tail — and it would follow the MCP server into jcode unchanged, since jcode would spawn the same node child.
- The exact live session denominator: a `ucomm` filter reads 14 claude/claude.exe, while a parent/child claude-pair analysis of 23 `node_modules/.bin/claude` processes reads ~13 real sessions (0 carried `--agent-id`). The per-live-session figure is therefore 75-88 MB, not a single point. It does not change any conclusion (all readings are 5.8-6.8x below 507).
