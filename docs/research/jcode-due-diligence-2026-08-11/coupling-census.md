# What a Claude Code -> jcode migration would actually cost this repo

*Axis `coupling-census` of the jcode due-diligence wave `wf_363ad50b-f2b`. Synthesis: [`../jcode-due-diligence-2026-08-11.md`](../jcode-due-diligence-2026-08-11.md).*

**Verdict.** A jcode swap is not a binary change but a rewrite of this repo's control plane: 42% of the 81 wired hook commands survive with intact semantics, 32% would fire into a channel jcode does not have, 26% have no event to fire on at all, and 100% of hooks/ (97 files, 23,064 LOC) plus the 45 transcript-parsing tools need an I/O rewrite regardless — so migration is a multi-month rebuild whose first casualty is the entire Session Close Protocol, while running jcode BESIDE Claude Code costs almost nothing to integrate and only one thing that matters (a capacity/safety blind spot in the 28 instruments keyed on the `claude` process).

**Load-bearing claim.** jcode has no channel by which a hook can stop or speak to the model at end-of-turn — turn_end is dispatched detached with stdout and stderr set to /dev/null and the source comment says it "cannot block the agent" — so the entire CLOSE_INTEGRITY layer (mechanical 🔧, the SHIP FLOOR, the ✅ close certificate, the ORIGIN Pyramid close contract, cross-turn auto-continue) has no jcode expression and would have to be re-invented on a substrate that supplies no equivalent primitive.

**Why it matters.** It is the claim most likely to be attacked as "you just didn't look hard enough for the extension point", and it is the one I can pin to a specific line of jcode's own Rust rather than to its docs or its README (the README says nothing about hooks at all, and docs/HOOKS.md is already stale — it omits the turn_start event that exists in the source). It is also the highest-leverage claim: hooks exist in jcode, so the shallow reading is "hooks port". The refutable specific is the MODE, not the existence. To refute it you would only need to show one of: a jcode hook event whose non-zero exit or stdout re-enters the conversation at turn end; a documented turn_end gate variant; or a harness-api client-side path (crates/jcode-harness-api) by which an external program could veto a turn's completion and inject text — the last of which I did not exhaustively rule out and is the strongest place to look.

**Skeptic (adversarial re-check): REFUTED** — confidence high.

> jcode's turn_end HOOK cannot block or speak back — it is spawned detached with all three stdio set to Stdio::null and the source says "the hook process cannot block the agent" (crates/jcode-base/src/hooks.rs:222-234). But the hook return path is not the only path back to the model. jcode ships a versioned, publicly documented harness API on a Unix socket (`jcode api-bridge`, $XDG_RUNTIME_DIR/jcode-api.sock, published npm SDK @1jehuang/jcode-sdk) that emits `ServerEvent::TurnDone { session_id }` (crates/jcode-harness-api/src/events.rs:89) and accepts `ApiRequest::SendMessage` and `ApiRequest::SoftInterrupt` (crates/jcode-harness-api/src/requests.rs:50-70). An external supervisor — or a turn_end hook, which receives JCODE_HOOK_SESSION_ID and runs with JCODE_HOOKS_DISABLED=1 precisely so it may call jcode back (docs/HOOKS.md:36,39,146-147) — can therefore observe turn completion and inject text that becomes the next turn. That is the exact primitive CLOSE_INTEGRITY consumes: this repo's own Stop hook does not stop anything either, it emits {decision:"block"} to force another turn (hooks/session-continue.sh:45), and its loop bound lives in its own state file (hooks/session-continue.sh:816, :637), not in the harness. A second, independent hook-to-model channel also exists mid-turn: pre_tool exit 2 returns the hook's stderr to the model as the tool error (docs/HOOKS.md:71-79). What actually survives is narrow and should be stated as the claim: jcode supplies no SYNCHRONOUS VETO of turn completion, and its turn_end notification is asynchronous, so the session reaches idle before an injection lands — a UX race at an operator's desk, immaterial for unattended dispatched sessions; the path additionally requires a resident api-bridge process of UNKNOWN footprint on the very axis that is the operator's bottleneck. CLOSE_INTEGRITY therefore requires a PORT onto an equivalent primitive (Stop-shaped hooks rewritten as TurnDone-driven harness-API clients, plus the I/O rewrite of 97 hook files), not a re-invention on a substrate that supplies none — which materially changes the axis verdict's "32% would fire into a channel jcode does not have" and "the first casualty is the entire Session Close Protocol."

**Instrument defect found:** Two compounding defects. (1) CATEGORY ERROR: the investigation audited the hook-dispatch layer (crates/jcode-base/src/hooks.rs::dispatch_observer) and concluded absence of a capability that lives in the client/API layer (crates/jcode-harness-api). The dispatch-layer fact is true and irrelevant — the hook's own return path was never the only route back to the model, and the investigator's own note conceded the harness-api path was not exhaustively ruled out. (2) ASYMMETRIC COMPARISON: jcode's turn_end was measured against an idealized Claude Code Stop hook that "can stop the model," a premise this repo's own CLAUDE.md (Session Close Protocol, corrected 2026-08-08) and hooks/session-continue.sh:45 both refute — decision:"block" forces another turn rather than stopping one. The two sides of the comparison were measured with different instruments, which turned a difference in ATOMICITY (synchronous vs. asynchronous re-entry) into a claimed difference in EXISTENCE.

## Findings

### `[MEASURED]` jcode HAS lifecycle hooks — 6 events, read from source, not marketing: turn_start, turn_end, session_start, session_end, pre_tool, post_tool. The README mentions 'hook' ZERO times; only docs/HOOKS.md documents them, and that doc is already stale (it omits turn_start, which exists in the source).

- **Evidence:** MEASURED by reading the Rust source. `hook_commands(event)` matches exactly six strings: "turn_start" | "turn_end" | "session_start" | "session_end" | "pre_tool" | "post_tool". `grep -ic hook /tmp/jcode-README.md` = 0. docs/HOOKS.md lists five (no turn_start).
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/crates/jcode-base/src/hooks.rs (fn hook_commands, ~L98-120); https://raw.githubusercontent.com/1jehuang/jcode/master/docs/HOOKS.md`
- **Decision relevance:** Kills the naive 'jcode has no hooks, migration impossible' verdict AND the naive 'it has hooks, so it ports' verdict. The question is not existence but MODE — see the next finding.

### `[MEASURED]` jcode's turn_end (the only analogue of Claude Code's Stop) CANNOT block and CANNOT reach the model. It is dispatched detached with stdout AND stderr wired to /dev/null. Claude Code's Stop hook is where this repo's entire close-integrity layer lives.

- **Evidence:** MEASURED, source: `dispatch_observer()` does `cmd.stdin(Stdio::null()).stdout(Stdio::null()).stderr(Stdio::null())` then `spawn_detached`; the doc comment reads "Detached and fire-and-forget: failures are logged, never propagated, and the hook process cannot block the agent." Against this repo's 12 wired Stop hooks: 7 of 12 depend on blocking or on systemMessage/additionalContext — session-continue.sh (9 block refs + both channels), completion-assert.sh (2), dispatch-assert.sh (6), operator-readout.sh (systemMessage, 6), boundary-handoff.sh (both, 3), goal-inert-watch.sh (both, 1), anti-deference-nudge.sh (2). Only 5 of 12 are pure side-effect and would survive: notify.sh, cache-expiry-tracker.sh, teammate-checkpoint.sh, session-beat.sh, cc-permission-beacon.sh.
- **Source:** `crates/jcode-base/src/hooks.rs L220-250; /Users/chrisren/.claude/settings.json Stop array (12 commands); /Users/chrisren/Development/claude-infrastructure/hooks/{session-continue,completion-assert,dispatch-assert,operator-readout,boundary-handoff,goal-inert-watch,anti-deference-nudge}.sh`
- **Decision relevance:** This is the single load-bearing cost. Mechanical 🔧, the SHIP FLOOR, CUSTODY-as-🔧, the ORIGIN Pyramid close contract, the ✅ close certificate and auto-continue are ALL Stop-blocking mechanisms. On jcode they do not degrade — they become inert. CLOSE_INTEGRITY (2026-08-10) would have to be rebuilt on a substrate that offers no equivalent primitive.

### `[MEASURED]` jcode's pre_tool gate is strictly weaker than Claude Code's PreToolUse: its decision type is a two-valued enum, Allow | Block{reason}. There is no auto-approve, no ask, no input mutation, no additionalContext, and no matcher — the hook fires for every tool and must filter itself.

- **Evidence:** MEASURED: `pub enum GateDecision { Allow, Block { reason: String } }` (hooks.rs L42-46); contract is exit 0 = allow, exit 2 = block with stderr shown to the model, anything else FAILS OPEN by design. Against this repo: rm-safe-allowlist.sh, ship-rail-push-allow.sh, plan-agent-teams-default.sh and agent-teams-enforce.sh all emit `permissionDecision: "allow"` (permission-reduction, not blocking); qos-rewrite.sh emits `hookSpecificOutput.updatedInput` to rewrite the Bash command in flight; validate-bash.sh uses "ask". 16 hooks emit permissionDecision, 2 emit updatedInput.
- **Source:** `crates/jcode-base/src/hooks.rs L42-46 + L254-258; hooks/qos-rewrite.sh:118-122; hooks/{rm-safe-allowlist,ship-rail-push-allow,agent-teams-enforce,plan-agent-teams-default,validate-bash}.sh`
- **Decision relevance:** Two concrete losses: (a) the whole permission-reduction layer that keeps 150 unattended sessions from stalling on prompts has no jcode expression; (b) qos-rewrite.sh — the in-flight Bash rewrite that is part of the toolchain-burst/compressor story — cannot exist, because jcode gives no way to modify a tool call, only to refuse it. Also note jcode's gate FAILS OPEN on timeout/error by explicit design, the opposite polarity to this repo's fail-closed gates.

## Unknowns

- jcode's on-disk session/transcript format is UNKNOWN — SERVER_ARCHITECTURE.md documents ~/.jcode/servers.json and server-side session persistence but no consumer-facing artifact spec. I could not price the rebuild of the 45 transcript-parsing tools because the target format has no published shape.
- Whether the harness API (crates/jcode-harness-api, NDJSON over ~/.jcode/jcode.sock, versioned handshake) can veto or extend a turn from outside. Its own design doc lists 'turn done' as a STREAMING EVENT and permissions as 'permission request event + client response' — which hints an external client CAN answer a permission request even though no pre-permission HOOK exists. If a client can also refuse a turn-completion, part of the close layer might be rebuildable as a socket client rather than a hook. NOT VERIFIED — I read the design doc (status: 'draft, approved direction 2026-07-24'), not the implementation.
- The TypeScript SDK at https://jcode.sh/sdk was not fetched (docs subpage fetches returned only performance copy). Its capability surface — whether it can drive sessions programmatically enough to replace handoff-fire.sh and the two-way comms layer — is UNKNOWN.
- Whether jcode supports per-account credential isolation equivalent to CLAUDE_CONFIG_DIR (111 non-doc/test files depend on it). JCODE_HOME exists (235 source hits) so the mechanism is plausibly there, but I did not verify that jcode's Anthropic OAuth provider honours a per-JCODE_HOME credential store, nor that four Max accounts can be held simultaneously.
- Whether jcode's `pre_tool` gate can see MCP tool names in the same namespaced form Claude Code uses (mcp__ms365__send-mail etc.). enforce-email-formatting.py matches seven such names; if jcode namespaces MCP tools differently that hook needs re-targeting, not just re-plumbing.
- I did not measure hook-dispatch OVERHEAD on jcode.
