# What LAYER does jcode occupy

*Axis `layer-identity` of the jcode due-diligence wave `wf_363ad50b-f2b`. Synthesis: [`../jcode-due-diligence-2026-08-11.md`](../jcode-due-diligence-2026-08-11.md).*

**Verdict.** jcode is an agent harness that runs INSIDE kitty exactly as `claude` does — it replaces the `claude` binary and nothing else, so "migrate from kitty to jcode" is a category error and the it2→kitty→jcode shim chain the operator fears would never exist.

**Load-bearing claim.** jcode occupies the SAME layer as the `claude` binary (agent harness / TUI guest process), not the kitty layer (terminal emulator / pane host) — it cannot replace kitty because it explicitly enumerates kitty as one of the hosts it asks to open windows for it.

**Why it matters.** Refuting it requires showing jcode implements a VT parser, a PTY host, or its own splits. The repo's 80-crate workspace has no such crate (no pty/vt/terminal-emulation crate exists; `jcode-terminal-launch` is a LAUNCHER of other terminals and `jcode-terminal-image` is an inline-image protocol client). jcode's own docs/TERMINAL_CAPABILITIES.md is a compatibility matrix of the emulators it renders into — including a Kitty row — which is a document only a guest writes. Every downstream operator question (shim layers, /handoff, Agent-Team panes, README §6 rigor) collapses onto this one claim: if jcode is a claude-binary replacement, kitty and the it2→kitty pane layer are untouched, and §6's terminal-migration HOLD is not even engaged.

**Skeptic (adversarial re-check): REFUTED** — confidence high.

> jcode's SHIPPED binary is indeed a TUI guest in kitty's cell grid — it hosts no PTY and owns no VT parser (MEASURED: Cargo.lock has no portable-pty / alacritty_terminal / wezterm-term; the one `termwiz` entry arrives only as `ratatui-termwiz`, ratatui's client-side backend). But the conclusion drawn from that — "migrate from kitty to jcode is a category error, so the pane layer is untouched and the it2→kitty→jcode shim chain would never exist" — is FALSE. kitty is two things to this repo (a cell grid AND a remote-controlled pane host/spawner), and jcode contends for the second one in shipped code: `crates/jcode-terminal-launch` is a 1,692-line pane spawner with its own per-backend split/open verbs (tmux `split-window -h -t $TMUX_PANE`, zellij `action new-pane --direction right`, herdr `pane split --current --direction right --focus` then `pane run <pane_id>`, kitty `kitty --title T -e prog`, iTerm2 via `osascript … create window`), driving "visible swarm spawns, resume-in-new-terminal, self-development launches, and restart restores" (docs/HERDR.md). That is the exact function of this repo's handoff-fire.sh / bin/it2-kitty / bin/kitty-split-launch.sh / bin/cc-pane. So adopting jcode installs a SECOND, non-interoperable pane spawner over the same kitty — a peer-layer ownership conflict, not an absent shim — and its kitty backend opens a NEW kitty OS window per spawn, the exact layout README.md:649 measured as the expensive one ("windows for 30 panes: 1" is why kitty won). Separately, jcode-the-product is not single-layer: `crates/jcode-desktop2` is ~700 KB of Rust on winit + wgpu + Vello + Parley (Cargo.toml: "Greenfield jcode desktop app") with app_workspace.rs / scene_workspace.rs / layout.rs, specced as a "Niri-like agent workspace superapp" hosting many session surfaces plus "terminals or command output surfaces" — a window host, not a guest. Narrowing that must survive: desktop2 is `publish = false`, v0.1.0, and ships in NO v0.75.0 release asset (all 9 assets are the single `jcode` binary), so the host client is roadmap, not today.

## Findings

### `[MEASURED]` jcode is a CLI agent harness (TUI client + persistent daemon), not a terminal emulator, not a multiplexer, not an editor.

- **Evidence:** Instrument: `gh api` tree listing of crates/ (80 crates) + direct curl of the docs page. The workspace is all harness parts — jcode-agent-runtime, jcode-provider-* (20 providers), jcode-tui-* (14 crates), jcode-memory-types, jcode-swarm-core — and contains NO VT-emulation or PTY-host crate. jcode.sh/docs, verified by `curl | grep` (not by the summarizer): "a client-server system: the daemon owns sessions, tools, and provider calls, and the TUI is just a client on a socket" and "The TUI runs remotely, your terminal just renders it. Use tmux or zellij so sessions survive disconnects".
- **Source:** `https://api.github.com/repos/1jehuang/jcode/git/trees/11f7565a50f4c24b348c97ee5f9b896d70d95b90 ; https://jcode.sh/docs (23,054 B HTML, HTTP 200)`
- **Decision relevance:** Sets the whole comparison: jcode competes with `claude`, not with kitty. A migrate/do-not-migrate call must be scored on harness features (hooks, subagents, providers, close protocol), never on terminal features.

### `[MEASURED]` jcode's own docs treat kitty, iTerm2, Ghostty, tmux, WezTerm, Alacritty and Handterm as HOST terminals it renders into — including guidance to TUI developers on surviving each host's quirks.

- **Evidence:** Instrument: direct read of the vendored doc. docs/TERMINAL_CAPABILITIES.md is a 14-row capability matrix ("Terminal Emulator Capabilities for TUI Rendering", compiled 2026-03-02) with rows for Kitty, iTerm2, Ghostty, tmux, Handterm; §"Recommendations for TUI Developers" tells the reader to "Always set BGC before erasing" and "Full redraw on SIGWINCH". Only a guest process writes this document.
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/docs/TERMINAL_CAPABILITIES.md lines 8–23, 126–141`
- **Decision relevance:** This is the direct refutation of the operator's premise. jcode does not replace kitty; it is a program you run in kitty. README §6's terminal-migration HOLD (README.md:515) is not engaged by adopting jcode.

### `[MEASURED]` "Handterm" is a DIFFERENT repository and a different binary — that is the terminal emulator, and it is a Wayland-first work in progress with a 63-star audience.

- **Evidence:** Instrument: `gh api repos/1jehuang/handterm` + curl of its README. "A terminal emulator for Wayland and macOS (Metal)"; 63 stars, 10 forks, 7 open issues, created 2026-03-04, last push 2026-07-26. Measured benchmarks are on "Intel Core Ultra 7 256V, 15 GB RAM, Arch Linux, niri Wayland compositor" — no macOS numbers. jcode's own README calls it "This is a work in progress."
- **Source:** `https://api.github.com/repos/1jehuang/handterm ; https://raw.githubusercontent.com/1jehuang/handterm/master/README.md lines 4, 27–63 ; /tmp/jcode-README.md:303`
- **Decision relevance:** If the operator actually wants a kitty replacement from this author, the artifact is handterm, not jcode — a 63-star, Wayland-benchmarked, WIP project on a box that is macOS-only. That is a separate and far weaker decision than the jcode one, and it should not be smuggled in under jcode's 16,951 stars.

### `[MEASURED]` jcode does not draw its own panes, splits or tabs. It DELEGATES window/pane creation to the terminal — and on macOS its built-in paths make new WINDOWS, not splits, so it is strictly weaker than this repo's existing it2/kitty pane layer.

- **Evidence:** Instrument: read of the launcher source. `build_spawn_command` branches: herdr → `pane split --current --direction right --cwd .. --focus`; tmux → `split-window -h`; zellij → `action new-pane --direction right`; handterm → `--backend gpu --exec`; kitty → `kitty --title <t> -e <prog>` (a new OS window, NOT `kitty @ launch`); iterm2 → osascript `tell application "iTerm2" create window with default profile command ...`; Terminal.app → AppleScript `do script`. The comment at line 620 says hooks "that need a single shell-command string (tmux, kitty `@ launch`) can use $JCODE_SPAWN_COMMAND" — i.e. kitty remote-control splits are the USER's job via spawn_hook, not jcode's.
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/crates/jcode-terminal-launch/src/lib.rs lines 620–815 ; docs/SPAWN_HOOK.md lines 1–60`
- **Decision relevance:** Kills the "another shim layer (it2 → kitty → jcode)" worry in its stated form — jcode sits beside claude, not under kitty. But it surfaces the real integration cost: jcode ships its OWN spawn path that decides where a session appears, which duplicates and can fight this repo's it2→kitty layer. Reconciliation is via `[terminal].spawn_hook`, one more owned config surface, and jcode's native macOS behaviour must be overridden or every swarm spawn opens a bare kitty WINDOW instead of a managed split.

### `[MEASURED]` The multi-session workspace UI — the only thing in jcode that would resemble a pane manager — is PROPOSED, not built.

- **Evidence:** Instrument: read of the design doc + the crate it names. docs/MULTI_SESSION_CLIENT_ARCHITECTURE.md line 3: "Status: Proposed"; lines 21–28 state today's model as "session ≈ client ≈ process" with "Each terminal window/process usually hosts one client"; lines 550–588 list Phases 0–6 as future work. The shipped crate `jcode-tui-workspace/src` contains only color_support.rs, lib.rs, workspace_map.rs, workspace_map_widget.rs — the MAP widget, not the multi-surface host.
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/docs/MULTI_SESSION_CLIENT_ARCHITECTURE.md:3,21-28,550-588 ; gh api contents/crates/jcode-tui-workspace/src`
- **Decision relevance:** Any expected-outcome model that assumes jcode manages 150 session surfaces itself is reading a roadmap as a feature. Today N visible sessions still means N client processes in N kitty panes — identical topology to the current fleet.

### `[MEASURED]` `jcode serve` / `jcode connect` is a single-daemon, many-thin-clients model: one server owns ALL sessions, provider connections and a SHARED MCP pool; clients are socket-attached TUIs that reconnect transparently.

- **Evidence:** Instrument: read of the architecture doc. docs/SERVER_ARCHITECTURE.md:11-13 "single-server, multi-client... One server process manages all sessions and state; TUI clients connect over a Unix socket"; the diagram at :24 lists under the server "MCP pool (shared across sessions)"; :76 first run spawns `jcode serve` detached via setsid; :92 idle-timeout 5 min; :121-128 `/reload` execs a new binary and clients auto-reconnect.
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/docs/SERVER_ARCHITECTURE.md:11-13,24,76,92,121-128`
- **Decision relevance:** This is the ONE part of jcode that is a genuine structural answer to the operator's stated bottleneck — and specifically to the ~507 MB/session of uncounted MCP children, which a shared pool eliminates by construction rather than by slimming. It is also a new failure mode the current fleet does not have: one process, one address space, one crash = every session.

### `[CLAIMED]` The server model is a real answer to resident memory in KIND, but its size is unproven here — the README's ~10.4 MB/added-session is a Linux PSS figure, and the documented socket path is Linux-only.

- **Evidence:** Instrument: README table + doc read. README "Extra PSS per added session" jcode ~10.4 MB vs Claude Code ~212.7 MB — PSS is a /proc/smaps metric with no macOS equivalent, and the timing tables state "Measured on this Linux machine across 10 interactive PTY launches". docs/SERVER_ARCHITECTURE.md:133-135 gives the socket as `/run/user/$UID/jcode.sock` — a path that does not exist on macOS (no XDG runtime dir); the doc names no macOS path. macOS binaries DO ship (jcode-macos-aarch64.tar.gz in v0.75.0), so a macOS path must exist in code, but it is undocumented.
- **Source:** `/tmp/jcode-README.md:231-241, 206 ; docs/SERVER_ARCHITECTURE.md:133-135 ; gh api releases/latest`
- **Decision relevance:** The per-session memory win is the entire economic case for migrating, and every published number for it is Linux PSS against this repo's macOS vmmap phys_footprint standard (docs/research/session-capacity-ceiling-2026-08-09.md §2.4). No trial should treat the 10.4 MB as an input; it is the hypothesis a trial would test.

### `[MEASURED]` jcode REPLACES the claude binary; it does not wrap or embed it. The subprocess path that would wrap it exists, is marked deprecated by its own source, and serializes every request behind one global mutex.

- **Evidence:** Instrument: read of the provider source. crates/jcode-provider-claude-cli-runtime/src/lib.rs line 1: "Deprecated Claude CLI provider runtime (subprocess transport)"; line 683 the user-facing string: "Claude transport: deprecated CLI subprocess; prefer `--provider claude` native Anthropic OAuth/API transport."; line 27: "Global mutex to serialize Claude CLI requests" (CLAUDE_CLI_LOCK); line 30 DEFAULT_MODEL = "claude-opus-4-6" and AVAILABLE_MODELS lists only opus-4-6 / sonnet-4-6 / opus-4-5 — no Opus 5.
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/crates/jcode-provider-claude-cli-runtime/src/lib.rs:1,27,30,49-51,683`
- **Decision relevance:** Removes the comfortable middle option. There is no "keep claude, gain jcode's memory model" configuration: the sanctioned path is jcode's own Anthropic transport, so adopting jcode means giving up the claude harness wholesale. And the wrapper that would have preserved it is both deprecated and, with one global mutex across all sessions, structurally incapable of 15 concurrent sessions.

### `[MEASURED]` Cross-harness session resume from Claude Code / Codex / OpenCode / Pi is IMPORT-ONCE (a one-way conversion), not live interop. MCP config is the single live-read exception.

- **Evidence:** Instrument: read of the behaviour doc + README. docs/RESUME_BEHAVIOR.md:25 "Importable external sessions are first converted to a Jcode session, then resumed in place." README:519-521 "Claude Code config is read live on every load rather than copied into jcode's global config" — but README:522-526 for Codex: "a one-time import ... That imported file is then jcode-owned; later Codex changes are not synced automatically."
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/docs/RESUME_BEHAVIOR.md:25 ; /tmp/jcode-README.md:519-526, 610`
- **Decision relevance:** There is no dual-run coexistence story. A migrated session is a jcode session; nothing flows back. A trial is therefore one-way per session, and a mixed fleet means two harnesses with two session stores, not one federated one.

### `[MEASURED]` Process model is the SAME as Claude Code's at the visible layer — one TUI client process per visible session in a pane — with a daemon added underneath, plus a genuine headless path for swarm workers.

- **Evidence:** Instrument: read of the two docs together. docs/MULTI_SESSION_CLIENT_ARCHITECTURE.md:21-28 "session ≈ client ≈ process"; docs/SPAWN_HOOK.md:1-8 lists the headed flows ("swarm agent spawning (`swarm spawn` with `spawn_mode=visible`), resume-in-new-terminal, self-dev sessions, restart restores") — implying a non-visible mode; README:325 "This can be done headlessly or headed."
- **Source:** `docs/MULTI_SESSION_CLIENT_ARCHITECTURE.md:21-28 ; docs/SPAWN_HOOK.md:1-8 ; /tmp/jcode-README.md:325`
- **Decision relevance:** Pane-count pressure — the README §6 interface ceiling — is unchanged by jcode for headed sessions. What jcode adds is a first-class HEADLESS swarm worker, which is the closer analogue to Agent-Team assignees than to /handoff panes.

### `[MEASURED]` The harness layer this repo actually depends on does not survive the swap: jcode has 5 hook points and only ONE can block, and it fails open.

- **Evidence:** Instrument: read of the hooks doc. docs/HOOKS.md:16-18 lists the complete set — turn_end, session_start, session_end, pre_tool, post_tool. :43-45 "`turn_end`, `session_start`, `session_end`, and `post_tool` are **observers**: spawned detached, fire-and-forget. They can never block or slow the agent". Only pre_tool is a gate (:71-83, exit 2 blocks, 5 s default timeout, "Anything else fails open"). There is no Stop/SubagentStop/UserPromptSubmit/PreCompact analogue and no channel that feeds text back to the model at turn end.
- **Source:** `https://raw.githubusercontent.com/1jehuang/jcode/master/docs/HOOKS.md:16-18,43-45,71-83`
- **Decision relevance:** Decisive against migration on this axis alone. The repo's entire Session Close Protocol — completion-assert, session-continue (mechanical 🔧), the ship floor, operator-readout, the origin Pyramid close — is built on a BLOCKING Stop hook that can return text to the model. jcode's turn_end is fire-and-forget by design and cannot block. Migrating means rebuilding that layer or losing it; it is not a port, it is a redesign.

### `[MEASURED]` jcode has a fourth component nobody has named — `jcode-desktop2`, a native GPU-rendered agent console with no PTY — and it is NOT in the shipped release.

- **Evidence:** Instrument: crate listing + release asset listing. crates/jcode-desktop2/src holds 67 files (paint.rs, scene.rs, viewport.rs, transcript.rs, file_tree.rs, editor.rs, frame_meter.rs) and no pty/vt file. docs/DESKTOP_APP_ARCHITECTURE.md: "no Electron/Tauri/web-app shell", stack winit + wgpu, "The UI should not embed the agent runtime directly", "Status: Proposed". v0.75.0 release assets are exclusively `jcode-{platform}` binaries + SHA256SUMS — no desktop app.
- **Source:** `gh api contents/crates/jcode-desktop2/src ; docs/DESKTOP_APP_ARCHITECTURE.md:1-50 ; gh api repos/1jehuang/jcode/releases/latest`
- **Decision relevance:** This is the only jcode component that would displace kitty, and it does so by NOT being a terminal — which is precisely the artifact README §6's diagram names as missing ("a CONSOLE, not a terminal · 1 row per session · no VT — drives kitty underneath", README.md:515 block). It is unshipped and marked Proposed, so it is a convergence signal for the repo's own roadmap, not an adoptable component.

## Unknowns

- What Unix socket path `jcode serve` uses on macOS. docs/SERVER_ARCHITECTURE.md:133-135 documents only `/run/user/$UID/jcode.sock`, which does not exist on macOS; macOS binaries ship, so the code must resolve something else, but it is undocumented and I did not locate it in the source. Unknown whether it is per-user, per-boot, or collides across the 4 accounts.
- Whether ONE `jcode serve` process holding 15–150 sessions is viable on macOS at all — no measurement exists anywhere (jcode's own numbers stop at 10 sessions, on Linux). Single address space and single fault domain are structural facts; their behaviour at this fleet's scale is entirely unmeasured.
- Whether the shared MCP pool actually reduces MCP child-process COUNT on macOS versus Claude Code's per-session children, and by how much. jcode supports stdio MCP servers only — HTTP/SSE entries are "recognized and skipped with a log line" (README:528) — which this fleet's MCP inventory may not satisfy.
- Whether handterm implements splits/panes at all, or only windows. Its README discusses only windows, and jcode's own handterm integration uses `--backend gpu --exec` (new window) where tmux/zellij/herdr get explicit split verbs — INFERRED as no split primitive, not established.
- handterm's macOS/Metal maturity: every published benchmark is Arch Linux + niri Wayland on Intel; there is no macOS measurement in its README.
- Whether `jcode-desktop2` is buildable/usable on macOS today, and on what timeline it would ship — it is in-tree, absent from v0.75.0 assets, and its design doc is marked Proposed.
- What the daemon actually holds per session versus what the thin client holds on macOS — the split is documented in prose (server: messages, tool state, provider; client: input draft, scroll, selection) but never as a measured byte split on any platform.
