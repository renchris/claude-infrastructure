# If jcode were trialled, what is the correct instrument and kill condition

*Axis `trial-design` of the jcode due-diligence wave `wf_363ad50b-f2b`. Synthesis: [`../jcode-due-diligence-2026-08-11.md`](../jcode-due-diligence-2026-08-11.md).*

**Verdict.** README §6's instrument does NOT apply — jcode is a harness, not a terminal, so four of terminal-bench's five axes return NA by construction; the right trial is a 2-hour, 8-session, identical-task A/B read with `top -l 2 -o mem` (phys_footprint-equivalent, 4.8× cheaper than vmmap, verified live this session) counting the whole process tree — but it must not be RUN until jcode's `bills_outside_plan` is established, and the decision will almost certainly be killed on hook capability (81 hook commands over 12 event types vs jcode's 5, observer-only except `pre_tool`) long before any memory number matters.

**Load-bearing claim.** jcode's headline scaling number — ~10.4 MB PSS per added session — was measured across "10 interactive PTY launches", i.e. sessions holding zero conversation, so it measures only the fixed floor and structurally cannot measure the context term, which in this fleet is ~0.343 MB per 1K input tokens (343 MB at the 1M window every live session runs) against a 228 MB floor — roughly half of a mature session's 400–460 MB. A benchmark of freshly-launched PTYs therefore cannot project a resident-session ceiling for this fleet, and the best case even if jcode's floor were zero is ~2×, not ~20×.

**Why it matters.** It is the single claim the whole migration case rests on ("6.0× / 21.5× less RAM"), it is refutable by one measurement (attach a real 500K-token session to jcode and re-read the server's footprint), and if it holds only for empty sessions then the entire memory rationale for migrating collapses to a bounded ~2× — smaller than the capability loss, and smaller than levers already available in place (pin the one repo-level `.mcp.json`, cap the node heap).

**Skeptic (adversarial re-check): REFUTED** — confidence high.

> jcode's RAM tables carry NO stated methodology, so the workload behind ~10.4 MB/added-session is UNKNOWN, not known-empty — the "10 interactive PTY launches" sentence the claim quotes belongs to the two LATENCY tables, not the memory ones. The suspicion is well-founded but unproven: the Claude Code marginal, derived as (2300.6−386.6)/9 = 212.7 MB, sits within 7% of this fleet's independently measured 228 MB floor, which is what a near-empty-session benchmark would produce. "Structurally cannot measure the context term" is not derivable and is false — the instrument could measure it; the workload (unstated) probably did not exercise it, and one loaded-transcript re-run settles it. The load-bearing half — "best case even if jcode's floor were zero is ~2×" — does not follow and is wrong twice over: (1) it holds Claude Code's context slope (0.343 MB per 1K input tokens; n=21, R²=0.71, regressed on Claude Code only) constant across harnesses without measuring jcode's, when 343 bytes/token is ~85× the raw text and is an artifact of a bun-compiled JS object graph, not an information-theoretic floor — and jcode is a single-server/multi-client architecture with a shared MCP pool, so its per-session marginal is a different quantity at a different layer than Claude Code's one-full-OS-process-per-session; (2) it evaluates that slope at 1M-token FILL, conflating window size with fill, at a point in this fleet's own measured distribution that is the tail. Against the fleet's real distribution (216 MB fresh / 232 median / 283 mean / 548 max at 26 h), the fixed floor is 98% of the median session and 82% of the mean — so a floor-dominated benchmark is the RIGHT instrument for the typical session here, not the wrong one. The correct floor-only best case is ~58× at the median, ~5× at the mean, and ~1.7× only at the 26-hour tail session the claim mistook for "mature". The claim's own proposed kill-experiment ("attach a real 500K-token session to jcode and re-read the server's footprint") is the measurement of jcode's slope, which concedes the number is unknown while the ~2× bound asserts it is known.

Skeptic evidence: PROVENANCE — the footnote is from a different table. /tmp/jcode-README.md:206 "Measured on this Linux machine across 10 interactive PTY launches." closes the **Time to first frame** table (lines 193–204); :225 repeats it for **Time to first input** (212–223). WHAT SURVIVES: the marginal-vs-floor coincidence (212.7 vs 228, two different instruments — Linux PSS vs macOS vmmap phys_footprint — on two different CC versions) is real circumstantial support that the added sessions were near-empty. That makes the workload *suspect*, not established, and it does not rescue the ~2× conclusion.

**Instrument defect found:** Three, all in the claim rather than only in the vendor. (1) Cross-table footnote import: the "10 interactive PTY launches" methodology belongs to jcode's two latency tables (README:206, :225); the RAM tables have no stated methodology, so a genuine UNKNOWN was resolved into a known defect — the same failure mode the wave's discipline forbids in the marketing direction, run in the skeptical direction. (3) Tail-point evaluation: the "~2×" is computed at ~1M-token fill / a 400–460 MB "mature" session, above both the median (232 MB) and mean (283 MB) of this repo's own measured distribution; at the median and mean the fixed floor is 98% and 82% of the session, which inverts the conclusion — a floor-ratio benchmark is the appropriate instrument for the typical session in this fleet. ## Findings

### `[MEASURED]` terminal-bench.sh is the WRONG instrument for jcode, and it fails asymmetrically: its per-pid ruler is generic and sound, but its four terminal-specific axes return NA or nonsense by construction.

- **Evidence:** Read of the script. (a) Window census: `layout_probe()` shells `window-census.swift --owner <CENSUS_OWNER>` against CGWindowList (:282-289); jcode is a TUI drawn inside a kitty pane and owns ZERO CGWindows, so the census returns empty → `layout_ok` rc 2 → BLIND_POLLS>0 → `LAYOUT_STATE=uncertified` (:363-370). (b) GPU discriminator: jcode has no case arm, so it falls into `*) GPU_RE='Metal|AGX|IOGPU|wgpu|CGL|OpenGL'` (:187) against a Rust TUI that issues no GPU calls → 0:0 → `GPU_VERDICT=NO-DATA` (:266-268). (c) `--panes N` normalisation (:375-382) divides by TERMINAL panes, a unit jcode does not have. (d) The leak axis the instrument exists for — mach-port/window drift at constant layout — is a WindowServer phenomenon of a windowed app; jcode is not one. What DOES survive is `reading()`'s `top -l 2` second-sample mem/threads/ports (:192-230), which is generic per-pid measurement, not terminal measurement.
- **Source:** `/Users/chrisren/Development/claude-infrastructure/scripts/terminal-bench.sh:187,192-230,266-268,282-289,363-390`
- **Decision relevance:** Answers the operator's §6 question directly: do NOT put jcode through §6's rigor. §6's machinery is a terminal bake-off (iTerm2/kitty/Ghostty/WezTerm/Alacritty/cmux); jcode occupies the harness layer — the same layer as Claude Code itself. Only the `top -l 2` reading primitive is reusable, and it should be lifted into a new harness-bench rather than the terminal script being pointed sideways.

### `[MEASURED]` Pointing terminal-bench at jcode cannot produce a confident-wrong number — it produces a structurally guaranteed `verdict=PARTIAL` with two axes NA. The instrument behaves correctly and is still useless: PARTIAL is the non-verdict that carries no decision.

- **Evidence:** `VERDICT` starts PARTIAL (:305); only a certified layout sets OK (:369); a non-OK GPU profile forces PARTIAL back (:389). Both preconditions are unreachable for a non-windowed process, so every jcode run emits PARTIAL, exit 0.

### `[INFERRED]` PSS does not exist on macOS. The vendor number and this repo's number are two instruments on two kernels and are not comparable even in principle.

- **Evidence:** PSS is Linux `/proc/<pid>/smaps_rollup` — shared pages divided by sharer count. macOS's nearest analogue is the ledger-based `phys_footprint` (`vmmap --summary` / `footprint`), which excludes clean file-backed shared-library pages rather than dividing them. This repo already bans the naive cross-instrument sum in source: 'ps rss summed over sessions OVERCOUNTS ~2.34× (it double-counts shared pages) — do not use it to decide anything.'
- **Source:** `/Users/chrisren/Development/claude-infrastructure/scripts/capacity-alarm.sh:23-31; /tmp/jcode-README.md RAM tables`
- **Decision relevance:** Kills the arithmetic 'jcode 167 MB vs our 400-460 MB ⇒ 2.7× win'. The only admissible comparison is both harnesses measured on THIS box with ONE instrument — which is precisely what the trial exists to do.

### `[MEASURED]` The vendor's marginal-session figure was measured on empty sessions, so it measures the floor and cannot see the term that dominates this fleet.

- **Evidence:** Vendor: '~10.4 MB extra PSS per added session' (jcode default) vs '~212.7 MB' (Claude Code), methodology '10 interactive PTY launches' — freshly launched, zero conversation. ## Unknowns

- Whether jcode's Claude OAuth draws from Max plan limits or from the metered extra-usage path — UNKNOWN by measurement; the README lists a login flow and jcode.sh/docs is silent on billing. Exactly the shape that hid pi-claude's per-token meter behind a subscription login list. Resolvable only by a live before/after read of an account's own meter, and the registry rule forbids wiring it until then.
- What jcode's SERVER footprint does per attached session at real context load. The published ~10.4 MB marginal figure is a thin CLIENT's cost; conversation state lives in the server and no published number describes the server's growth. This is the single measurement the whole memory case turns on, and it exists nowhere.
- Whether a jcode session has a stable per-session pid or any pane-addressable identity. The server model implies it does not — which would break every pane↔pid↔session-id mechanism here (addressing, wake, mail, custody, teardown) — but this was inferred from an architecture doc, not observed.
- Whether jcode's local-embedding memory layer scales sub-linearly with session count. The vendor's own default-vs-off spread is 6.0× at ONE session (167.1 vs 27.8 MB); if the embedding model is per-server it is nearly free at scale, if per-session it dominates. The 10-session row does not disambiguate.
- Whether macOS `phys_footprint` and Linux `PSS` are within a usable factor for the SAME binary. Nothing here calibrates them; no cross-OS memory claim in either direction should be quoted until one binary is measured both ways.
- Whether jcode's `pre_tool` gate is rich enough to carry this fleet's 14 PreToolUse commands. It gets exit 0/2 and stderr, but the docs do not say whether it receives the tool name, arguments, or cwd — and every guard in hooks/ keys on at least one of those.
- Whether the 268 open issues include a class that would fire during a trial. Issue #177 alleges file/folder modifications without confirmation prompts and 'excessive' telemetry on macOS — unverified, single-reporter, but a data-egress and blast-radius question a sandboxed-HOME trial must answer before any real repo is exposed.
