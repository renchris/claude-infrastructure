## The defect: an identifier in the text is not the row's subject

I auto-derived probes from row text — pane id, worktree path, `refs/…`, `session_…` — and ran them
read-only over a 20-row sample. **17 of 20 read "would retire": an 85% rate.** That number is wrong,
and the way it is wrong is the finding.

Spot-checking three of the seventeen:

- `4f31ab82428c` — *"Activate com.claude.desk-invariant — the job that repairs a STALE desk role."*
  My probe retired it because a pane id **mentioned in its prose** was gone. Live check:
  `launchctl list | grep -c com.claude.desk-invariant` → **0**. The job is not loaded. **The row is
  still real.** The pane was a consequence the text described.
- `981a403a05fa` — *"OPERATOR DECISION — where should a failed land file its row?"* Retired because a
  `refs/land/failed/*` string no longer resolved. It is an open policy question; the ref appears
  inside a measurement in its body.
- `0618ec5090a4` — *"Press Ctrl-U in kitty pane 341 to clear a stray composer draft."* Here the pane
  **is** the subject. Genuinely moot. ✓

So the discriminator is grammatical, and it is checkable: **does the row's ACTION VERB govern the
identifier?** Splitting the 13 pane rows on whether the text opens with a verb taking that pane as
its object (`press` · `answer` · `approve` · `confirm-close` · `unfreeze` · `clear` · `re-arm` ·
`close`):

- **subject-keyed: 10** — probe is honest
- **merely mentions: 3** — probe would retire live work

One of the three is `2aa99648bd80`, *"On or after 2026-09-26, unblock this row and read A6"* — a
**date-gated** row. Auto-retirement would have destroyed a row whose whole content is a future
instruction. That is the worst available failure and it was one pattern-match away.

This is the corpus's own rule firing on a new surface:
`discharge-predicate-must-measure-its-own-subject`.

## The door does not save you, and this changes §7's mechanism

§7 leans on `cc-backlog falsify` refusing a lying probe: it runs the probe before storing and
**refuses one that exits 0 against a live row (rc 5)**. Read that against the two cases:

| row | probe says | truth | door verdict |
|---|---|---|---|
| `4f31ab82428c` (live) | moot | live | **refuses (rc 5)** — correct |
| `0618ec5090a4` (moot) | moot | moot | **refuses (rc 5)** — also |

The door cannot tell them apart, because "the probe passes right now" is the only thing it measures.
So it correctly blocks the dangerous attachment **and** blocks the harmless one. The consequence is
structural, not a bug: **a row that is ALREADY moot can never receive a falsifier. It must be
CLOSED.** §7's pipeline (attach → sweep → retire) only ever reaches rows whose premise is still true
*today* and decays *later*. Rows whose premise died before the probe was written are invisible to it.

That is why this pilot's yield is ten CLOSES and zero falsifiers.

a LIST of objects keyed `paneUUID`. Print the parsed set before trusting a membership test.

## What §7 should say instead

1. **Keep the objective.** Premise-first is right: the addressable `open` queue is 0–2 rows while 340
   sit blocked, and a probe that re-runs every tick is what kills the "183 rows unchecked >14 d".
2. **Drop auto-derivation.** A probe must be written from the row's subject by judgment. The
   grammatical test above is a cheap pre-filter, not an authorisation.
3. **Add a CLOSE arm beside the falsify arm.** Already-moot rows cannot be falsified and are the
   ones with immediate yield. The lane's unit of work on a blocked row is *adjudicate*: close it,
   falsify it, or leave it — three outcomes, not one.
4. **Re-scope the population.** 110 probeable, not 309. The other 199 need a human sentence before
   any machine can check them, which is a different and much larger piece of work.
